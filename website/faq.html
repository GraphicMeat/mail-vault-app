Frequently Asked Questions

Everything you need to know about MailVault.

MailVault is a free, open-source desktop email client for macOS that stores your emails locally. It connects to your email accounts via IMAP and saves all messages as standard .eml files (RFC 5322) in Maildir format on your computer, giving you a permanent offline backup with no vendor lock-in.

MailVault connects to your email server using the IMAP protocol and downloads each email as a standard .eml file stored in Maildir format on your Mac. Each email is one file on disk — human-readable, portable, and compatible with any mail client. Once synced, you can safely delete emails from the server to free up space while keeping them accessible locally.

MailVault works with any email provider that supports IMAP, including Gmail, Outlook, Yahoo Mail, iCloud Mail, ProtonMail (with Bridge), Fastmail, Zoho Mail, and any self-hosted or business email provider with IMAP access.

MailVault is free for core features including email reading, composing, search, threading, local archiving, and manual backup. Premium features — scheduled automatic backups, cross-account mailbox migration, and auto-cleanup rules — are available for $4/month or $25/year; the yearly plan includes a 14-day free trial. The source code is available on GitHub. See full pricing for details.

All emails are stored locally on your Mac as standard .eml files organized in Maildir format — one file per email, no database required. Your data never leaves your computer and is never uploaded to any cloud service. Because .eml is a universal standard, your emails can be opened by Apple Mail, Thunderbird, Outlook, or any other mail client — you're never locked in to MailVault.

Directory structure:

~/Library/Application Support/com.mailvault.app/
└── maildir/
    └── you@example.com/
        └── INBOX/
            ├── headers.json          ← cached list for fast loading
            └── cur/
                ├── 1234567890.eml    ← auto-cached email
                └── 1234567891_AS.eml ← archived + seen email

.eml (RFC 5322) is the internet standard format for email messages. Every email — headers, body, and attachments — is stored as a single, self-contained text file. Unlike proprietary databases, .eml files can be opened by any email client (Apple Mail, Thunderbird, Outlook) and read with any text editor.

Maildir is a proven directory structure for storing email, used by mail servers for decades. Each email is one file, so there's no single database that can corrupt — if one file is damaged, the rest of your archive is unaffected. Together, .eml + Maildir mean your emails are future-proof, portable, and never locked in to any single application.

Filename flags:

MailVault appends flag characters to the .eml filename to track status: A = Archived, S = Seen, R = Replied, F = Flagged. For example, 1234567890_AS.eml means the email has been archived and seen.

MailVault is designed with privacy first. Your email credentials are stored in the macOS Keychain, not in plain text. All data stays on your machine — there is no cloud sync, no tracking, no analytics, and no data mining. The app is open source so you can verify the code yourself.

If you delete emails from your email server after MailVault has synced them, they remain safely stored in your local MailVault archive. This is one of the main use cases — back up locally, then free up server storage space without losing anything.

There is a known Microsoft server-side issue affecting personal Outlook.com, Hotmail, and Live.com accounts since late 2024. After signing in with your Microsoft account, the IMAP connection fails with "User is authenticated but not connected." This affects all third-party email clients that use IMAP with OAuth2 — not just MailVault.

Microsoft requires OAuth2 for personal accounts. Unfortunately, their IMAP service has a regression that prevents OAuth2-authenticated sessions from connecting to the mailbox.

What you can do:

  • Microsoft 365 Business/Enterprise accounts are not affected — OAuth2 works normally for organizational accounts
  • Monitor the issue — This is a server-side problem that only Microsoft can fix. The Microsoft Q&A thread tracks the issue
  • Use the Outlook web app or Microsoft's official apps in the meantime for personal accounts
  • MailVault is ready — Once Microsoft resolves the issue, MailVault's OAuth2 sign-in will work immediately with no changes needed

For technical details: MailVault uses the same OAuth2 implementation as Mozilla Thunderbird, following Microsoft's official IMAP OAuth2 documentation with PKCE and XOAUTH2 authentication.

Proton Mail encrypts your mail end-to-end, so it doesn't expose IMAP directly. Connecting it to MailVault (or any third-party mail client) requires Proton Mail Bridge — a desktop app from Proton that runs locally on your Mac and exposes your encrypted mailbox as standard IMAP/SMTP on 127.0.0.1. Bridge requires a paid Proton Mail plan; it isn't available on Proton's free tier.

Setup steps:

  1. Install Proton Mail Bridge from Proton's website
  2. Sign in to Bridge with your Proton account
  3. Bridge displays per-account IMAP/SMTP credentials — the password shown is a Bridge-generated app password, not your regular Proton account password
  4. In MailVault, choose Proton Mail Bridge in the provider list (or Custom IMAP if it isn't listed) and enter:
    • Server: 127.0.0.1
    • IMAP Port: 1143, Security: STARTTLS
    • SMTP Port: 1025
    • Username: your Proton email address
    • Password: the Bridge-generated password from step 3

Proton Mail Bridge must be running in the background whenever MailVault syncs — if Bridge is closed, MailVault can't reach the mailbox. Mail you've already archived stays fully readable and searchable in MailVault even while Bridge is closed, since MailVault is local-first and reads from its own .eml store rather than live from Bridge.

Bridge secures its local IMAP/SMTP server with a self-signed TLS certificate. MailVault handles this automatically for local (127.0.0.1) connections, so no manual certificate installation is required.

MailVault requires macOS 10.15 (Catalina) or later. It runs natively on both Intel and Apple Silicon Macs. The app is lightweight and runs in the background from your menu bar with minimal resource usage.

Attachments are embedded inside each .eml file as MIME parts — they are not stored as separate files. When you open an email, MailVault's Rust backend parses the MIME structure and extracts attachments on the fly. You can Open, Save As, or Show in Folder any attachment directly from the email viewer. Extracted attachments are temporarily cached for quick re-access.

Archiving downloads the full email from your server (if not already cached) and stores it as a .eml file on disk with the A (Archived) flag in the filename. If the email was already cached locally, MailVault simply renames the file to add the archive flag. Archived emails appear in the Local view mode and are included in backups. The email remains on your server unless you explicitly delete it.

When you choose "Archive & Delete from Server," MailVault first archives the email locally (downloading and saving the .eml file with the archive flag), then sets the IMAP \Deleted flag on the server copy. The email becomes "local-only" — it only exists on your machine. This is the recommended workflow for freeing up server storage while keeping a permanent local backup.

MailVault exports your emails as a ZIP archive containing all .eml files plus a manifest.json that maps emails to accounts by email address (not internal IDs), making backups portable across different installations. You can choose to export all emails or archived only. Importing is idempotent — if an email already exists locally, it won't be duplicated. If a backup contains emails for an account you haven't set up yet, MailVault creates it automatically (you just re-enter the password in Settings).

Google caps how much mail data a single Gmail or Google Workspace account can move per day. The caps apply to the account, not to the app — Apple Mail, your phone and MailVault all draw from the same daily budget.

Access method Download Upload
IMAP (what MailVault uses) 2500 MB / day 500 MB / day
POP 1250 MB / day —
Gmail web client 750 MB / hour, 1250 MB / day 300 MB / hour, 1500 MB / day

Go over a limit and Google temporarily suspends the account: usually about 1 hour, but it can last up to 24 hours. The limits are the same on every Google Workspace edition, and Google can change them without notice — see Google's bandwidth limits documentation for the current numbers.

What this means for a first backup. A mailbox larger than about 2.5 GB cannot be downloaded in one day over IMAP — no client can do it, that is a server-side cap. Expect a large archive to take several days.

What MailVault does. It recognises the limit response, stops the run cleanly instead of retrying into a longer lockout, and tells you the daily limit was reached. Start the backup again once the suspension clears and it continues where it stopped — messages already saved locally are skipped, so nothing is downloaded twice. Everything already on disk stays readable and searchable while you wait.

MailVault always keeps a working copy of your mail in the app's own storage — that is what you read, search and open. An external backup location adds a second, independent copy on a drive you control: an external SSD, a NAS share, or a synced folder.

  • Written alongside the working copy. During a backup run each message is saved to both places, in the same .eml + Maildir layout — so the second copy opens in Apple Mail, Thunderbird or any other client without MailVault.
  • Cold storage, not a mirror. The app never reads it day to day. Emails deleted on the server, or removed inside MailVault, stay in the external copy.
  • Read and write flags survive both directions. The copies are reconciled before a run, so a message you read stays read.
  • Independent of the app. If your Mac dies or you uninstall MailVault, the external folder is still a complete, self-describing mail archive.

Set it in Settings → Backup → “Second copy — external cold storage” and pick any folder. On macOS, MailVault saves a security-scoped bookmark for that folder, so access survives restarts and app updates — a raw path would not. A status badge shows Ready, Needs reauthorization, Unavailable or Access denied, and reauthorizing is one click.

If the drive is unplugged mid-backup, the working copy still completes and MailVault reports how many messages did not reach the external copy. The next run copies them across — nothing is lost, and the failure is never silent.

Yes. By default MailVault keeps its mail store inside the app's own Application Support folder on your startup disk. You can move that store to any folder on any drive — an external SSD, a second internal disk — which matters once an archive grows to tens of gigabytes.

Only mail data moves: the messages, header caches, attachment cache and folder lists. Accounts, settings and logs stay in the app's own folder, so MailVault can always start far enough to tell you a drive is missing and ask for the folder again.

The move is verified before anything is deleted. MailVault copies everything to the new folder, checks that every file arrived at the correct size, switches over, and only then removes the originals. A move interrupted by a disconnect or a crash leaves the current store intact; run it again and it resumes rather than recopying what is already there.

The folder is stamped and recognised. A small marker file identifies the store, so if you later reconnect the drive or move the folder by hand you can point MailVault back at it, and MailVault will refuse a folder that belongs to a different store or that holds no mail.

If the drive is not connected, MailVault reports the mail store as unavailable instead of quietly starting a second archive in the default location and leaving you with two half-complete copies. Reconnect the drive, or select the folder again. You can also switch back to the default location at any time — the mail stays where it is until you move it.

Not the same as a second copy. This changes where the live store lives. An external backup location adds an extra cold copy on top of it. Using both — mail store on a fast external SSD, cold copy on a NAS — is a reasonable setup.
