よくある質問

MailVaultについて知っておきたいことのすべて。

MailVaultは、macOSとLinux向けの無料・オープンソースのデスクトップメールクライアントで、メールを自分のディスク上の保管庫に保存します。IMAPでメールアカウントに接続し、すべてのメッセージを標準的な.emlファイル（RFC 5322）として、コンピューター上にMaildir形式で保存するため、ベンダーロックインのない恒久的なオフラインバックアップになります。

MailVaultはIMAPプロトコルでメールサーバーに接続し、それぞれのメールを標準的な.emlファイルとして、MacまたはLinuxマシン上にMaildir形式でダウンロードします。メール1通がディスク上の1ファイル — 人が読めて、持ち運べて、どのメールクライアントとも互換性があります。メッセージが保管庫に入れば、サーバー側のコピーを削除して容量を空けられます。ローカルのコピーは影響を受けません。

MailVaultは、IMAPに対応しているあらゆるメールプロバイダーで使えます。Gmail、Outlook、Yahoo Mail、iCloud Mail、ProtonMail（Bridge経由）、Fastmail、Zoho Mail、そしてIMAPでアクセスできる自前運用や法人向けのメールも含まれます。

MailVaultは、メールの閲覧、作成、検索、スレッド表示、ローカルへのアーカイブ、手動バックアップといった中心の機能が無料です。Premiumの機能 — 自動バックアップのスケジュール実行、アカウント間のメールボックス移行、自動クリーンアップのルール — は$4/月 または $25/年でご利用いただけます。年額プランには14日間の無料トライアルが付きます。ソースコードはGitHubで公開しています。詳しくは料金の詳細をご覧ください。

保管庫は、MacまたはLinuxマシン上で標準的な.emlファイルをMaildir形式に整理したフォルダです — メール1通が1ファイルで、データベースは不要です。データがコンピューターの外に出ることはなく、クラウドサービスにアップロードされることもありません。.emlは汎用的な標準形式なので、メールはApple Mail、Thunderbird、Outlookなど、ほかのどのメールクライアントでも開けます — MailVaultに縛られることはありません。

ディレクトリ構成:

~/Library/Application Support/com.mailvault.app/
└── maildir/
    └── you@example.com/
        └── INBOX/
            ├── headers.json          ← cached list for fast loading
            └── cur/
                ├── 1234567890.eml    ← auto-cached email
                └── 1234567891_AS.eml ← archived + seen email

.eml (RFC 5322)は、メールのメッセージのためのインターネット標準の形式です。メールは — ヘッダーも、本文も、添付ファイルも — 1つの、それ自体で完結したテキストファイルに収まります。独自形式のデータベースと違い、.emlファイルはどのメールクライアント（Apple Mail、Thunderbird、Outlook）でも開けますし、どのテキストエディタでも読めます。

Maildirは、メールサーバーが何十年も使ってきた、実績のあるメール保存のディレクトリ構造です。メール1通が1ファイルなので、壊れうる単一のデータベースがありません — 1つのファイルが傷んでも、アーカイブの残りは影響を受けません。.emlとMaildirを合わせることで、メールは将来にわたって読め、持ち運べ、どの単一のアプリケーションにも縛られません。

ファイル名のフラグ:

MailVaultは、状態を追うために.emlのファイル名にフラグの文字を付け足します。A = Archived、S = Seen、R = Replied、F = Flaggedです。たとえば1234567890_AS.emlは、そのメールがアーカイブ済みで既読であることを表します。

はい。同期が済んだメールはローカルに保存されるので、インターネット接続がなくてもすべて閲覧、検索、参照できます。インターネットが必要なのは、新しいメールを同期するときと、メールを送信するときだけです。

MailVaultはプライバシーを最優先に設計されています。メールの認証情報はmacOSのキーチェーンまたはLinuxのSecret Serviceに保存され、平文のファイルに書き出されることはありません。データはすべてお使いのマシンに残り、クラウド同期も、トラッキングも、分析も、データの二次利用もありません。オープンソースなので、コードはご自身で確認できます。

先にアーカイブしたものは保管庫に残り、その後サーバーで何が起きても影響を受けません — それがこの製品の目的そのものです。アーカイブしなかったものは、サーバー側のコピーと一緒に失われます。そのためMailVaultは、削除する前に各メッセージの状態を行ごとに表示します。サーバー上にあるのか、保管庫にあるのか、その両方か。安全な手順はArchive & Deleteです。各メッセージを保管庫にコピーし、そこに確かにあることを確かめてから、サーバーから削除します。

2024年後半以降、個人のOutlook.com、Hotmail、Live.comのアカウントに影響する既知のMicrosoftのサーバー側の問題があります。Microsoftのアカウントでサインインしたあと、IMAPの接続が「User is authenticated but not connected.」で失敗します。これはMailVaultだけでなく、OAuth2でIMAPを使うすべての第三者のメールクライアントに影響します。

Microsoftは個人アカウントにOAuth2を必須としています。しかし同社のIMAPサービスには、OAuth2で認証したセッションがメールボックスに接続できないリグレッションがあります。

できること:

  • Microsoft 365のBusiness／Enterpriseのアカウントは影響を受けません — 組織のアカウントではOAuth2は通常どおり動きます
  • 問題の推移を見守る — これはMicrosoftにしか直せないサーバー側の問題です。Microsoft Q&A のスレッドで追跡されています
  • 個人のアカウントでは当面、Outlookのウェブ版やMicrosoftの公式アプリをお使いください
  • MailVaultの準備はできています — Microsoftが問題を解決すれば、MailVaultのOAuth2のサインインは何も変えずにすぐ動きます

技術的な詳細: MailVaultはMozilla Thunderbirdと同じOAuth2の実装を使い、PKCEとXOAUTH2の認証について、MicrosoftのIMAP OAuth2の公式ドキュメントに従っています。

Proton Mailはメールを端から端まで暗号化するため、IMAPを直接には公開していません。MailVault（やほかの第三者のメールクライアント）につなぐにはProton Mail Bridgeが必要です — Protonが提供するデスクトップアプリで、自分のコンピューター上で動き、暗号化されたメールボックスを127.0.0.1の標準的なIMAPとSMTPとして見せます。Bridgeには有料のProton Mailのプランが必要で、Protonの無料の枠では使えません。

設定の手順:

  1. ProtonのウェブサイトからProton Mail Bridgeをインストールします
  2. Protonアカウントで Bridge にサインインします
  3. BridgeはアカウントごとのIMAP／SMTPの認証情報を表示します — 表示されるパスワードはBridgeが生成したアプリパスワードで、いつものProtonのアカウントのパスワードではありません
  4. MailVaultで、プロバイダーの一覧から Proton Mail Bridge を選びます（一覧にない場合は Custom IMAP ）。そして次を入力します:
    • サーバー: 127.0.0.1
    • IMAPのポート: 1143、セキュリティ: STARTTLS
    • SMTPポート: 1025
    • ユーザー名: Protonのメールアドレス
    • パスワード: 手順3でBridgeが生成したパスワード

MailVaultが同期するあいだ、Proton Mail Bridgeは背後で動いている必要があります — Bridgeが閉じていると、MailVaultはメールボックスに届きません。すでにアーカイブしたメールは、Bridgeが閉じていてもMailVaultの中でそのまま読め、検索できます。MailVaultはローカルを主とし、Bridgeから直接ではなく自身の.emlの保存領域から読むからです。

Bridgeは、自身のローカルのIMAPとSMTPのサーバーを自己署名のTLS証明書で保護します。MailVaultはローカル（127.0.0.1）の接続についてこれを自動で扱うので、証明書を手でインストールする必要はありません。

はい。設定 → アカウントを開き、アカウントを選んで、Send Mail Asを入力します。空のままにすると、ログインに使うアドレスから送信します。Fastmailや、サインインに使うアドレスと人に伝えるアドレスが違う提供元では、よくあることです。

変わるのは、送信するメールのFromのアドレスだけです。ユーザー名とパスワードはそのままで、MailVaultは設定したアカウントとしてIMAPとSMTPにサインインし続けます。また、Reply-Toのヘッダーは追加されません — 返信は、送信に使ったアドレスへ届きます。

アドレスの見つけ方と確認方法:

  • 候補の表示 — MailVaultは、自分のメールの中ですでに見かけたアドレスを提示します。以前そのアドレスで送ったもの、そして自分宛てのメールが届いているアドレスです。
  • 検証 — そのアドレスからテストのメッセージを1通、既定では自分のメールボックス宛てに送るので、頼りにする前に提供元が受け付けるかを確かめられます。
  • 拒否された場合 — そのアドレスは、そのログインでの送信を提供元が認めているエイリアスか差出人である必要があります。Fastmailはアカウント上のどのエイリアスでも受け付けます。GmailではGmailの設定の「Send mail as」にアドレスを追加する必要があり、Microsoft 365では管理者からSend Asの権限をもらう必要があります。

エイリアスはMailVaultではなく、メールプロバイダー側で設定します — MailVaultは、プロバイダーがすでに許可しているアドレスとして送信するだけです。

MailVaultにはmacOS 11（Big Sur）以降が必要で、IntelとApple Siliconの両方でネイティブに動作します。Linuxでは、Ubuntu 22.04以降 / Debian 12以降向けに.deb、AppImage、Snap、Flatpakを提供しています。メニューバーに常駐し、ウィンドウを閉じたままでも同期を続けます。

添付ファイルは、それぞれの.emlファイルの中にMIMEのパートとして埋め込まれています — 別々のファイルとして保存されるのではありません。メールを開くと、MailVaultのRustのバックエンドがMIMEの構造を解析し、その場で添付ファイルを取り出します。メールの表示から直接、どの添付ファイルでもOpen、Save As、Show in Folderができます。取り出した添付ファイルは、すぐに開き直せるよう一時的にキャッシュされます。

アーカイブすると、（まだキャッシュされていなければ）サーバーからメールの全体をダウンロードし、ファイル名にA（Archived）のフラグを付けた.emlファイルとしてディスクに保存します。すでにローカルにキャッシュされていた場合、MailVaultはファイル名を変えてアーカイブのフラグを足すだけです。アーカイブしたメールはVaultの表示に現れ、バックアップにも含まれます。サーバー側のコピーは、自分で削除するまで手つかずのままです。

Archive & Deleteは3つの手順を順に行います。メッセージを.emlファイルとして保管庫にコピーし、そのコピーが本当にあることを確かめ、そのあとで初めてサーバーから削除します。確認に通らなかったものはサーバーに残ります — コピーに失敗しても、元を失うことはありません。そのあと行には唯一のコピーと表示されます。そのメッセージが残っている場所は保管庫だけだということで、バックアップ用のドライブをつないでおく合図でもあります。

MailVaultは、すべての.emlファイルと、内部のIDではなくメールアドレスでメールをアカウントに対応付けるmanifest.jsonを含んだZIPアーカイブとして、メールを書き出します。これにより、バックアップは別の環境へ持ち運べます。書き出す対象はすべてのメールかアーカイブ済みのみかを選べます。取り込みは冪等です — 同じメールがすでにローカルにあれば、重複しません。まだ設定していないアカウントのメールがバックアップに含まれていれば、MailVaultが自動でそのアカウントを作ります（設定でパスワードを入れ直すだけです）。

Googleは、1つのGmailまたはGoogle Workspaceのアカウントが1日に転送できるメールデータの量に上限を設けています。上限はアプリではなくアカウントに対するものなので、Apple Mail、スマートフォン、MailVaultはすべて同じ1日分の枠を使います。

アクセス方法 ダウンロードの上限 アップロードの上限
IMAP （MailVaultが使用） 2500 MB / 日 500 MB / 日
POP 1250 MB / 日 —
Gmailのウェブクライアント 750 MB / 時、1250 MB / 日 300 MB / 時、1500 MB / 日

上限を超えるとGoogleはアカウントを一時的に停止します。通常は1時間ほどですが、24時間続くこともあります。上限はどのGoogle Workspaceのエディションでも同じで、Googleは予告なく変更できます — 現在の数値はGoogleの帯域制限のドキュメントをご覧ください。

最初のバックアップにとって、これが何を意味するか。およそ2.5 GBを超えるメールボックスは、IMAPで1日のうちにダウンロードしきれません — どのクライアントでも無理で、これはサーバー側の上限です。大きなアーカイブには数日かかると見込んでください。

MailVaultの振る舞い。上限に達した応答を認識し、より長い締め出しを招く再試行はせずに実行をきれいに停止して、1日の上限に達したことをお知らせします。停止が解けてからバックアップを始め直せば、止まったところから続きます — すでにローカルに保存されたメッセージは飛ばされるので、二度ダウンロードされることはありません。待っている間も、ディスクにあるものはすべて読めますし、検索もできます。

MailVaultは常に、アプリ自身の保存領域にメールの作業用のコピーを保ちます — 読み、検索し、開いているのはこれです。外部バックアップ先は、自分が管理するドライブ上に2つ目の独立したコピーを加えます。外付けSSD、NASの共有、同期されたフォルダなどです。

  • 作業用のコピーと並べて書き込まれます。バックアップの実行中、それぞれのメッセージは同じ.emlとMaildirの構成で両方の場所に保存されます — そのため2つ目のコピーは、MailVaultがなくてもApple MailやThunderbirdなど、ほかのメールクライアントで開けます。
  • ミラーではなく、コールドストレージです。アプリが日常的にそこを読むことはありません。サーバー上で削除したメールも、MailVaultの中で消したメールも、外部のコピーには残ります。
  • 既読と未読のフラグは双方向で保たれます。実行の前に両方のコピーが突き合わされるので、読んだメッセージは読んだままです。
  • アプリから独立しています。そのコンピューターが壊れても、MailVaultをアンインストールしても、外部のフォルダはそれ自体で完結した、内容を語れるメールのアーカイブのままです。

設定 → バックアップ → 「2つ目のコピー — 外部のコールドストレージ」で設定し、任意のフォルダを選びます。macOSではMailVaultがそのフォルダのセキュリティスコープ付きブックマークを保存するため、再起動やアプリの更新をまたいでもアクセスが続きます — 生のパスではそうはいきません。状態のバッジには準備完了、再認証が必要、利用できません、アクセスが拒否されましたのいずれかが表示され、再認証はクリック1回です。

バックアップの途中でドライブが取り外された場合でも、作業用コピーの処理は最後まで完了し、MailVaultは外部のコピーに届かなかったメッセージの数を報告します。次回の実行でそれらがコピーされるので、失われるものはなく、失敗が黙って見過ごされることもありません。

はい。既定では、MailVaultは起動ディスク上のアプリ専用のApplication Supportフォルダの中にメールストアを置きます。このストアは、外付けSSDや2台目の内蔵ディスクなど、どのドライブのどのフォルダにも移動できます。アーカイブが数十ギガバイトに育つと、これが効いてきます。

移動するのはメールのデータだけです: メッセージ、ヘッダーのキャッシュ、添付ファイルのキャッシュ、フォルダの一覧です。アカウント、設定、ログはアプリ自身のフォルダに残るので、ドライブが見つからないことを伝えてフォルダを尋ね直せるところまでは、MailVaultは必ず起動できます。

移動は、何かを削除する前に検証されます。MailVaultはすべてを新しいフォルダにコピーし、どのファイルも正しいサイズで届いたことを確かめ、切り替えてから、そのあとで初めて元のファイルを削除します。切断やクラッシュで移動が中断されても、現在の保存領域はそのまま残ります。もう一度実行すれば、すでにあるものをコピーし直すのではなく、続きから再開します。

フォルダには印が付き、認識されます。小さな目印のファイルが保存領域を識別するので、あとでドライブをつなぎ直したり、フォルダを手で移動したりしても、MailVaultをそこへ向け直せます。また、別の保存領域に属するフォルダや、メールの入っていないフォルダは、MailVaultが受け付けません。

ドライブがつながっていない場合、MailVaultはメールの保存領域が利用できないと伝えます。黙って既定の場所に2つ目のアーカイブを作り始め、中途半端なコピーを2つ抱えさせるようなことはしません。ドライブをつなぎ直すか、フォルダをもう一度選んでください。既定の場所にはいつでも戻せます — 移動するまで、メールはその場所に留まります。

2つ目のコピーとは別のものです。これは実際に使う保存領域の場所を変えるものです。外部バックアップ先は、その上にさらに冷たいコピーを1つ足します。両方を使うこと — メールの保存領域は高速な外付けSSDに、冷たいコピーはNASに — も、理にかなった構成です。

そのマシンにスペル辞書がないからです。macOSとWindowsはシステムに辞書が同梱されていますが、Linuxでは辞書はディストリビューションから提供され、最小構成のデスクトップにはないことがよくあります。MailVaultはWebKitGTKを通じてスペルチェックを行い、WebKitGTKはenchantとhunspellを使って単語を調べます。そのため、hunspellの辞書が入っていないと下線を引けません。

どちらの状態にいるかは、メッセージのツールバーのボタンが教えてくれます。辞書があれば、下線の表示をオンとオフに切り替え、その設定をMailVaultが覚えます。辞書がなければ、スイッチのふりをする代わりに、この説明そのものを開きます。

お使いの言語の辞書をインストールしてください:

Debian、Ubuntu、Mint
sudo apt install hunspell-en-us
Fedora
sudo dnf install hunspell-en
Arch、Manjaro
sudo pacman -S hunspell-en_us
openSUSE
sudo zypper install myspell-en_US

言語のコードはご自分のものに置き換えてください — hunspell-de-de、hunspell-frなどです。複数を入れてもかまいません。MailVaultはシステムの言語に合うものを使って確認し、合うものがなければすべてを使って確認します。そのあとMailVaultを再起動してください — スペルチェックはアプリの起動時に設定されます。

snapのビルドは特別な場合です。厳密に閉じ込められたsnapはホストに入れた辞書を見られないため、自前のコピーを持っています。snapが辞書なしと伝えてきたら、代わりに.debパッケージを入れてください — こちらはシステムにすでにある辞書を使います。
