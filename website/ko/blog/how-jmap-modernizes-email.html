JMAP은 이메일을 대체하지 않고 어떻게 현대화하는가

4분 분량

메일함 연결부터 살펴보기

받은편지함은 겉으로는 현대적으로 보여도 동기화를 유지하기 위해 많은 작업을 수행합니다. 메시지를 찾고, 내용을 가져오고, 변경 사항을 기록하고, 오프라인 동안의 변경을 반영해야 합니다. 관련 글에서는 이메일이 여전히 복잡한 이유를 설명합니다. JMAP은 이 문제의 중요한 부분인, 앱과 메일을 보관하는 서버 사이의 통신 방식을 다룹니다.

IETF는 2019년 7월에 JMAP 핵심 명세를, 2019년 8월에 JMAP for Mail을 발표했습니다. 범용 동기화 프로토콜에 메일함, 메시지, 스레드, 전송 요청 같은 이메일 전용 객체를 결합합니다.

네트워크 왕복 줄이기

JMAP은 HTTPS를 통해 구조화된 JSON을 교환합니다. 클라이언트는 여러 메서드 호출을 하나의 요청으로 묶고, 뒤의 호출에서 앞선 호출의 결과를 참조할 수 있습니다. 예를 들어 조건에 맞는 메시지 ID를 조회하고 해당 메시지의 필요한 속성을 요청할 때, 두 작업 사이에 클라이언트와 서버가 별도로 왕복 통신할 필요가 없습니다.

지연 시간이 길 때 이 점이 중요합니다. 데이터를 처리하는 것보다 네트워크 응답을 기다리는 데 더 많은 시간이 걸릴 수 있기 때문입니다. 일괄 처리는 이러한 대기를 줄입니다. 실제 속도는 서버, 연결, 메일함, 클라이언트에도 좌우됩니다. 프로토콜 선택만으로 성능을 평가할 수는 없습니다.

처음부터 다시 시작하지 않고 변경 사항 묻기

JMAP은 내부 의미를 해석할 필요가 없는 상태 토큰으로 컬렉션을 추적합니다. 앱은 토큰을 저장했다가 나중에 그 상태 이후 어떤 객체가 생성, 수정, 삭제되었는지 물을 수 있습니다. 덕분에 클라이언트는 모든 데이터를 반복해서 다운로드하는 대신 정해진 방식으로 최신 상태를 반영할 수 있습니다.

복구 방법도 있습니다. 서버가 오래된 상태로부터의 변경 사항을 계산하지 못하면 cannotCalculateChanges를 반환할 수 있습니다. 그러면 클라이언트는 해당 화면의 데이터를 다시 구성해야 합니다. JMAP은 이 상황을 명확히 정의하지만, 장기간의 미접속이나 동기화 중단을 처리할 필요까지 없애지는 않습니다.

푸시 알림과 공통 메일 모델

푸시 알림은 상태가 변경되었음을 앱에 알려 차이를 가져오도록 유도할 수 있습니다. 알림은 동기화를 시작하라는 신호이며, 동기화를 완전히 대체하지는 않습니다. 알림이나 네트워크 접근이 끊기면 앱은 다시 연결하고 복구해야 합니다.

JMAP for Mail은 검색, 스레드, 메시지 전송도 같은 API 체계에서 정의합니다. 클라이언트가 JMAP으로 발신 메일을 제출하고, 제공업체는 계속 SMTP를 사용해 다른 메일 서버로 전달할 수 있습니다. 현대적인 접근 방식과 기존 인터넷 전송 방식은 공존할 수 있습니다.

JMAP이 시스템의 다른 부분에 맡기는 것

앱과 제공업체가 모두 JMAP을 지원해야 합니다. 클라이언트만으로 임의의 메일함에 JMAP을 활성화할 수는 없습니다. 또한 스팸 차단, 종단 간 암호화 추가, 백업 보존, 모든 메시지의 오프라인 이용이 자동으로 이루어지지는 않습니다. 이는 다른 시스템과 제품 설계에 달려 있습니다.

MailVault에서 효율적인 메일함 접근과 유용한 로컬 기록 보존은 서로 보완하는 목표입니다. JMAP은 호환 서버와의 통신을 개선하지만, 로컬 저장, 검색, 복구에는 각각의 설계와 구현이 필요합니다. 이러한 설계 선택에 관해서는 JMAP과 현대적인 이메일 앱에 대한 Graphic Meat의 관점을 읽어 보세요.
