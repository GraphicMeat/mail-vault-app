자주 묻는 질문

MailVault에 대해 알아야 할 모든 것.

MailVault는 메일을 사용자 자신의 디스크에 있는 볼트에 저장하는 macOS와 Linux용 무료 오픈소스 데스크톱 메일 클라이언트입니다. IMAP으로 이메일 계정에 연결해 모든 메시지를 표준 .eml 파일(RFC 5322)로 컴퓨터의 Maildir 형식 안에 저장하므로, 공급업체 종속 없는 영구 오프라인 백업이 생깁니다.

MailVault는 IMAP 프로토콜로 메일 서버에 연결해 각 메일을 표준 .eml 파일로 내려받아 Mac이나 Linux 컴퓨터의 Maildir 형식으로 저장합니다. 메일 하나가 디스크의 파일 하나입니다 — 사람이 읽을 수 있고, 이식 가능하며, 어떤 메일 클라이언트와도 호환됩니다. 메시지가 볼트에 들어오고 나면 서버 사본을 지워 공간을 비울 수 있고, 로컬 사본은 그대로입니다.

MailVault는 IMAP을 지원하는 모든 이메일 제공업체와 함께 작동합니다. Gmail, Outlook, Yahoo Mail, iCloud Mail, ProtonMail(Bridge 사용), Fastmail, Zoho Mail은 물론, IMAP 접속을 제공하는 자체 호스팅 서버나 업무용 메일 서비스도 포함됩니다.

MailVault는 메일 읽기, 작성, 검색, 스레딩, 로컬 보관, 수동 백업을 비롯한 핵심 기능이 무료입니다. 예약 자동 백업, 계정 간 메일함 이전, 자동 정리 규칙 같은 Premium 기능은 $4/월 또는 $25/년에 쓸 수 있으며, 연간 요금제에는 14일 무료 체험이 있습니다. 소스 코드는 GitHub에 있습니다. 자세한 것은 전체 가격을 보십시오.

볼트는 Mac이나 Linux 컴퓨터에서 표준 .eml 파일을 Maildir 형식으로 정리해 둔 폴더입니다 — 메일 하나에 파일 하나이며 데이터베이스는 필요 없습니다. 데이터는 컴퓨터를 벗어나지 않으며 어떤 클라우드 서비스에도 올라가지 않습니다. .eml은 보편적인 표준이므로 메일을 Apple Mail, Thunderbird, Outlook을 비롯한 어떤 메일 클라이언트로도 열 수 있습니다 — MailVault에 묶이는 일은 없습니다.

디렉터리 구조:

~/Library/Application Support/com.mailvault.app/
└── maildir/
    └── you@example.com/
        └── INBOX/
            ├── headers.json          ← cached list for fast loading
            └── cur/
                ├── 1234567890.eml    ← auto-cached email
                └── 1234567891_AS.eml ← archived + seen email

.eml(RFC 5322)은 메일 메시지의 인터넷 표준 형식입니다. 모든 메일은 — 헤더, 본문, 첨부파일까지 — 그 자체로 완결된 텍스트 파일 하나에 저장됩니다. 독점 데이터베이스와 달리 .eml 파일은 어떤 메일 클라이언트(Apple Mail, Thunderbird, Outlook)로도 열 수 있고 아무 텍스트 편집기로도 읽을 수 있습니다.

Maildir은 메일 서버가 수십 년째 써 온, 검증된 메일 저장용 디렉터리 구조입니다. 메일 하나가 파일 하나이므로 손상될 수 있는 단일 데이터베이스가 없습니다 — 파일 하나가 망가져도 나머지 보관본은 영향을 받지 않습니다. .eml과 Maildir을 함께 쓰면 메일이 앞으로도 열리고, 이식 가능하며, 어떤 앱 하나에도 묶이지 않습니다.

파일 이름 플래그:

MailVault는 상태를 기록하려고 .eml 파일 이름에 플래그 문자를 덧붙입니다. A = Archived(보관됨), S = Seen(읽음), R = Replied(답장함), F = Flagged(깃발). 예를 들어 1234567890_AS.eml은 그 메일이 보관되었고 읽혔다는 뜻입니다.

볼 수 있습니다. 메일이 한 번 동기화되면 로컬에 저장되므로 인터넷 연결 없이도 전부 읽고, 검색하고, 살펴볼 수 있습니다. 인터넷은 새 메일을 동기화하거나 메일을 보낼 때만 필요합니다.

MailVault는 프라이버시를 우선해 설계되었습니다. 메일 계정의 인증 정보는 macOS 키체인이나 Linux Secret Service에 저장되며, 평문 파일에는 절대 저장되지 않습니다. 모든 데이터는 사용자의 컴퓨터에 남습니다 — 클라우드 동기화도, 추적도, 분석도, 데이터 수집도 없습니다. 앱은 오픈소스이므로 코드를 직접 확인할 수 있습니다.

그렇습니다. MailVault가 여는 모든 메시지는 추적 픽셀 검사를 거칩니다 — 광고 메일이 언제, 몇 번, 어느 IP 주소에서, 어떤 클라이언트로 열렸는지 알리는 데 쓰는 숨은 1x1 이미지 말입니다. 추적 픽셀이 든 메시지에는 제목 옆에 작은 눈 표시가 나타나고, 그것을 누르면 추적 회사의 이름과 그 픽셀이 호출했을 정확한 URL이 나옵니다. 탐지는 누구에게나 무료입니다. MailVault Premium은 메시지가 그려지기 전에 그 신호기를 HTML에서 걷어내기까지 하므로, 요청은 아예 일어나지 않고 보낸 사람은 아무것도 알지 못합니다. 알려진 추적 엔드포인트 500개 가까이가 앱과 함께 배포되며, 이 목록은 앱에 담겨 릴리스마다 갱신될 뿐 실행 중에 서버에서 받아 오지 않습니다. 차단 전과 후가 어떻게 다른지 보십시오.

먼저 보관해 둔 것은 서버가 그 뒤에 무엇을 하든 손대지 않은 채 볼트에 남습니다 — 그것이 이 제품의 존재 이유 전부입니다. 보관하지 않은 것은 서버 사본과 함께 사라지므로, MailVault는 지우기 전에 메시지마다 그 상태를 각자의 행에 보여 줍니다. 서버에 있는지, 볼트에 있는지, 둘 다인지 말입니다. 안전한 길은 Archive & Delete입니다. 각 메시지를 볼트로 복사하고 거기 있는지 확인한 뒤에야 서버에서 지웁니다.

그렇습니다. MailVault는 Gmail, Outlook을 비롯해 IMAP을 지원하는 어떤 메일 서비스와도 함께 작동합니다. Gmail은 OAuth2로 Google 계정에 바로 로그인하면 됩니다 — IMAP 설정을 손으로 넣을 필요가 없습니다. Microsoft 365 Business와 Enterprise 계정도 OAuth2로 Microsoft 계정에 바로 로그인할 수 있고, 2단계 인증과도 매끄럽게 맞물립니다. 개인용 Outlook.com 계정은 현재 알려진 Microsoft 서버 문제의 영향을 받고 있습니다.

2024년 말부터 개인용 Outlook.com, Hotmail, Live.com 계정에 영향을 주는 알려진 Microsoft 서버 쪽 문제가 있습니다. Microsoft 계정으로 로그인한 뒤 IMAP 연결이 "User is authenticated but not connected."로 실패합니다. 이는 MailVault만이 아니라 OAuth2로 IMAP을 쓰는 모든 제3자 메일 클라이언트에 해당합니다.

Microsoft는 개인 계정에 OAuth2를 요구합니다. 그런데 Microsoft의 IMAP 서비스에는 OAuth2로 인증된 세션이 메일함에 연결되지 못하게 만드는 회귀 버그가 있습니다.

할 수 있는 일:

  • Microsoft 365 Business/Enterprise 계정은 영향을 받지 않습니다 — 조직 계정에서는 OAuth2가 정상 작동합니다
  • 진행 상황 지켜보기 — Microsoft만 고칠 수 있는 서버 쪽 문제입니다. Microsoft Q&A 스레드에서 이 문제를 추적합니다
  • 그동안 개인 계정에는 Outlook 웹 앱이나 Microsoft의 공식 앱을 쓰십시오
  • MailVault는 준비되어 있습니다 — Microsoft가 문제를 해결하면 MailVault의 OAuth2 로그인은 아무것도 바꾸지 않아도 곧바로 작동합니다

기술적인 내용은 이렇습니다. MailVault는 Mozilla Thunderbird와 같은 OAuth2 구현을 쓰며, PKCE와 XOAUTH2 인증을 사용하는 Microsoft의 공식 IMAP OAuth2 문서를 따릅니다.

Proton Mail은 메일을 종단 간 암호화하므로 IMAP을 직접 열어 두지 않습니다. MailVault(또는 다른 제3자 메일 클라이언트)에 연결하려면 Proton Mail Bridge가 필요합니다 — 사용자 컴퓨터에서 돌면서 암호화된 메일함을 127.0.0.1의 표준 IMAP/SMTP로 노출해 주는 Proton의 데스크톱 앱입니다. Bridge는 유료 Proton Mail 요금제가 있어야 하며 Proton 무료 등급에서는 쓸 수 없습니다.

설정 순서:

  1. Proton 웹사이트에서 Proton Mail Bridge를 설치하십시오
  2. Proton 계정으로 Bridge에 로그인합니다
  3. Bridge가 계정별 IMAP/SMTP 인증 정보를 보여 줍니다 — 거기 표시되는 비밀번호는 Bridge가 만들어 준 앱 비밀번호이며, 평소 쓰는 Proton 계정 비밀번호가 아닙니다
  4. MailVault에서 제공업체 목록의 Proton Mail Bridge 를 선택하고(목록에 없으면 Custom IMAP 을 선택), 다음을 입력합니다:
    • 서버: 127.0.0.1
    • IMAP 포트: 1143, 보안: STARTTLS
    • SMTP 포트: 1025
    • 사용자 이름: Proton 이메일 주소
    • 비밀번호: 3단계에서 Bridge가 생성한 비밀번호

MailVault가 동기화하는 동안에는 Proton Mail Bridge가 배경에서 돌고 있어야 합니다 — Bridge가 닫혀 있으면 MailVault는 메일함에 닿을 수 없습니다. 이미 보관해 둔 메일은 Bridge가 닫혀 있어도 MailVault에서 그대로 읽고 검색할 수 있습니다. MailVault는 로컬 우선이라 Bridge에서 실시간으로 받아 오는 대신 자기 .eml 저장소에서 읽기 때문입니다.

Bridge는 자체 서명 TLS 인증서로 로컬 IMAP/SMTP 서버를 보호합니다. MailVault는 로컬(127.0.0.1) 연결에 대해 이를 자동으로 처리하므로 인증서를 직접 설치할 필요가 없습니다.

가능합니다. 설정 → 계정을 열어 계정을 고른 다음 Send Mail As를 채우십시오. 비워 두면 로그인 주소로 보냅니다. Fastmail을 비롯해, 로그인하는 주소와 남에게 알려 주는 주소가 다른 제공업체에서 흔한 설정입니다.

바뀌는 것은 보내는 메일의 From 주소뿐입니다. 사용자 이름과 비밀번호는 그대로이고, MailVault는 여전히 설정해 둔 계정으로 IMAP과 SMTP에 로그인하며, Reply-To 헤더는 추가되지 않습니다 — 답장은 보낼 때 쓴 주소로 갑니다.

주소를 찾고 확인하는 방법:

  • 추천 — MailVault는 이미 사용자 메일에서 본 주소를 제안합니다. 전에 그 주소로 보낸 적이 있는 것, 그리고 사용자에게 온 메일이 도착하는 주소입니다.
  • 확인 — 그 주소로 시험 메일 한 통을 보냅니다. 기본값은 자기 메일함이며, 믿고 쓰기 전에 제공업체가 그 주소를 받아 주는지 확인할 수 있습니다.
  • 거부당한다면 — 그 주소는 제공업체가 그 로그인으로 보낼 수 있게 허용한 별칭이나 신원이어야 합니다. Fastmail은 계정의 어떤 별칭이든 받아 줍니다. Gmail은 Gmail 설정의 "Send mail as"에 주소를 추가해야 하고, Microsoft 365는 관리자가 준 Send As 권한이 필요합니다.

별칭은 MailVault가 아니라 이메일 제공업체 쪽에서 설정합니다 — MailVault는 제공업체가 이미 승인한 주소로 보낼 뿐입니다.

MailVault는 macOS 11(Big Sur) 이상이 필요하며, Intel과 Apple Silicon 모두에서 네이티브로 실행됩니다. Linux에서는 Ubuntu 22.04 이상 / Debian 12 이상을 대상으로 .deb, AppImage, Snap, Flatpak으로 제공됩니다. 메뉴 막대에 상주하므로 창을 닫아 두어도 동기화가 계속됩니다.

첨부파일은 각 .eml 파일 안에 MIME 파트로 들어 있습니다 — 별도 파일로 저장되지 않습니다. 메일을 열면 MailVault의 Rust 백엔드가 MIME 구조를 해석해 그때그때 첨부파일을 꺼냅니다. 메일 뷰어에서 바로 어떤 첨부파일이든 Open, Save As, Show in Folder할 수 있습니다. 꺼낸 첨부파일은 다시 열 때 빠르도록 잠시 캐시됩니다.

보관은 (아직 캐시되지 않았다면) 서버에서 메일 전체를 내려받아, 파일 이름에 A(Archived) 플래그를 붙인 .eml 파일로 디스크에 저장합니다. 이미 로컬에 캐시되어 있었다면 MailVault는 파일 이름만 바꿔 보관 플래그를 더합니다. 보관한 메일은 볼트 보기에 나타나고 백업에도 포함됩니다. 서버 사본은 사용자가 직접 지울 때까지 그대로입니다.

Archive & Delete는 세 단계를 차례로 밟습니다. 메시지를 .eml 파일로 볼트에 복사하고, 그 사본이 정말 거기 있는지 확인한 다음, 그때에야 서버에서 지웁니다. 확인을 통과하지 못한 것은 서버에 남습니다 — 복사에 실패해도 원본을 잃는 일은 없습니다. 그 뒤 해당 행에는 사본은 이곳뿐이라고 표시됩니다. 그 메시지가 아직 존재하는 곳은 볼트 하나라는 뜻이며, 백업 드라이브를 연결해 두라는 신호이기도 합니다.

MailVault는 메일을 모든 .eml 파일과 manifest.json이 든 ZIP 아카이브로 내보냅니다. 이 manifest는 내부 ID가 아니라 이메일 주소로 메일과 계정을 이어 주므로, 백업을 다른 설치 환경으로도 그대로 옮길 수 있습니다. 모든 메일을 내보낼지 보관된 것만 내보낼지 고를 수 있습니다. 가져오기는 몇 번을 해도 결과가 같습니다 — 로컬에 이미 있는 메일은 중복되지 않습니다. 백업에 아직 설정하지 않은 계정의 메일이 들어 있으면 MailVault가 그 계정을 자동으로 만들어 줍니다(설정에서 비밀번호만 다시 넣으면 됩니다).

Google은 Gmail 또는 Google Workspace 계정 하나가 하루에 옮길 수 있는 메일 데이터 양을 제한합니다. 이 제한은 앱이 아니라 계정에 적용됩니다 — Apple Mail, 휴대폰, MailVault가 모두 같은 하루치 한도를 나눠 씁니다.

접속 방식 다운로드 한도 업로드 한도
IMAP (MailVault가 사용하는 방식) 2500 MB / 일 500 MB / 일
POP 1250 MB / 일 —
Gmail 웹 클라이언트 750 MB / 시간, 1250 MB / 일 300 MB / 시간, 1500 MB / 일

한도를 넘기면 Google은 계정을 일시적으로 정지시킵니다. 보통 1시간 정도지만 최대 24시간까지 갈 수 있습니다. 이 한도는 모든 Google Workspace 등급에서 같고, Google이 예고 없이 바꿀 수 있습니다 — 현재 수치는 Google의 대역폭 한도 문서를 보십시오.

첫 백업에서 이것이 뜻하는 것. 약 2.5 GB가 넘는 메일함은 IMAP으로 하루 만에 내려받을 수 없습니다 — 어떤 클라이언트도 할 수 없는 서버 쪽 상한입니다. 큰 보관본은 며칠이 걸린다고 보십시오.

MailVault가 하는 일. 한도 응답을 알아보고, 더 긴 정지로 이어질 재시도 대신 실행을 깔끔하게 멈춘 다음, 일일 한도에 닿았다고 알려 줍니다. 정지가 풀린 뒤 백업을 다시 시작하면 멈춘 자리에서 이어집니다 — 로컬에 이미 저장된 메시지는 건너뛰므로 두 번 내려받지 않습니다. 기다리는 동안에도 디스크에 이미 있는 것은 그대로 읽고 검색할 수 있습니다.

MailVault는 앱 자체 저장소에 언제나 메일의 작업용 사본을 둡니다 — 읽고, 검색하고, 여는 대상이 바로 그것입니다. 외부 백업 위치는 사용자가 관리하는 드라이브에 두 번째 독립 사본을 더합니다. 외장 SSD, NAS 공유 폴더, 동기화되는 폴더 같은 곳입니다.

  • 작업용 사본과 나란히 기록됩니다. 백업이 도는 동안 메시지는 같은 .eml + Maildir 배치로 두 곳 모두에 저장됩니다 — 그래서 두 번째 사본은 MailVault 없이도 Apple Mail이나 Thunderbird, 그 밖의 어떤 클라이언트로도 열립니다.
  • 거울이 아니라 보관용입니다. 앱은 평소에 그것을 읽지 않습니다. 서버에서 지워진 메일이나 MailVault 안에서 없앤 메일도 외부 사본에는 남습니다.
  • 읽음과 쓰기 플래그가 양쪽 방향으로 유지됩니다. 실행 전에 두 사본을 맞추므로, 읽은 메시지는 읽은 상태로 남습니다.
  • 앱과 무관합니다. 그 컴퓨터가 죽거나 MailVault를 지워도 외부 폴더는 그 자체로 완결된 메일 보관본으로 남습니다.

설정 → 백업 → “두 번째 사본 — 외부 보관 저장소”에서 지정하고 원하는 폴더를 고르십시오. macOS에서는 MailVault가 그 폴더에 대한 보안 범위 북마크를 저장하므로 재시작이나 앱 업데이트 뒤에도 접근이 유지됩니다 — 단순 경로였다면 그렇지 않습니다. 상태 배지가 Ready, Needs reauthorization, Unavailable, Access denied 가운데 하나를 보여 주며, 재승인은 클릭 한 번입니다.

백업 도중 드라이브가 분리되어도 작업 사본은 끝까지 완료되며, MailVault는 외부 사본에 도달하지 못한 메시지가 몇 통인지 알려 줍니다. 다음 실행에서 그 메일들을 옮겨 담습니다 — 잃는 것은 없고, 실패가 조용히 넘어가는 일도 없습니다.

가능합니다. 기본적으로 MailVault는 시동 디스크에 있는 앱 전용 Application Support 폴더 안에 메일 저장소를 둡니다. 이 저장소는 어떤 드라이브의 어떤 폴더로든 옮길 수 있습니다 — 외장 SSD든 두 번째 내장 디스크든 상관없습니다. 보관본이 수십 기가바이트로 커지면 중요한 선택지입니다.

메일 데이터만 옮겨집니다: 메시지, 헤더 캐시, 첨부파일 캐시, 폴더 목록입니다. 계정과 설정, 로그는 앱 자체 폴더에 남으므로, MailVault는 언제나 드라이브가 없다고 알리고 폴더를 다시 물어볼 수 있을 만큼은 시작됩니다.

무엇이든 지우기 전에 이동을 검증합니다. MailVault는 모든 것을 새 폴더로 복사하고, 파일마다 올바른 크기로 도착했는지 확인하고, 저장소를 전환한 다음, 그때에야 원본을 지웁니다. 연결이 끊기거나 앱이 죽어 중단된 이동은 현재 저장소를 그대로 남겨 둡니다. 다시 실행하면 이미 옮긴 것을 다시 복사하지 않고 이어서 진행합니다.

폴더에는 표식이 찍히고, 그것을 알아봅니다. 작은 표식 파일이 그 저장소를 식별하므로, 나중에 드라이브를 다시 연결하거나 폴더를 손으로 옮겨도 MailVault를 그쪽으로 다시 가리킬 수 있습니다. 또 MailVault는 다른 저장소에 속하거나 메일이 들어 있지 않은 폴더는 거부합니다.

드라이브가 연결되어 있지 않으면 MailVault는 기본 위치에 조용히 두 번째 보관본을 만들어 반쯤 찬 사본 두 개를 남기는 대신, 메일 저장소를 쓸 수 없다고 알립니다. 드라이브를 다시 연결하거나 폴더를 다시 고르십시오. 언제든 기본 위치로 되돌릴 수도 있습니다 — 메일은 옮기기 전까지 있던 자리에 그대로 있습니다.

두 번째 사본과는 다릅니다. 이것은 실사용 저장소가 어디에 있는지를 바꿉니다. 외부 백업 위치는 그 위에 보관용 사본을 하나 더 얹습니다. 둘을 함께 쓰는 것도 — 메일 저장소는 빠른 외장 SSD에, 보관용 사본은 NAS에 — 합리적인 구성입니다.

컴퓨터에 맞춤법 사전이 없기 때문입니다. macOS와 Windows는 시스템과 함께 사전을 제공하지만, Linux에서는 사전이 배포판에서 오며 최소 구성으로 설치한 데스크톱에는 사전이 없는 경우가 많습니다. MailVault는 WebKitGTK를 통해 맞춤법을 검사하고, WebKitGTK는 enchant와 hunspell로 단어를 찾습니다 — 그래서 hunspell 사전이 설치되어 있어야만 밑줄을 칠 수 있습니다.

메시지 도구 모음의 버튼이 지금 어느 경우인지 알려 줍니다. 사전이 있으면 밑줄을 켜고 끄며, MailVault가 그 설정을 기억합니다. 사전이 없으면 스위치인 척하는 대신 바로 이 안내를 엽니다.

사용하는 언어의 사전을 설치하십시오:

Debian, Ubuntu, Mint
sudo apt install hunspell-en-us
Fedora
sudo dnf install hunspell-en
Arch, Manjaro
sudo pacman -S hunspell-en_us
openSUSE
sudo zypper install myspell-en_US

언어 코드를 자기 것으로 바꾸십시오 — hunspell-de-de, hunspell-fr 같은 식입니다. 여러 개를 설치해도 됩니다. MailVault는 시스템 언어와 맞는 사전으로 검사하고, 맞는 것이 없으면 설치된 전부로 검사합니다. 그다음 MailVault를 다시 시작하십시오 — 검사기는 앱이 시작할 때 준비됩니다.

snap 빌드는 특별한 경우입니다. 엄격하게 격리된 snap은 호스트에 설치된 사전을 볼 수 없어 자체 사본을 안고 다닙니다. snap이 사전이 없다고 알린다면 대신 .deb 패키지를 설치하십시오 — 그쪽은 시스템에 이미 있는 사전을 씁니다.
