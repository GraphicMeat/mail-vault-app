云备份意味着服务商可以永远读你的邮件。本地备份意味着只有你能读。

6 分钟阅读

一旦有人接受了“收件箱不是备份”这件事 — 它确实不是，我们详细论证过这一点 — 接下来的本能反应通常是再找一个云产品来补救：一个第三方备份服务，接上 Gmail 或 Microsoft 365，把一切持续复制到它自己的服务器上。感觉像是把问题解决了。从结构上看，这更接近于把问题挪了个地方。

你并没有消除单点故障。你只是又添了一家公司，它长期持有你收发过的每一封邮件的副本，外加继续永久拉取新邮件所需的凭据或委托授权。

云备份服务商实际掌握着什么

大多数云邮件备份产品背后的架构很直白：服务通过 API 或协议级访问直接连上你的邮件服务器，复制每一封邮件和附件，并把这份归档存在备份服务商自己运营和管理的服务器上 — 不是你的。这就是它全部的价值主张；同时也是它全部的风险面。

只要订阅还在续，备份服务商 — 以及顺带地，任何成功攻破他们系统的人 — 就能持续访问你完整的邮件历史。不是你注册那天的一张快照，而是一份不断增长的归档，攒得越久，对攻击者就越值钱。你把「我的服务商有我的邮件」换成了「我的服务商和一家备份供应商都有我的邮件」，这严格来说是暴露更多，而不是更少。

这些都不意味着云备份服务商疏于职守或者做得不好。靠谱的公司在安全上投入很认真。这里说的是结构问题，不是对某家具体公司的评判：把敏感数据的更多副本，集中到更多由其他组织控制的地方，出错的路径就会变多，无论每一方各自执行得多好。

真正重要的那个问题

评估任何一种邮件备份方案时，要问的不只是“别处有没有一份副本”。而是：谁能读到那份副本，以及能读多久？

放在某家服务商服务器上的副本，可能在满足内部访问条件时被该服务商的员工读取，可能被对该服务商有管辖权的法院调取，可能在该服务商被入侵时泄露，也可能在该服务商被一家数据处理规范与你当初信任的那家不同的公司收购时被一并交出。这些结果都不需要你这边出任何问题。它们只是「副本存在于别人基础设施上」这件事本身自带的属性。

放在你自己磁盘上的副本，只有其中一类风险：你自己的设备安全。这是一份实实在在的责任 — 全盘加密、一台管好的机器，想要更多冗余的话，再给备份做个备份 — 但这是一个边界清晰、由你直接掌控的单一风险，而不是无限期地托付给第三方替你管理的开放式风险。

本地备份还能扛住更多状况

除了访问权的问题，本地副本还能扛住一串具体的失败情形，而云到云的备份并没有真正解决它们：备份服务商涨价或者关停，备份服务商自己的服务偏偏在你要恢复时宕机，因为一张卡过期而导致订阅失效，或者服务商把条款改成一个你今天不会同意的方向。你磁盘上的一个文件没有订阅状态。它就在那儿。

MailVault 的做法不一样在哪里

MailVault 连接你现有的 IMAP 或 OAuth 邮箱账户，把每个文件夹都归档成一个个独立的 .eml 文件 — 直接写到你自己的磁盘上。中间没有一台由 MailVault 运营、存着你邮件副本的服务器。我们读不到你的归档，因为我们从来就没收到过；连接发生在你的设备和你的服务商之间，产生的文件只存在于你放它们的地方。

格式在这里同样要紧：.eml 是一种朴素的开放标准，任何邮件客户端都能读，而不是把你的归档绑死在某个软件、或某家公司能否继续存在上的专有数据库。手动的、不限次数的本地备份是免费的，就这么简单。不用你记着去点一下、自动让归档保持最新的定时备份，是 $4/月 或 $25/年 的 Premium 功能 — 年付方案含 14 天试用。
