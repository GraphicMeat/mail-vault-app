# MailVault Architecture

This document describes the stable architecture of the codebase and the design rules that should guide future changes. It is intentionally higher level than implementation notes in code.

## Goals

- Keep email data local and portable.
- The Tauri app is a thin shell; all heavy logic and actions run in the daemon, off the UI process, on their own threads.
- Keep the React layer focused on presentation, state coordination, and user workflow.
- Preserve feature parity across providers and views wherever practical.
- Prefer changes that improve resilience without obscuring control flow.

## Local drafts and compose recovery

Local-only drafts use a stable logical draft ID across editor windows, account changes and restarts. The daemon owns `drafts.save`, `drafts.list` and `drafts.discard`, MIME/attachment preparation, copy-on-write vault identities, revision ordering and durable terminal cleanup in the existing app.db. An issued complete revision and its exact request remain separate from the last native accepted revision and physical location. An unknown save reply retains the same immutable revision for retry. Account moves publish the destination before retiring old copies. Native metadata projects one logical draft onto the existing list and UID caches; stale physical copies cannot become duplicate editable drafts.

The existing compose-session settings value remains UI recovery state. Main owns a cleanup-only entry for explicit discard and draft retirement after actual send or schedule acceptance. It freezes the stable ID and latest complete snapshot before discard, fences further autosaves, distinguishes acknowledged native cleanup-pending from an unknown RPC outcome, and preserves terminal intent through minimize, detach, hydration and source-window removal. Unknown cleanup waits for initial session hydration and its merged React array to commit, then is acknowledged with `flushSafeStorage` before its last UI owner is released; a failed flush keeps the in-memory entry and a retry indication. Restore and explicit Retry perform only canonical draft cleanup, never reopen an editor or resend/recreate a schedule. No additional queue, persistence key or polling worker is involved.

Undo-send retains its existing editable snapshot until actual `sendStaged` success. Afterwards draft cleanup failure cannot become an SMTP/outbox retry or invalidate a successful schedule. Automatic retirement carries the frozen issued `throughRevision` bound through retries and restart; the existing native draft mutex checks accepted, pending and retry claims atomically and skips a newer revision without a tombstone. Main conservatively retains a reopened writer even when unpublished typing is ahead of its snapshot. Draft-row reopen, Outbox Cancel/Dismiss and Undo all use the same owner admission path. While conditional cleanup is reserved, supplied restore content and its mode/reply context stay noneditable until settlement; a native skip releases it on the current ID, and a terminal result preserves it through the existing fresh-ID recovery seam. Explicit user discard remains unconditional. The queued closure retains main's terminal-owner callback after the editor closes. Detached bridge acceptance continues to mean main owns the undo queue. Child accepted identity changes signal a coalesced, owner-fenced native metadata reconciliation in main, rather than treating child-provided identity as proof or querying on keystrokes.

## Read-only compose preparation seam

`mailvault_core::compose_prep` holds pure reply recipients/ancestry, quote content, mailto decoding, ordered UX checks, attachment reminder policy and send-plan conversion. `compose.reply_context` and `compose.check` run bounded work off the IPC runtime and are marked foreground so indexing yields. They never fetch a body or attachments, read credentials, stage/send mail, create a schedule or mutate the vault. Native checks use the daemon clock and an explicit IANA zone; the source-specific two-pass offset algorithm preserves the JavaScript fold/gap outcomes. Both methods dispatch before OAuth credential injection, including when unknown account-bearing fields will be rejected. Complete message preparation has no product byte/count cutoff or truncation; complete authored check text likewise has no aggregate byte cutoff. Mailto payload validation and the independent account-file reader keep their existing limits. The ordinary 30-second reply budget and blocking-worker isolation remain unchanged.

The two routes read strict nonsecret account records and one versioned settings snapshot, rejecting recovery or malformed identity data. Absent optional identity maps keep their existing empty defaults. The returned `settingsVersion` names those same accepted values; accounts bytes and settings version/values are checked again before replying. An optional `expectedSettingsVersion` fences an acknowledged owner write. SettingsDoc may update its existing version sidecar during observation; the compose routes never write the settings document. Compose applies ECMAScript trimming on every identity input before using the shared no-trim mailbox folding primitive; legacy notes/search callers retain their Rust trimming wrapper. Initialization account precedence, localized labels/date formatting, DOM text extraction and the existing wire quote marker remain frontend responsibilities.

Reply/forward and mailto callers use `services/composePrep`: it projects only supported original header/body fields, supplies localized presentation labels, validates response types/request/version, and refuses native sender fallback mismatches. Main flushes accepted settings and reads back the coherent version and intended alias/default-From maps before preparation. A token-fenced detached request waits for main settings callbacks and receives that numeric version; child-disabled storage cannot acknowledge writes. Main account and identity changes invalidate pending child work.

Compose initializes authored body/signature/template independently from generated defaults. One coalesced preparation generation preserves recipient/subject edits and has an explicit readiness guard and retry. Failed initial preparation retains editable content and session recovery flags; a failed quote-only fill keeps the accepted header reply usable. Automatic detach waits for readiness. App's narrow reply-fill controller retains the latest complete resolved intent, coalesces preparation under a changed identity while the same window/original remains attached and nonterminal, and awaits the actual reducer commit before retiring that intent. Ordinary timeout/errors report once without automatic retry. App prepares late fills outside its reducer and commits only to the captured current window/original/identity generation; live editors consume the prepared result, and minimized merges change only quote/context plus replyTo, preserving immutable issued draft bytes until ordinary save. Complete message inputs are neither truncated nor count-limited.

Mailto keeps synchronous scheme claiming while its existing module retains ordered intent occurrences until asynchronous preparation and opener delivery succeed. Shell queue takes and wake drains serialize, accepted URLs survive stop/remount in memory, and opener/bridge generations fence every await. Preparation errors have visible Retry; this adds no crash-durable URL queue or polling. The browser demo has a backend-owned preparation adapter using isolated pure policy helpers, with settings/account/version authority and no live store import at backend startup. The thin `checkCompose` adapter preserves complete authored text and validates the exact native invalid/confirmation/ready union, request/settings version and optional issued draft identity. Scheduled readiness also requires a valid Gregorian date/time and runtime-supported timezone; validation does not convert the wall time or reselect its route. Its ordinary mode acknowledges the narrow send-check settings projection and can reacknowledge one settings conflict; an explicitly supplied settings version performs one final check without an ACK or retry. The demo check uses backend-owned settings/accounts and an injected clock with isolated pure helpers. Production Send uses native ordered validation, attachment confirmation and routing for one complete snapshot captured before waiting for saves. A synchronous submission claim and immediate monotonic edit/settings/account generation fence every await; Send anyway is bound to the same confirmed source. Detached main retains one transient checked attempt per existing token-fenced session. The child admits only by attempt/generation reference; main checks the fixed acknowledged settings version again, compares current account and sender authority synchronously, then hands a separate copy and the final native route to the existing queue or scheduler. Invalid/confirmation ACKs remain nonterminal. Send-check preparation has a finite 70-second outer timeout; reply settings ACK and final admission ownership retain their existing budgets. This adds no persisted draft state or queue and preserves the original issued cleanup bound, Undo and accepted-ACK-loss ownership. Transport validation and accepted draft identity/revision/terminal contracts remain unchanged.

## System Overview

MailVault is a desktop application built from three runtime pieces: a React frontend, a thin Tauri v2 shell, and a Rust daemon sidecar that does the work.

- `src/`: React UI, Zustand stores, hooks, and browser-side service adapters.
- `src-tauri/src/`: the shell. Windows, native dialogs, OS integration, external-location authorization, spawning the daemon, and forwarding requests to it.
- `src-daemon/`: the daemon. Sync, fetch, send, delete, backup, archive, indexing, import/export, vault and cache writes.
- `src-core/`: shared Rust logic used by the daemon (and, during migration, the shell). Testable logic lives here.
- `website/`: marketing site and website API, kept separate from the desktop runtime.

The app is not a web app wrapped in Tauri, and the Tauri process is not the backend. Work happens in the daemon; the shell exists so the UI has a native window and a channel to the daemon.

Migration note: many Tauri commands still do real work from before this split. They are legacy, not precedent. New work goes to the daemon; an existing command that does real work moves to the daemon when it is touched.

## Architectural Boundaries

### User bulk pending state

`mailvault_core::bulk` freezes selected keys in first-seen account/mailbox order and interprets the existing `app.db` pending-operation meta record. The daemon loads it without starting mail work; `bulk.status` exposes it as awaiting Resume, and `bulk.discard` clears only the matching pending id. Unknown versions and unreadable records remain errors with their evidence retained. New intent records are versioned, retain the original selection, and reach app.db before the coordinator grants the single in-memory operation ownership. Every resume plan requires fresh provider identity and copy proof before a future worker may delete; a legacy phase label or progress count grants no destructive authority.

The ordinary worker implements archive, permanent server delete, archive then verified delete, and archive then verified mirror copy then delete. It freezes membership once, runs every folder through a phase before advancing, copies in batches of 100, and checkpoints exact destructive attempts and successful identities in the same app.db record. An attempt whose remote outcome was not durably recorded is uncertain after restart and is never blindly replayed. Resume requires the original provider identity and fresh copy proof; legacy records with no native identity evidence remain unresolved. Selection keeps an immutable companion snapshot for each selected key, captured from its actual original row before asynchronous work. Native admission requires typed original target hints and preserves their exact request Scope in the existing FrozenIntent; current cache rows establish native eligibility but never repair original generation, origin, Message-ID or provider proof. The worker compares that original evidence with the provider before any mail effect. Successful archive/store outcomes carry exact raw-byte hashes and stored identities after custody persistence. A different existing vault payload is preserved and refused rather than overwritten. Verify, copy and pre-delete checks re-read those receipts through the targeted registry/message-store boundary, including records/blobs and messages without Message-ID; failed archive fetches cannot borrow stale UID presence as proof. Worker mirror copies compare the exact receipt bytes. Worker archive and bin reads validate the frozen generation and Message-ID on their fetch connection before replacing or capturing local bytes; Graph and JMAP archive reads retain the original stable provider IDs. A non-secret provider-origin hash prevents an account endpoint edit from retargeting an active or resumed job while token/password refresh remains allowed. IMAP generation validation happens on each deletion connection, including pool retries; the worker refuses exact deletion when UIDPLUS is absent, while legacy delete callers retain their original fallback. JMAP retains its mailbox-label removal and destroy-if-last rule. Graph archival remains supported, while these four modes refuse Graph deletion.

Initial claim, exact duplicate comparison, checkpoint and Resume preparation use immutable owner seeds outside coordinator and journal locks. Claim validates the eligible pending Arc (or current empty state) and admission attempt under the journal fence, persists its prepared encoded record without the coordinator lock, then publishes compact ownership. During an admitted first claim, status reads the last committed compact view and cancellation promptly refuses until Active exists. A fence won during a successful write leaves durable inactive evidence and grants no worker. Allowed legacy pending writes invalidate the existing cached view before attempting storage, so a prepared empty claim cannot overwrite new legacy work. Checkpoint seeds share the existing immutable pending record. Full validation and JSON encoding run outside coordinator and journal locks; the journal fences the exact operation, execution attempt and base revision before the prepared string reaches the same app.db record, and remains held through publication. Active status reads the last committed compact snapshot and cancellation uses its own atomic token while persistence is busy. A validated versioned pending record also owns a cached inactive summary; legacy writers cannot replace it. None, legacy and error states still reconcile current disk evidence outside the coordinator lock. Resume uses an immutable pending seed and prepares its new attempt outside shared locks, then checks the exact pending revision and admission before persistence and publication. If an admission fence wins during the write, the successfully durable record becomes inactive pending evidence and no worker starts; a failed save invalidates cached mutation authority until a fenced reread resolves disk state. Large retired records are freed after shared locks are released. Provider errors in new bulk snapshots use translated service keys. A typed archive download-limit outcome keeps its dedicated manual-operation diagnostic through the durable checkpoint and drained snapshot; it promises no automatic retry. Each operation owns its cancel token and a named background-QoS thread/runtime. Provider and blocking copy work drains before the terminal event. The RPC only claims or controls work; live status uses short state access and no mailbox lock spans network or a copy batch. Local-folder eligibility reads only the selected target's existing native import marker under the vault gate. A known local target is excluded even when a server has a coincident name. Unreadable, symlink or unproved target state is unknown; an unselected corrupt sibling has no bearing on the target. Plain Delete during vault closure requires independent native server-list and selected-row/provider evidence. Closing an otherwise reachable vault for a move does not impose the archive write gate on plain server Delete.

The shell intercepts bulk.start and bulk.resume before both generic RPC paths, strips client mirrorRoot and externalStatus, and parks the native backup path/status pair and scope by operationId before kickoff. The hold and terminal evidence include an execution attempt id, so a delayed earlier terminal cannot release a same-operation Resume. Admission is recorded before pre-claim IO. An extension of bulk.status can fence an unstarted attempt, including a request delayed before registration; a later request carrying that fenced attempt cannot claim. Only a matching drain or a definitive done/rejected/fenced receipt releases access. An empty active snapshot or missing receipt never proves admission finished. Reconnect/lag uses these same receipts rather than releasing all. An absent mirror still lets archive finish and keeps all unproved server copies. Original selection snapshots now survive refresh, pagination, modal minimization and direct selection changes; a deliberate deselect/reselect captures a new original. Undo rekeys without native restore identity leave the new UID unresolved. The frontend adapter sends these original snapshots through the native bulk controls for all five actions. The manager owns only transport, exact native-attempt subscriptions and status-first recovery; shared purge facades prepare optimistic presentation once and reconcile only exact native target outcomes. Reader confirmations retain their original clicked Scope. App startup attaches to active status and offers explicit pending Resume/Discard without replay or legacy completed-key arithmetic. Old mail APIs remain available to unrelated callers. Compatibility pending writes share the journal mutex, cannot overwrite a versioned or active coordinator record, and refuse any incoming schemaVersion. Only native claim/checkpoint/resume produce versioned authority; unversioned worker/intent fields cannot become Resume proof. There is no additional job database or journal file.

Delete-everywhere uses the same worker and pending record, while retaining its exact original Scope and empty ordinary groups. Typed per-target proof binds the original provider identity or a native compose receipt and available raw-byte digest. Provider-only IMAP/JMAP dispatch returns exact successful UIDs before any local bookkeeping; Graph uses its existing Delete-to-Deleted-Items API without bin capture. Each target proof, attempted effect and completed outcome is checkpointed before its next effect. Uncertain attempts survive restart without blind replay. Before local proof, the worker captures requested target registry rows (including sequence and tombstones), existing mailbox/global invalidation epochs and the vault root in bounded mailbox -> vault gate units. It then builds one fallible, operation-local all-format names inventory per selected mailbox off shared locks, checking cancellation between entries. Each local unit rechecks those existing fences, opens only that target's exact candidates, validates every candidate's bytes and ownership, and unlinks only those candidates through the existing registry/index/record deletion bodies. Before initial server-local byte proof and final local bookkeeping, the metadata-only cached native owner must agree with the full original account/mailbox/origin/generation/JMAP-label owner; unreadable or conflicting ownership refuses effects. Initial owner/target evidence is read on one held custody connection. The final mailbox -> vault gate -> custody target unit keeps that existing custody guard from ownership validation through exact candidate reads/unlink and registry, receipt, custody, cache and local bookkeeping effects, so native cache publication cannot replace the validated owner before use. Connection-based proof and retained-receipt readers reuse the same policy without recursively taking custody. Provider, mirror and pending-checkpoint IO remain outside this unit. Graph/JMAP local proof additionally requires the exact provider ID from the targeted native-owned header row. Missing owner or provider ID leaves local work unresolved and cannot authorize mirror work, while the independently proved original server action remains available. Complete provider ledgers are read only by the existing server identity paths outside these local units; the fifth action does not resample a later selection through the legacy whole-cache/ledger classifier. IMAP generation metadata is a single indexed scalar read. Resume inventories retained, not-yet-attempted server proofs as well as completed-server targets; attempted/uncertain effects are never replayed. The D receipt reader accepts those resolved bytes under the same custody policy. An unreliable or changed fence refuses the target; there is no UID-wide rescan fallback. Shared JMAP blobs and decrypted-file cleanup retain their existing ownership rules. This bounds shared-lock work by target candidates rather than mailbox size; it does not add a cross-process or external-writer guarantee. A local identity conflict blocks mirror work. Ordinary local IO failures retain server counts. Complete compose receipts reach supported Workflow storage before exact source retirement, and Resume uses D's retained ownership reader. The mirror phase calls E2's proved capability on blocking work with no local/coordinator/DB lock, and only its durable Queued outcome increments queuedBackup. Missing proof never falls back to UID-only purge. Per-target mirror outcomes retain removed counts and unresolved reasons. Compact status retains the four purge counters; progress adds one exact target outcome, and the existing pending-operation reader exposes the full durable target list for reconnect reconciliation. The latest full pending row survives terminal drain until discard or a later operation replaces it; this getter has no history or operation selector. Consumers must match its operation id, native accepted attempt id, supported action and original Scope before reconciling, and ignore late responses after ownership advances. Missing or mismatching evidence requires identity-bound refresh/rollback of the original optimistic change, never another operation's target list or a destructive retry. A finished frame means drained, not proof that every target succeeded. The shell's same attempt-owned hold covers this action, including pathless unavailable/unconfigured reservations and fresh native resolution on Resume. No new journal, UI orchestration or dual execution is introduced.

### Native header batch identity

Native list, UID-header and server-search results retain their original `nativeIdentity`: account id, mailbox, UIDVALIDITY from the same IMAP SELECT (JMAP's existing synthetic 1; null for Graph), and the existing native non-secret provider-origin hash of the configuration actually used. JMAP batches also retain jmapMailboxId from the actual query or membership scope; label changes participate in the same coherent cache ownership checks. Actual Graph and JMAP email ids remain on their rows. Frontend ingestion attaches immutable `_nativeIdentity` to each original row and preserves it through memo, restore, unified, pagination and flag merges; retained rows never inherit a later batch's identity. Selection projects only explicit original identity fields into typed target hints; nativeExpectedIdentity and _nativeExpectedIdentity remain publication preconditions and never enter FrozenIntent. Native JMAP admission compares the original label ID with current native resolution before persisting the existing Identity::Jmap.mailbox_id binding. Missing original label proof is unresolved.

The coherent cache batch owns its identity in the existing mailbox metadata JSON. No per-row generation schema is added. Full and partial reads return that stored identity with their rows; `load_email_cache_by_uids` adds `envelope:true` for a coherent metadata-and-row read under the same custody lock, while the default remains an array. Legacy or unproved rows remain visible without acquiring today's configuration as proof. Row associations and the publication expectation are not persisted as per-row authority.

Before network fetch, native producers capture `nativeExpectedIdentity` from cache metadata: explicit null means observed unbound/absent, while a missing expectation is unresolved. A cross-identity publication compares that full expected scope/origin/generation inside the existing custody transaction before replacing only header-cache state and binding the fetched batch. Same-identity partial pages can merge. Corrupt metadata is not observed absence. The UI cache-save boundary also validates the currently configured native origin. Native sync validates an initial takeover of another origin after capturing its expectation, then pins that operation's expectation across backfill chunks; it does not reread credentials per chunk. A stale-publication refusal leaves a future current-owner backfill eligible. A captured A batch may remain explicitly A after an account edit if B has not published; consumers must compare original A with current B before effects. This preserves original association and fences ownership changes, without promising global response freshness or an account revision registry.

Normal cold/delta/backfill and JMAP rebuild use actual fetched proof. A changed SELECT generation refuses earlier STATUS assumptions. Source-scoped flag/count/prune writes cannot modify a different bound owner. Same-identity insert-only hole healing preserves proof; unbound repair cannot establish proof for retained rows. Generic unproved header/repair inserts explicitly invalidate batch proof, and metadata-only observations cannot create it. Local custody, Maildir/imports and provider ledgers remain outside header replacement.

Backfill coverage uses the actual listing SELECT generation and reads current cache ownership with its UID coverage before either zero-work exit. The existing process-memory completion marker is qualified by the attempt's captured requested origin and exact pre-attempt cache owner, including explicit unbound state. A changed origin or cache generation may try again; secret-only refresh and the same-owner no-op/error policy remain unchanged. Unreadable ownership and identity refusals cannot install a marker. Delayed completion compares only the marker it observed, so it cannot replace a newer owner's marker. Account/mailbox in-flight exclusion remains shared across owners; this adds no scheduler, durable registry or general freshness guarantee.

### External mirror path invariant

Every raw account email and mailbox name reaches the external mirror through fallible `maildir::mirror_cur`. The email must be one safe component; mailbox hierarchy is validated on both separators while retaining the raw name and the platform's existing join behavior. Validation rejects traversal, NUL and drive-prefixed components on every OS. On Windows it also rejects stream syntax, device names, trailing-dot or trailing-space aliases and invalid Windows characters. On Unix these literal characters retain their existing safe layouts. The `mirror_safe` boolean helper retains the folder-operation traversal contract; the builder applies the additional component rules. Safe names retain their exact layout and Unicode; nothing is sanitized into a colliding name. Callers propagate refusal before mirror IO or deletion authorization. A scan that cannot validate or reach its mirror is unknown, never confirmed empty. Legacy invalid purge entries stay unresolved while valid entries drain, and disconnected drives cannot accept new invalid entries. Optional flag updates may omit an unsafe mirror while updating the vault. `mirror_cur_in` only appends `cur` to an already trusted directory; import rehome receives it from the validated presync builder. Lexical validation does not provide symlink or reparse-point containment, and external bookmark ownership stays with the shell.

Native mail-mirror mutations share process-local exclusion keyed by the canonical existing authorized root. A short map lookup supplies a strongly owned root mutex; filesystem resolution and waiting occur outside that map lock. Copy/readback/failed-copy cleanup, archive, Graph/JMAP backup writes, presync and local-folder copies, import replay, flag renames, mailbox moves/adoption and legacy purge use bounded root units, with no provider work or local vault locks held. Caller-owned filename listings retain that root handle and compare its in-memory mutation revision before reuse. Flag intents take WRITER before local mailbox/gate/custody work, fully release those scopes, then take the mirror guard while preserving intent order. Replies still wait for mirror completion so shell bookmark access remains held. Missing roots are unavailable and never recreated. This excludes participating writers in one daemon only; external actors, overlapping configured roots and other processes are outside the guarantee. Legacy UID-only purge remains identity-unsafe until its separate proof migration.

Protected native mirror purge retains a versioned original artifact proof in the existing app.db purge table (schema 10, nullable `proof_json`). Server provenance retains the original account, provider-origin hash and target provider identity; local provenance requires a freshly validated Present compose receipt. There is no digest RPC. Immediate purge first atomically inserts or matches its obligation, refusing legacy or conflicting work before touching files. Immediate and delayed execution share a fresh fallible listing, exact raw-byte hash for every same-UID candidate and unlink under one root unit. Mismatches, failed listing/read/unlink and malformed/future payloads remain unresolved. A complete empty listing is idempotent absence; a missing folder is unknown. Database snapshots are released before root resolution/IO and the guard is released before exact-payload conditional acknowledgement. Cancellation is checked between targets. Compatibility reads/writes/import cannot flatten protected rows; NULL rows explicitly retain their legacy UID policy. Native bulk delete-everywhere and frontend cutover remain separate work.

### Frontend

#### Atomic UI design and reuse

Build UI from the smallest useful shared units, then compose them into workflows:

- **Atoms** in `src/components/ui/` own one control or visual rule: buttons, searchable selects, segmented choices, labels, and accessible input states. Use one atom for the same interaction across Settings and the rest of the app.
- **Molecules** combine atoms into one understandable choice. `SettingsField` joins a visible label and explanation to a control; `SettingsSection` groups related fields with the shared settings card rhythm. Their layout and responsive behavior belong to the molecule, not each feature page.
- **Organisms** own a complete task with state and feedback, such as an Auto Tag rule editor, a saved View editor, or a message preview. They consume the shared controls and keep feature-specific rules in their store or service.
- **Templates and pages** arrange organisms in the Settings window, message list, or compose window. A page chooses the reading order and where a preview appears; it should not copy the atoms' CSS or recreate their keyboard behavior.

Reuse is an ownership rule, not a requirement to make every control generic. When two surfaces need the same behavior, extend the existing shared component and update both callers. When their behavior differs, keep two clear components. New settings flows should use the established 920px reading width, settings sections, field labels, and preview placement. Preview data stays local to its editor and never repaints the active mail list. A detached window is another host for the same page component, not a second implementation of that page; the main window remains the owner of persisted settings and receives explicit changes from the detached host.

Notifications enter exactly one display chokepoint: `notify()` in `src/stores/focusStore.js`. Native sync owns new-mail arrival proof, grouping, policy and the selected presentation variant (`src-daemon/src/arrival.rs`, `src-core/src/arrival.rs`). `sync.events` returns prepared notices or the same native owner emits a bounded deferred `notify` event; a late `code-ready` event offers a bubble without another banner. The renderer formats the selected locale template and passes the native decision to `notify()`, which records the reason, applies the current privacy state and holds an eligible banner during a current Focus session. A local snooze wake uses one native ring proof through `notify.arrival` before that same display path. The older `notify.decide` route remains for compatibility callers. When the daemon's keychain gate closes and no app has the event channel open, the daemon posts its own "unlock your keychain" banner (see the keychain gate under Daemon), because there is no app to decide anything.

**Focus lock scenes.** A Focus session can run on a pixel-art 3D scene (countryside, sea, town) instead of the plain lock. It is presentation only and lives in the frontend: `src/components/focus/FocusScene.jsx` mounts it, `src/components/focus/scenes/` holds the engine (`world.js`), the screen-fit math (`view.js`, pure and tested on its own) and one module per scene. three.js is imported only there and only through dynamic `import()`, so it ships as its own chunk that loads when a lock opens; a static import of three anywhere else would put about 750 KB on startup. The scene's day is a pure function of the session's start and end stamps, so nothing about it is persisted beyond the chosen scene id in `focusStore`. It fails soft: no WebGL, a chunk that will not load or a lost GPU context falls back to the plain lock, and the WebGL context is released when the lock closes.

**Privacy mode.** People's names, emails, phones and addresses are masked at render time by a pure detector (`src/utils/privacy/piiDetector.js`, names from the daemon contacts index via `people.contacts.names` plus loaded headers plus own accounts). It lives in the UI deliberately: it masks only what is rendered, does no I/O and persists nothing, so the thin-shell rule holds. Masked text is replaced with filler before it is blurred; originals stay in React props or a WeakMap, never in the DOM, so clones and exports cannot leak them. Two deliberate exceptions: an editable person field (compose recipients, alias and rule inputs) keeps its value and is painted as discs (`.mv-private-input`), and a message frame's `srcdoc` holds the raw body until the frame's own pass has masked it. Message frames arrive gated (`#mv-privacy-gate`) and are revealed only after `useBodyPrivacy` has masked them. `notify()` masks banners. The source view is blocked while privacy is on. Known limits: an email popup opened before privacy was turned on stays unmasked, PDF attachment previews are not masked, and text inside images is never detected.

**Private and social export.** Both stay in the frontend export pipeline (`src/services/export/`), like the plain image and HTML export: rendering a message to a canvas or a self-contained file is presentation, and nothing in it writes the vault. The dictionary comes from `PrivacyDictionaryHost`, which builds only while something needs it: privacy mode, a social capture (`captureMask`) or an export waiting with `dictWanted` up. `dictWanted` builds the dictionary without masking the UI; `ensurePrivacyDictionary` raises it (shared by a counter across overlapping exports) and waits up to 10 s under the busy spinner for a build made after it woke the host, not a stale `ready` flag. A redacted export (`exportRedact.js`) masks the headers structurally and runs the detector over every body text node, then strips what never renders but would ship: comments (Outlook's conditional blocks), `<template>` content, links, remote image and CSS URLs, and any other attribute holding a match. Image exports blur or bar `.mv-pii` spans of filler; HTML exports write `█` runs, header card included. Attachments are renamed but their bytes are not redacted, so redaction starts with them off. A social image (`services/export/social/`) is either the email card (the same redacted render, always shown whole: header block in the Appearance theme and mail body in the Mail theme, rasterized apart and stacked; a dark body runs Dark Reader under a nonce-only CSP) or the live app window captured with `modern-screenshot`. For a redacted app capture, `captureMask` masks the live UI in place for the length of the capture: React fields mask in the same render and the message frames are masked by their own `useBodyPrivacy` pass, with no reload. The clone is redacted again before it is drawn, and each frame's body is rasterized separately and composited over its rect. While privacy mode is on, every social image is redacted. The export (Image, HTML and Social, one tab strip shared by the dialog and the window, Social for a single message only) can open in a window of its own (`ExportWindow`, `kind: 'export'` in `open_auxiliary_window`, `export-*` in the default capability, listed in `isChildWindow` so it never writes shared files): the window holds only the panels and switches format in place, every build runs in the main window (`useExportWindow`: `exportSource.buildLocal` for Image and HTML, which also forces redaction while privacy mode is on, and `buildSocialContent` for Social, whose app shot answers `not-open` once the main window has another message open) and comes back as plain files or a PNG to preview and save, the Social style is written to the main window's settings, each panel's choices travel as `{ format, files, social? }` under their own names (redact starts on in one and off in the other), and Back to app reopens the dialog on the messages the main window kept.

**Alternative body renderers and the Blitz module.** The reading pane draws a message in an iframe by default. `src/components/email/bodyRendererRegistry.jsx` is the one core seam for drawing it another way: a module registers `{ Body, SettingsRow }` under a name, a surface calls `useAltBodyRenderer(surface)` and draws the returned component instead of its iframe when the `emailRenderer` setting (`'web'` by default, or `'blitz'`) names a registered renderer, and `BodyRendererSettingsSlot` renders the registered rows in Settings, Appearance, Colors. With nothing registered, or the setting on `'web'`, the hook returns `null` and the surface draws its iframe exactly as before. Every mail-body surface asks, by name: `reader` (`EmailViewer.jsx`), `thread` (`ThreadView.jsx`), `bubble` (`ChatBubbleView.jsx`), `fullView` (`FullViewEmailModal.jsx`), `original` (the quoted original in compose) and `popout` (the Open in window view), both `OriginalFrame.jsx`, and `preview` (`EmailPreviewFrame.jsx`, which the Cleanup and Time Capsule previews share). Image export and the social card reach the module through the registry's `rasterize` and `compositeBodies` entries instead (`getActiveBodyRenderer()`), and Open in window through `openWindow`. The export dialog's HTML-format preview, PDF attachment preview and the exported HTML file format stay out of scope. The only renderer is Blitz, a Rust HTML engine, in the removable module `src/features/blitz/` (setting row, `BlitzBody`, `BlitzTiles`, `FailureBubble`, `service.js` for the `render.*` RPCs and the `render-updated` event, and `prepass/`). It is experimental and off by default. The Mac App Store build (`VITE_MV_APPSTORE`) carries it too, as the same opt-in setting: `scripts/build-appstore.sh` builds the shell with the `blitz-render` feature, and the worker is the daemon binary re-executed, so it runs under the daemon's inherit sandbox entitlements. A worker the sandbox refuses shows the failure bubble; the sandboxed spawn has not been run on a signed App Store build yet. While privacy mode is on, the hover URL chip under the pointer is not drawn at all, because a URL can carry a name the pre-pass does not know to mask.

- **Pre-pass.** Everything the iframe does with script happens before the HTML leaves the webview, on an inert `DOMParser` document whose scripts never run. `runPrepass` builds the document the iframe would get (`buildBlitzDocument` in `prepass/document.js`, which wraps the iframe's own `buildEmailIframeHtml` with the theme tag, the table mode and the link-safety sheet and no script, or the surface's own `documentHtml`), parses it, strips every `<script>` and every inline `on*` attribute, applies the iframe's own privacy redaction when privacy mode is active, and serializes. Blitz has no JS engine, so mail cannot run code in it whatever the pre-pass missed. Privacy follows the iframe (`useBodyPrivacy`): `usePrivacyDict` holds the body, drawing nothing, for up to 3 s per message while the dictionary loads, then draws with whatever dictionary exists; a pre-pass that throws leaves the body undrawn rather than drawn unmasked. HTML pre-passed for one privacy state is never served in the other: a flip (privacy on, a peek released, a capture mask) unmounts the tiles and closes their document in the same render, and the new document opens only from HTML built for the new state. The output is byte-identical for equal inputs (the constant CSP nonce `BLITZ_NONCE`), so a dictionary update that changes nothing does not reopen the document. The steps after the build run in one fixed order: folds, then privacy, then the unselectable marks and the open search's `<mark>`s, with plan B's parity stamp after those. Folds come first because the iframe's fold scripts run while it parses, before its load-time privacy pass; the search marks come after privacy because a mark inside a name would split it before the redaction could match it. Before folding, the pre-pass removes every `data-mv-*` handle and `data-quote-toggle` a mail wrote itself, since the worker trusts those attributes and a crafted `data-mv-fold` would hijack a toggle. Fold detection is one shared file, `src/utils/foldDetection.js`: `iframeQuoteFolding.js` inlines it into the iframe's script through `?raw` and `prepass/folds.js` imports it, so both paths fold the same elements, and a test (`foldDetection.test.js`) pins that the injected script carries the shared source.
- **Drawing and links.** `BlitzTiles` asks `render.open` for the document at the pane's width and the display's pixel ratio (clamped to 1 to 4000 CSS px and 0.5 to 4 before sending, because the daemon refuses values outside those ranges), then sends the theme with it (`blitzThemeFor`: `{mode: 'light'}`, or `{mode: 'dark'}` with the palette's email background and text colours and Dark Reader's brightness, contrast and sepia, so a palette change reopens the document), then shows 512 CSS px tall PNG tiles as `<img src>` URLs of the `mvrender` scheme, loading those near the viewport; a `render-updated` event (images arrived, layout changed) bumps the revision so the tiles reload. A hover or click is hit-tested by the worker (`render.hit` answers `{link, fold}`: the link under the point and the id of a fold toggle under it, which can both be set; hover keeps one in flight), and a click on a toggle opens or closes its fold (below), any other click goes through `activateEmailLink` (`src/utils/emailLinkActivation.js`), the same rule the iframe's click handler uses (mailto composes in-app, link safety asks first, otherwise the system opens it), so the two cannot drift. Links are also listed in a screen-reader-only nav; while privacy mode is on that list carries no `href` attribute and no address text, only the visible link text, as a role-link element that still activates the link, and a link with no visible text is left out.
- **Text layer and copy.** The tiles are pictures, so selection is real DOM laid over them (`text/TextLayer.jsx`): transparent spans that carry the worker's laid-out text, fitted to the runs it measured, so the webview's own selection, keyboard and accessibility act on them. `render.textRuns` answers one tile `{runs, owners}`; a run is `{x, y, w, h, text, fontPx, node, start, seg}` where `node` is the inline root's NodeId and `start` a UTF-8 byte offset into that root's layout text. A root is split into segments at hard newlines (`<br>`, a newline in `pre`), and a tile's runs are those whose segment's first line falls in it, later lines included, so a paragraph is one element of the layer however many tiles it crosses and a triple-click selects it whole; `owners` names the other tiles whose segments continue into the asked one, which the layer fetches too. A segment is drawn as one block of line wrappers that wrap at `<wbr>`, not `<br>`, which would add a newline to the selection's text; line boxes sit on whole pixels with each line's text shifted back by the fraction rounding took, so tall paragraphs at fractional line heights do not drift down the layer. Spans are keyed node, segment and tile, and a rev bump keeps the old runs until each tile's new reply lands, so a live selection survives a relayout; a new `docId` clears everything. Tiles are asked for lazily, only the shown ones, and select-all asks for every tile first. A selection becomes two endpoints `{node, offset}` (the span's `data-node` and `data-start` plus the DOM offset converted from UTF-16 to UTF-8). Copy is precomputed so the `copy` event can write synchronously: a controller (`text/clipboard.js`, rebuilt per rev) calls `render.serialize` at the end of a selection (pointer up, key up, or a short pause for a selection with neither), caches the rich and plain text keyed by the endpoints, and the document `copy` event does one synchronous `setData` of both flavours from that cache. On a cold miss it writes the layer's own text as the plain floor and tries a bounded promise `ClipboardItem` upgrade to the rich text; WKWebView rejects the upgrade, so the floor is what it keeps. The plain flavour gets CRLF on Windows, as the iframe's native copy does. The worker's `serialize` walks the inline roots between the endpoints in reading order, joins them the way WebKit joins blocks, splices a nested in-flow inline root (an inline-block, an inline table, a `<button>`) into its host at its box and leaves floats and absolute boxes as pieces of their own; the markup is our own `Range.cloneContents()`-style serializer, with the ancestor chain and table and list wrappers, because blitz's `outer_html` does not escape. Text marked `data-mv-noselect` (fold toggles, privacy masks), folded away, or hidden by `visibility` (a mail preheader is often `visibility:hidden`) is neither drawn into the layer nor serialized, plain or html, and a `visibility:visible` child of a hidden parent is still copied. The markup drops event handlers and any `href` or `src` (and `action`, `poster`, `background`) that starts with `javascript:`, `vbscript:` or `data:text/html`, which is stricter than the iframe's own copy.
- **Reply, keys and menu.** `BlitzBody` is a `forwardRef` exposing `{ selectionRoot(), selectionText() }`: the layer's root and the selection's copy text (the controller's cache when warm, the layer's text otherwise). A body renderer that receives a ref must be a `forwardRef` (`bodyRendererRegistry.jsx` says so), and `altBodyQuote` (`src/utils/replySelection.js`) turns it into the reply quote, escaped as `replySelection` escapes, so Reply quotes a Blitz selection with its `<br>` newlines; with no handle it reads the DOM selection as before. Keys stop at the focused body (`text/useBodyKeyboard.js`): only a plain Cmd or Ctrl with A or C, and Escape, act, every other key is swallowed at the body so the app's window shortcuts do not fire, as an iframe's never do, and Tab and capture-phase listeners are unaffected. The right-click menu (`menu/BodyContextMenu.jsx`) is a portal on `document.body`, fixed in the window and clamped into it, with Copy, Copy Link (added in place when the hit answers after the menu opened) and Select All, and closes on Escape, a press outside, scroll, blur, resize or a change of document.
- **Folds.** The pre-pass marks each quote and signature region and its toggle with `data-mv-*` attributes, and `DocMeta.folds` lists them (`{id, kind, open}`). A click on a toggle sends `render.fold {docId, id, open}`. The worker flips the region's `display` and the toggle's label by style mutation and relays out once; a fold already in the asked state changes nothing and bumps nothing. The reply is `{rev, meta}`, but the frontend takes the new layout only from the `render-updated` event the same operation emits, as for an image arrival. `BlitzBody` records the toggle optimistically, per message, so a re-open for search or fonts does not fold it again, and a refusal undoes only its own record (a sequence per fold id guards against a later click). A rebuild keeps the folds' state (`fold::carry_folds`).
- **Mail fonts.** The module hands the worker the mail's Google Fonts the way the iframe loads them, and no new network path exists: `useBlitzMailFonts` reads the families off the pre-pass document (`fontSourcesOf`), sends the installed ones with `render.fonts` before `render.open`, holding the whole read-and-send to 300 ms so a slow daemon never delays the body, and downloads the rest through `familyForMail`, which tracker blocking and this session's failures still refuse, so a blocked mail never makes a font request. `render.fonts {families}` is answered in the daemon, which reads the installed faces through `mailvault_core::google_fonts` and sends each family to the worker whole, in one frame, once; the host remembers what it sent and replays it to a respawned worker before the first call. The worker acknowledges each family; a registration that panics is skipped without ending the worker, and a worker that dies with replayed families still unacknowledged is blamed on the first of them, which is dropped from what the host replays (a family sent to a live worker is blamed the same way on the next spawn if it really kills), so one bad family costs a worker or two, not every worker. The worker keeps one master `FontContext` (system fonts and blitz's bullet font plus every family it was sent) and gives each document a clone. A document cannot see a family registered after it opened, so when a new family lands the worker reopens, in place, every open document whose HTML names it (same `docId`, `rev + 1`, an `updated` frame, the image cache carried over so nothing is fetched twice, folds carried), and the tiles reload. fontique keeps one font per weight and style for a family, so of the several subset files a css2 family comes as, the worker keeps the face with the best coverage of U+0020 to U+00FF for each weight and style. Known limitation: a glyph that exists only in a family's latin-ext file (Lithuanian, Polish or Czech diacritics) falls back to the next family in the stack in Blitz. Closing it takes a fontique patch (`collection/query.rs::matches_with` yielding the family's same-attribute siblings) and it must land before Blitz becomes the default renderer.
- **Failure never falls back to an iframe.** If `render.open` is rejected for any reason (`render_unavailable`, `render_too_large`, `render_too_complex`, `render_bad_request`, an `INVALID_PARAMS` error) or a tile of the live document fails to load (`render_tile_failed`), `BlitzBody` shows the message's plain text under a one-line notice and, once per message per session, a corner bubble, styled like the restore and outbox trays, offering to switch to the standard renderer. The plain text goes through the standard plain view's own masking, so privacy mode masks it and a privacy hold shows only the notice. Leaving a message forgets its failure, so returning to it tries Blitz again.
- **Removable by construction.** Only `src/main.jsx` imports the module (`import './features/blitz'`), and `src/features/__tests__/blitzBoundary.test.js` fails if anything else does (it sees `from`, bare `import`, dynamic `import()`, `require`, `import.meta.glob` and `new URL(...)` specifiers, resolves relative ones against the importing file, and ignores comments; it does not walk `__tests__` directories). The pieces outside the module are listed in "File and Module Placement" below, with the recipe for deleting it. `scripts/check-blitz-removal.sh`, run as CI job `blitz-removable`, proves a deletion on a scratch copy of the checkout in two phases: first the module stays and the `blitz-render` feature is switched off (`cargo check --all-targets` of the daemon and the shell), then the module's four layers (`src/features/blitz/`, `src-render/`, `src-daemon/src/blitz/`, `src-tauri/src/blitz_tiles.rs`), the entry import and the lines marked `# blitz-render` in the Cargo manifests are deleted, and `vite build`, `cargo check --all-targets` of the daemon and the shell, and the vitest suites for `src/components`, `src/stores` and `src/features` must pass. Phase 2 also deletes the files that exist only for the module (the e2e specs `connected-blitz-*.test.js`, their shot helper `tests/e2e/blitzSurfaceShots.js`, `wdio.blitz.conf.js` and `tests/fixtures/blitz-corpus/`; `src-render/tools/` goes with `src-render/`), and the vitest run also covers `src/services/export`, where the export and social-card seams are tested against a stub. The other cfg-gated lines in the Rust crates and the JS touch points are left in place on purpose: the script proves they compile out and degrade. A saved `'blitz'` setting with the module gone resolves to no renderer and the iframe draws.
- **Current scope.** Messages follow the app theme (dark mode is below), and every email-body surface draws through it (*Surfaces*, below), except the out-of-scope ones named in the first paragraph of this section. Text selection and copy, Reply quoting, the context menu, quote and signature folding, search highlights and the mail's Google Fonts work in it, with the known gaps listed under Known Gaps.
- **Dark mode and parity.** Dark mode in the Blitz renderer is Dark Reader 4.9.120's colour engine ported to Rust (`src-render/src/dark/`; MIT, attributed in each file's header and in `public/licenses/rust/darkreader-mit.txt`, and `src-render/tests/dark_attribution.rs` fails if a ported file loses its header or the notice goes). It runs in the render worker, so the app only sends `theme` with `render.open` (the same colours and options the iframe passes `DarkReader.enable`, taken from `src/utils/darkReaderInject.js` and pinned to it by `themeInputs.test.js`). Before the first resolve the worker reproduces what Dark Reader writes into the iframe DOM, from the same cascade positions:
  - the static override sheets, prepended to the first `<style>` (one is created when the mail has none);
  - per-sheet sync rules, appended to each `<style>` except `media="print"` ones, which Dark Reader does not manage;
  - `data-darkreader-inline-*` attributes and `--darkreader-inline-*` properties for inline styles, `bgcolor`, `color` and the other presentational attributes, and SVG fills measured by a layout pass (`dark::apply` takes the layout callback so that pass runs inside the net provider's layout window);
  - CSS-variable typing (`dark/variables.rs`, two passes in Dark Reader's order, with depth, call and total-output caps and a per-pass budget on reference-graph walks because the variable text is mail-controlled; a declaration block is indexed once, since Stylo finds a custom property by a linear scan);
  - `data:` raster `background-image` analysis and filtering (`dark/image.rs`): decoded in the worker for Dark Reader's `analyzeImage`, header-checked against `MAX_IMAGE_PIXELS` before any decode, decoder limits on top, a 64 Mpx per-document budget for the dark pass, an 8 MiB output cap per image and 16 MiB per document, charged on every use of an image, a cache hit included (past it an image keeps its URL). A `data:` SVG background is left alone (not inverted), and a large dark image with transparency becomes `none`, as Dark Reader's own filter draws it empty.

  Sheets are rewritten in place and never added: Blitz orders author sheets by node id, so a new node would change the cascade. Remote CSS backgrounds are never analysed, matching Dark Reader's failed cross-origin fetch in the iframe. `dark/` is checked against 4.9.120 golden vectors (`src-render/tests/fixtures/dr/vectors.json`, generated by `src-render/tools/dr-vectors/` from the pinned tag); regenerate them on a Dark Reader bump (`dark_attribution.rs` fails while the vectors name another version than `package-lock.json`).
- **Parity harness.** Parity with the iframe is measured, not assumed. The worker's `inspect` op (daemon `render.inspect`, not foreground) reports, per element carrying a `data-mv-id`, the rendered flag, the border-box rect, the six colours, the four border widths, font size, weight and family and a text line count. The pre-pass stamps those ids (`parity/parityIds.js`) and `BlitzTiles` exposes `data-mv-parity-{doc,width,rev,theme}` on its root, both only when the e2e harness sets `globalThis.__MV_PARITY__`. `tests/e2e/connected-blitz-parity.test.js` (opt-in with `MV_PARITY=1`, so the connected battery skips it) renders every fixture of `tests/fixtures/blitz-corpus/` (MIT templates from Cerberus, Lee Munroe and Postmark with their licences, plus MailVault's own `ours/` cases) in the iframe and in Blitz, at 576 CSS px and at 375, in light and dark, and `src/features/blitz/parity/compare.js` compares them per element (colours +-1 per channel, x and w +-1, y and h +-2, border widths +-0.5, font size, font weight, line count; a case that compared no element fails). `report.json` lists a case that threw (no Blitz root, an inspect error, a timeout) as failed with its error, and its `totals.complete` (every planned case ran, none threw or waited out its web fonts, each compared an element; a setup that failed is 0 of N planned) with every case passed is the gate (`parity/report.js` `reportGate`, run by `tools/parity-gate.mjs` in `parity-job.sh` and `run-parity.sh`, which exit non-zero otherwise); the reader's header must name the fixture just opened before either side is measured, and the iframe only once the mail's web fonts the reader registers have loaded (a wait retried once, then the case fails). Approved exceptions live in `known-diffs.json` (empty so far). Run it on the mini with `src-render/tools/run-parity.sh light|dark|light,dark [fixture-id,...]`. The one-to-one gate is not green: the last run passed 37 of 56 cases in light and 37 of 56 in dark (an earlier 38 in light counted a Postmark case measured before its web font loaded), and most of the rest (28 of the 38 failing cases) is the Postmark templates' web font, which the iframe loads and Blitz does not yet; the other 10 are layout differences in four fixtures that are not approved as known.
- **Vendored engine.** Fixes the parity loop needed live in `src-render/vendor/blitz-dom` (crates.io 0.3.0-beta.4, upstream commit 92b11f1, with stylo 0.22, parley 0.12 and taffy 0.15; `LICENSE-MIT` and `LICENSE-APACHE` kept), patched in through the `[patch.crates-io]` line in the workspace `Cargo.toml` marked `# blitz-render`. The series was rebased from beta.2 (parley 0.12 lays a line out as the union of the block's strut and its spans' boxes, so a `line-height: normal` span now gets its own font's line height with each metric rounded, not the block's): what beta.4 does itself was dropped (line-height `normal`, the line-height floor, row heights, collapsed gap widths, inline-block margins, the line after a trailing `<br>`, cell `vertical-align`, which beta.4 maps to `align-content`), the rest ported by intent. Every change is marked `MailVault parity fix (plan B)` (plan D adds three in `layout/table.rs`, marked `(plan D)`, each written from CSS 2.1 17.5 and 17.6 and measured in WKWebView: a percentage `max-width` is ignored on a table with a length `width`; a table is never narrower than its minimum content width, whatever its own `width`, except under `table-layout: fixed` and in intrinsic-size queries; and the collapsed-border painter, which lives in the unvendored `blitz-paint`, is fed nothing for a first cell without a visible border and otherwise the style and colour of its first visible side, where it had drawn a 3px dark frame around every borderless `border-collapse: collapse` table, such as the export header and the chat bubble's tables), has a test in `src-render/tests/parity_fixes.rs` (fixtures in `src-render/tests/fixtures/parity/`; the security and hardening changes, the SVG entity refusal, href resolver and budgets and the colspan and font clamps, are tested in `tests/svg.rs` and `tests/limits.rs` instead) and a drafted upstream text; nothing has been posted to DioxusLabs/blitz yet (they are offered to Rokas). Some are WebKit-specific and not upstream candidates (line-height truncated to whole px, the Helvetica ascent bonus, the table `max-width` rules). Three beta.4 behaviours are patched there too, marked `(blitz beta.4)` or explained at the patch: a table cell's `vertical-align` leaked into the root text style, so every line a `<br>` ends grew a pixel; a family list with no generic family and no installed family fell back to a system sans-serif, so it now ends in the serif default as in WebKit; and `SvgImageData::from_data` inflates SVGZ with no cap, so gzip data is refused, as beta.2 did by failing it as non-UTF-8 (BridgeNet's gzip refusal is the tested layer). `src-render/vendor/string_cache` (crates.io 0.11.0, the latest release, pulled in by stylo 0.22 and html5ever 0.40; second `# blitz-render` patch line) mixes the hash of an inline atom (7 bytes or fewer) with a splitmix64 finalizer: 0.11.0 returns the packed bytes, whose low byte is the same for every atom of one length, and stylo's `PrecomputedHasher` passes the value to hashbrown unchanged, so 40,000 short custom properties took 83 s to style (`tests/dark_limits.rs`). Accepted residue (pinned by tests in `src-render/tests/parity_fixes.rs` so a change shows): `blitz-paint` beta.4 lays a collapsed table's outer lines out as the table's own border and paints every collapsed line with the track gutter widths, so cell borders now ring the box on its outermost pixels as in WKWebView, but a row-separator table (cells with only `border-bottom`) also gets a top line WKWebView does not draw. parley 0.12 lays each line out as the union of the block's strut and its spans' boxes, and builds the strut from the font file's ascent; WebKit's taller Times, Helvetica and Courier ascent lifts its strut, so a Helvetica block with a span in another font (Arial) at a fixed line-height is a pixel taller per line in Blitz (postmark inbody in the export). Fixing it needs a metrics override in parley. The painter and parley are not vendored; vendoring the painter is the follow-up if screenshots show the extra line matters. The crates are not workspace members, so `cargo clippy --workspace` does not lint them. Re-run `src-render/tests/svg.rs`, `net.rs`, `dark_limits.rs` and `parity_fixes.rs` when one is bumped.
- **Module-side compatibility shims.** `<style media>`: Blitz ignores the attribute, so `src-render/src/styles.rs` wraps the rules of a sheet that has one in `@media` (the attribute parsed as a media query list, never pasted in as text; the rewritten text has its `&` escaped, because blitz-dom decodes entities in `<style>` text on every parse; the same pass is the carrier for Dark Reader's prefix and suffix). `word-break: break-word`: stylo's servo build drops the value, so `src-render/src/compat.rs` rewrites it to `overflow-wrap: anywhere` in the HTML text before parsing, only in `style` attribute values and `<style>` text, found in one linear pass over the markup. Edge no-break spaces: parley 0.11 trimmed a `&nbsp;` at the edge of a text run, so the vendored engine wraps one in a U+2060 word joiner; parley 0.12 no longer trims or hangs it, and the joiner stays only so the layout text keeps the shape plan C replays. The joiner exists only in the layout engine's text, not in the DOM, and plan C keeps it out of everything it produces: `src-render/src/text.rs` leaves every U+2060 out of the text runs and counts their offsets (`start`, `seg`) without it, so the text layer, its selection and the endpoints it sends back never see one; `serialize.rs` turns those endpoints back into layout bytes (`text::to_layout`) and leaves the joiners out of the plain copy (the rich copy reads DOM text); `dommap.rs` replays the joiners, and the vendored engine's dropped space before a `<br>`, through a model of parley 0.12's whitespace processing (one pending collapsible space carried across span boundaries, dropped at the start, after a preserved break and at the end), so layout text still aligns with the DOM and a selection next to an edge nbsp lands on the right DOM character. The inspector's line count skips such nodes, as the iframe's does a bare `&nbsp;`.
- **Surfaces.** Each surface hands `useAltBodyRenderer('<surface>')` a `Body` either the same pre-processed body its iframe gets or its exact `srcdoc` (`documentHtml`, which replaces the pre-pass's build step), and only once the daemon's body scan has answered. The surface records its own tracker verdict and link alert (`services/rowVerdicts.js`). The registry's `rasterize`, `openWindow` and `compositeBodies` entries serve code outside React.
  - `thread` and `bubble` mount many bodies, so a body opens its doc only near the viewport (`useNearViewport`) and hands the surface its measured height (`sizing`: `content`, `fill` or `{collapsedMax}`). A chat bubble's wrapper has a definite width of its own so the bubble is as wide as the iframe's was.
  - `reader`, `fullView`, `original`, `popout` and `preview` open on mount. `preview` is capped (`collapsedMax`) and scrolls inside.
  - Iframe-only effects (auto-size, link handling) list `!!Alt` among their dependencies, so switching the setting on or off with a message open re-attaches them.
- **Doc lifecycle.** Docs are held through `surfaces/docRegistry.js`, one per webview, keyed by the document's hash, width, scale, remote flag and theme. A holder gets its own handle (per-`docId`), so releasing one body never closes a doc another body still holds, and two bodies with identical html share one doc. Releasing the last handle defers the close for `thread` and `bubble` only: the doc waits in a deferred LRU of 8 for 60 s, so a scroll back or a collapse and expand reuses it. Every other surface releases at once. Switching the setting off closes the deferred docs a tick later, so the worker can idle out. A body that unmounts before its open lands drops the doc when it does, never leaking it.
  - The worker caps open docs per worker (`MAX_OPEN_DOCS` = 32, `RenderHost::lru_victims`): an `open` past the cap closes the least recently used other docs first, and any op on an evicted doc answers `render_unknown_doc`. `service.js` reports that to the registry (`docGone.js`), which stops serving the id and lets the body reopen once, quietly (no failure view, no bubble), before it counts the loss as a failure. A restarted worker loses its docs the same way.
  - The `original-*` auxiliary window installs its close handler on its first doc acquire, not at startup: a web-mode window (a compose window that may refuse its close) is left alone. On a close request it holds the close, awaits `closeAll` (live docs, and ones still opening, for up to 1 s), then destroys the window, since a destroyed webview runs no React cleanup.
- **Pop-out.** In Blitz mode "Open in window" opens the `original-*` auxiliary window through the existing ready/payload handshake (`openBlitzWindow`, `open_auxiliary_window`), with `surface: 'popout'` in the payload, not `open_email_window`. No mail document loads into a webview. The window keeps the subject as its native title (`core:window:allow-set-title` in the default capability) only while privacy mode is off; it is not re-masked if privacy turns on later.
- **Export.** `renderMessageToCanvas` asks `rasterize` first (`rasterizeWithBlitz`: `render.open` of the same export document, then `render.image`, whole document). The canvas is web-size and never downscaled, as the frame rasterizer's is. Under the image area cap (`MAX_IMAGE_AREA_PX`, 16.7 Mpx at doc scale) the PNG of `render.image` is the canvas. Over it, the worker would shrink the PNG, so `render.image` is asked with `settleOnly` (it waits for the doc's images and applies them, then returns the settled meta and paints nothing) and the canvas is built from full-scale `render.tile` PNGs drawn at their own offsets; the size always comes from the settled meta, because images relayout the doc after `open`. A document that reaches `MAX_CSS_HEIGHT` (200,000 CSS px) was truncated by the worker, so it becomes an export failure, as does any other failure to draw (`blitz_export_failed` in `failures`). No hidden frame is ever mounted in Blitz mode. The social app shot clones the DOM without the tile layers and `compositeBodies` paints each settled body over its visible rect from the live doc (`render.image`); a busy body, or any body not drawn masked while redacting or privacy masking, is skipped (fail closed). The dark card's body reaches both bottom corners in the mail background colour.
- **Workers.** The daemon runs `WORKERS` = 2 render workers (`RenderPool`), docs pinned by `doc % WORKERS`; the open-doc cap, eviction, watchdog and idle exit stay per worker, fonts register on both, and each worker's host has its own image-fetch slots (`FETCH_PARALLEL` = 6, so up to 12 fetches at once across the pool). While an image frame is outstanding the silence clock uses `IMAGE_TIMEOUT` (20 s) rather than the 6 s watchdog, so a long export paint does not kill a worker and every reader body on it.
- **Thread and chat perf gate (`tests/e2e/connected-blitz-perf.test.js`).** 20 corpus bodies in a scroll box (thread 680 px, chat 300 px), first paint of the visible ones, iframe against Blitz, p50 over 7 runs after a discarded cold run, on a debug build. The gate needs Blitz p50 <= max(1.25 x iframe p50, iframe p50 + 150 ms), <= 1500 ms, and a longest main-thread gap <= max(the iframe's, 50 ms). It FAILS the gate even with two workers, so no further tuning was done and the numbers went to Rokas. One worker: thread iframe 161 ms against Blitz 3056 ms, bubble 22 against 2628. Two workers: thread 164 against 1392, bubble 22 against 1362 (the 1500 ms and gap checks passed then; the ratio did not). Latest, with the table fixes (commit 8ab976b74, debug build, two workers): thread iframe 162 against Blitz 1534 ms, bubble 22 against 1363. The ratio check fails on both, and the thread now also fails the 1500 ms absolute check. A control that mounts only the visible bodies (not part of the gate) took about 255 to 353 ms on the thread and 266 to 333 ms on the bubble: time scales with the bodies opened, about 80 to 150 ms each on one worker, not with the visible ones. Open follow-ups for Rokas, not done: open the visible bodies first, measure a release build, or accept the debug numbers.

The frontend owns:

- Rendering and interaction flows.
- View-specific state and derived UI state.
- Coordination of async work through stores, hooks, and service adapters.
- User feedback, optimistic UI, and progress indicators.

Open compose windows keep a separate UI-session snapshot through `safeStorage`, alongside persisted preferences. App restores these snapshots as minimized draft bubbles after storage hydration. The snapshots retain editor fields, attachments, sending identity and reply context; the existing local-draft service still writes the message itself into the vault through the daemon. Sending or discarding a compose window removes its session entry.

The frontend should not:

- Reimplement transport or storage logic that belongs to the daemon.
- Encode provider-specific protocol behavior unless it is purely presentational.
- Scatter business rules across many components when they can live in a store or service.

### Tauri shell

The shell owns:

- Windows, menus, tray, notifications, and native dialogs.
- OS integration that must run in the app process.
- External file access authorization: security-scoped bookmarks on macOS, path validation on Linux (including Snap confinement detection). Long-lived access to user-chosen folders must be managed natively; the frontend renders state but does not own authorization. Filesystem features must degrade explicitly rather than silently dropping writes when access is lost.
  - **Every user-picked export destination uses this path**, not only the backup location: attachment downloads (Download All), a view's or a search's attachment download, the timeline's month and year downloads, and any future export. The picked folder is saved in its own `external_location.rs` slot (`SLOT_ATTACHMENT_EXPORT`, overwritten per pick) as a security-scoped bookmark on macOS, checked with a real write (`validate_external_location`), resolved with access started by the shell and held for the whole job while the daemon writes, then released. On Windows and Linux the same calls store the plain path and do the same write check; under Snap confinement that check is what refuses a folder outside the snap's reach, and the save says so instead of losing files.
- Daemon lifecycle (spawn, reconnect, shutdown) and forwarding requests and events between the frontend and the daemon.
- **Keeping the daemon alive across app quit and login** (`src-tauri/src/autostart.rs`, pure parts in `mailvault_core::autostart`). One setting, `daemonAlwaysOn`, drives two things: `RunEvent::Exit` skips the daemon SIGTERM so the running daemon is adopted by init, and a per-platform login item brings it back at login. `stop_daemon()` (vault moves, restarts) is unaffected; only the app-quit path is gated.
  - macOS registers through `SMAppService`. **Currently unproven and not working on a signed build**: `register()` fails with "Operation not permitted". The cause is not the app being sandboxed — Microsoft Teams is sandboxed and registers bundled agents fine — but the agent's *program*. A sandboxed app may not ask launchd to run a binary that is not itself sandboxed, because that escapes the app's sandbox, and `src-daemon/entitlements.plist` deliberately carries no `app-sandbox` key. Teams signs its agents `app-sandbox` + `application-groups` and puts them in `Contents/Library/LaunchAgents/`.
  - Fixing that is coupled to *where the app and daemon meet*. A sandboxed helper gets its **own** container (`~/Library/Containers/com.microsoft.teams2.agent` exists beside `com.microsoft.teams2`), so a sandboxed daemon would lose both `~/.mailvault` and `~/Library/Application Support/com.mailvault.app`, which today it only sees by inheriting the app's sandbox when the app spawns it. One binary cannot do both: without `inherit` it gets its own container, with `inherit` launchd cannot start it. The meeting point has to become the `group.com.mailvault` container (`core::group_container_dir`; a socket there is 76 bytes, under the 104-byte `SUN_LEN` cap) — a migration, so it is deliberately not done yet.
  - Two further facts cost a signed build each: **the agent label must sit under the app's bundle id** (`com.mailvault.app.daemon`, not `com.mailvault.daemon`) or macOS answers `NotFound`; and the App Store sidecar is signed `com.apple.security.inherit`, which aborts unless its sandboxed parent spawned it. `NotFound` is reported as "unsupported" only when the plist is genuinely absent — when it is present the switch stays live so `register()`'s NSError surfaces, which is the only reason the EPERM was ever seen.
  - Until this lands, the shipped behaviour is the half that works everywhere: the daemon outlives app quit. Nothing brings it back at login on macOS.
  - Linux writes an XDG autostart `.desktop`. Its `Exec=` names the *app* binary with `--daemon-only` (a launcher mode handled before any window exists), because the sidecar's own path depends on the packaging and an AppImage's mount root does not survive a reboot — `$APPIMAGE` is used there. Snap is refused with a reason rather than attempted: `~/.config/autostart` is outside the `home` interface.
  - Windows uses the `HKCU` Run key. The daemon speaks the same protocol over a named pipe there (see Where state lives).
- The settings JSON file only as a fallback, kept for one release (`read_settings_json`/`write_settings_json`: for a daemon without `settings.*`, one that is unreachable when a window first reads, or a write while it is unreachable; the write is `settings_doc::write_document`, atomic and under the daemon's lock), and the narrow **bookmark forwarders**: `vault_apply_flags`, `vault_rename_mailbox`, `vault_adopt_mailbox_dirs` (`vault_flags.rs`) plus `backup_run_account`, `backup_status`, `backup_purge_uids`, `backup_scan_uids`, `backup_copy_uids` (`backup.rs`, `commands.rs`), plus `attachment_export_start` (`export_folder.rs`), which forwards `export_attachments` and `views.export_attachments` for a folder the person picked, plus `abd_summarize`, `abd_start` and `abd_attach` (`abd.rs`) for the Archive & delete jobs. Of these, the vault and backup forwarders resolve the backup mirror's security-scoped bookmark, forward the call to the daemon with the resolved path as `mirrorRoot`, and release it again. `attachment_export_start` resolves the picked folder's bookmark in `SLOT_ATTACHMENT_EXPORT` instead and forwards the params unchanged (they already name `destDir` inside that folder), holding the folder for the job (below). The daemon cannot resolve a bookmark itself, so this one step of an otherwise daemon-owned operation stays in the shell; every rename, mirror copy, fetch and custody update the call triggers runs in the daemon.
  - Release timing splits the two groups. The six bounded calls finish before they reply, so they release on every path — success, daemon error, budget expiry. `backup_run_account` is fire-and-forget: the daemon ACKs the start with a `runId` and the run keeps going for minutes, still needing the path live. The shell parks the resolved path in `backup::HeldBackupPaths` (keyed by account id) and `daemon_channel.rs` releases it when that run's terminal `backup-progress` frame (`active: false`) comes back up the channel. A second start for the same account releases the displaced path rather than leaking it.
  - `attachment_export_start` has the job shape too, keyed by the client's `jobId` instead of the account: it saves and validates the picked folder in `SLOT_ATTACHMENT_EXPORT`, resolves it, parks the path in `export_folder::HeldExportPaths` before the call, and `daemon_channel.rs` releases it on that job's final `attachment-export-progress` frame (`finished: true`, result or error). A failed start releases at once, and a `daemon-events-lagged` event or a channel reconnect releases every held export folder, since either can have eaten a final frame (the app fails those jobs on the same two events).
  - `abd_start` is the job shape again, in backup mode only: it resolves the backup slot, refuses with `E_ABD_NO_BACKUP_DRIVE:` if the drive is not there (a backup-mode job never starts without it), parks the path in `abd::HeldAbdPaths` before the call and forwards `abd.start` with it as `mirrorRoot`. `HeldAbdPaths` is a separate map from `HeldBackupPaths` on purpose: a `backup-progress` frame must never release a job's drive and an `abd-progress` frame must never release a backup run's. `daemon_channel.rs` releases the path on the job's terminal `abd-progress` frame (`finished: true`) and on a frame saying the job paused for the drive (`drive_unavailable`); a lag or reconnect releases every held path, as for exports. Releasing early is safe because the daemon keeps running on the path it was given, a lost scope makes its next mirror write or verify fail (the job pauses, never deletes on a vault-only copy) and every delete re-verifies the mirror copy first. `abd_attach` is how a paused or restarted job gets its drive back: the shell resolves the slot again, holds it and forwards `abd.attach_mirror`; the app calls it on launch and reconnect for each backup-mode job and every 30 seconds while one is paused for the drive. `abd_summarize` is a bounded call (resolve, forward, release). Archive-only jobs never resolve or hold the drive.

The shell must not do heavy work: no transport, no vault walks, no indexing, no bulk file I/O. A Tauri command is a forwarder to a daemon RPC, not an implementation. **Apart from the settings file and the bookmark forwarders above, the shell no longer opens or writes a vault file, cache, journal or ledger at all** — the recorded exception that stood through Phases 3-5 is closed, in both of the two senses it was ever tracked in:

- No vault write lives in `src-tauri/src`'s own text. `commands.rs`'s `graph_cache_mime` went to the daemon at Task 5.6, `main.rs`'s `maildir_store_raw` at Task 5.4a, the mbox and backup-ZIP importers at Tasks 4.6/4.4, and the Phase 3 remainder took the last one: `backup.rs`'s Graph fetch loop and its bidirectional mirror pre-sync, both now in `mailvault_core::backup` in the daemon (the fetch loop's writes under the daemon's gate, the pre-sync outside it; see Daemon below).
- No app-side path *reaches* a core vault writer either. `src-tauri/src/archive.rs` — the shim that built the core archive runner's context with a deliberately no-op write gate, because the daemon's `vault_gate` `RwLock` cannot cross the process boundary — existed only for the app-side backup runner to call. With that runner in the daemon the shim had no callers and is deleted; the daemon's own backup route builds the same context from its own state under the real gate. `vault::root`, the app's mail-data path accessor, went with it for want of a caller, as did `main.rs`'s `maildir_cur_path`/`graph_ledger_path` and its `nudge_index` index signal. The app process now holds no `ImapPool`, no vault path builder, and no way to write a message.

`restore.rs` comes off this list entirely: it reads local `.eml` files and re-uploads them over IMAP, and never writes the vault. Its earlier inclusion here was a misclassification, an ungated reader flagged as a writer, corrected at Task 3.9 (the same failure mode project memory already cites twice).

`tests/unit/vaultInDaemon.test.js`'s `ALLOWED_WRITERS` is now **empty**, and keeps the real list of *message* writers closed at zero. Since Task 3.9 its pattern also sees a raw `fs::write` / `fs::copy` into a vault path, not only a `vault_files::` call - the Graph backup writer (`backup.rs`) was never routed through `vault_files::`, so the old pattern was structurally blind to it; the mbox importer had the same shape before Task 4.6 moved it to the daemon. As of Phase 4 (Task 4.9, verified with a negative control: plant a raw write on `main.rs`, watch the assertion go red, revert, watch it go green), `main.rs` no longer trips the raw-write pattern at all - its one surviving writer, `maildir_store_raw`, goes through `vault_files::store` and is caught by the `vault_files::` pattern instead, and since the Phase 3 remainder's Task 5 `backup.rs` does not either. With no offender left, neither pattern can be proven non-vacuous against a current file, so the guard instead asserts both patterns still match a planted example string — an empty offender list then means "nothing writes" rather than "the regexes rotted". `src-tauri/src/vault.rs` used to sit outside this list on purpose (`copy_tree`'s `std::fs::copy` and `set_aside_custody`'s `std::fs::rename` moved the whole vault tree during a relocation, a structurally different operation from a single message write); as of Phase 6 those functions are gone from `vault.rs` entirely, moved verbatim to `mailvault_core::vault_ops` and called from the daemon (`handlers::vault.rs`), so the exception no longer has a subject - `vault.rs` is now the bookmark broker and local status cache only, with no vault write of its own in either shape. Backup's own migration has now landed too (Phase 3 remainder), which is what empties the list; the bookmark-scope question that deferred it is still unanswered but no longer blocking, because the shell still resolves the bookmark exactly as it always did and only hands the resolved path across (see Known Gaps below).

**The `mvrender` scheme (Blitz tiles).** With the `blitz-render` feature the shell registers one asynchronous URI scheme, `mvrender` (`src-tauri/src/blitz_tiles.rs`). The webview builds a tile URL with `convertFileSrc`, which puts the path in one percent-encoded segment: `mvrender://localhost/<docId>%2F<rev>%2F<index>` on macOS and `http://mvrender.localhost/<docId>%2F<rev>%2F<index>` on Windows. The CSP `img-src` in `tauri.conf.json` allows `mvrender:` and `http://mvrender.localhost`. The shell renders nothing: it decodes the `%2F`, parses the three numbers and forwards to the daemon's `render.tile`, answering the PNG with an immutable cache header (`<rev>` busts the cache when a document changes) or a 404 when the daemon cannot. Doc ids start at a random per-daemon-boot base, so a respawned daemon almost never reuses an id whose tiles the webview still has cached. The same file holds the `reply_timeout` arms for the `render.*` family, each a little above the daemon's own budget so the daemon's `render_unavailable` arrives first: `render.open` 10 s, `render.tile` and `render.textRuns` 6 s, `render.fold` 6 s, `render.inspect` 6 s, `render.image` 30 s, any other `render.*` (`hit`, `serialize`, `fonts`, `close`) 3 s. The daemon routes `render.open`, `render.tile`, `render.hit`, `render.textRuns`, `render.serialize`, `render.fold`, `render.fonts`, `render.inspect` and `render.close` today; `render.image` and `render.tile` are the export path (*Export*, above). `main.rs` carries only the `mod`, the `register` call and the delegation from `reply_timeout`, all behind the feature.

### Daemon

The native account routes are `accounts.list/get/put/reorder/replace_all`, `accounts.save/add/update`, and `accounts.remove_local`, backed by `mailvault_core::accounts_doc` over the accepted JsonDoc engine. Public `accounts.remove` is retired; metadata-only removal remains an internal AccountDoc operation. `accounts_fallback` is read-only. The JavaScript DB adapters use native per-record credentials; add/update and complete removal workflow ownership are described below. Legacy arrays remain readable, including old secret fields. Incoming records and newly made good backups have password and OAuth token fields removed. Before daemon live cleanup, unique representable legacy records are preserved through the state-aware credential writer, whose finalizer owns credential events. The account writer then checks the entire preserved list and its version before cleanup and the requested mutation. A changed snapshot refuses the operation; callers must explicitly read and preserve again. Missing/empty/non-string IDs and any duplicated secret-bearing ID make the list unrepresentable: credential preservation is skipped and retained live fields stay in place. Internal metadata removal and supported replacement retain their requested semantics.

Account writes use PrivateDurable creation and durable sidecars, supported OS locking, atomic replacement and version fences. Existing plugin-fs writers do not participate in the lock; this does not promise universal cross-process CAS or an atomic document-plus-sidecar crash commit. Historical backups and raw corrupt copies are not retroactively scrubbed, existing lock permissions are not retroactively changed, and no new Windows ACL guarantee is introduced. The shell delegate uses backup-only cleanup and performs no credential IO or daemon event emission. Its availability does not authorize retrying an unknown daemon mutation. Account shell replies retain 30-second read and 50-second write budgets; the combined credential/document path may exceed the write budget, and timeout does not cancel native work. Portable host companion cleanup is best effort only after a successful requested copy/removal; individual companion failures are not included in `removedFromHost`. The earlier renderer deletion path checked compose receipts before its direct metadata, credential and file cleanup. The current native retirement route below owns the complete ordered operation and reports its exact outcome.

The native credential routes `credentials.get/save/update/delete` use fresh per-record changes and a shared core split-secret writer. App DB adapters use these native calls; the shell's compatibility credential writers are retired. Credential mutations serialize reads and writes, refuse unreadable state, retain exclusion while a timed-out write finishes, and publish IDs/version only after confirmed changes. Native credential completion invalidates joined reads before OAuth token trust is rechecked. Cache refresh uses a connection epoch so a restarted daemon generation and delayed old reads cannot retain stale data. A definite unsupported or unavailable native mutation refuses an old-writer fallback; an unknown mutation result is never replayed. Quiet credential reads remain available through the shell fallback. Only Busy receives bounded native retry.

A successful OAuth response is retained privately before IMAP retirement. If credentials changed during refresh, one bounded quiet read may validate the exact source record or its exact known predecessor pair; generation validation and adoption share the entries lock. Pending responses cannot be used, offered or refreshed again until resolved. Failed/stale reads and ambiguous changed same-grant tuples retain one private response per account; a later existing read/recheck can resolve it, and a distinct new grant supersedes it. This retention is memory-only and may remain unresolved without later activity. Public credential cache clear detaches the obsolete epoch's refresh task while preserving the native unknown-result barrier.

Original OAuth grant chains reach the native guarded update unchanged. The daemon persists validated refreshed pairs through its quiet shared credential writer. A failed persistence attempt retains the pair privately in daemon memory for its existing backoff retry schedule; a restart or update can lose an unsaved rotated refresh token and require reauthentication. There is no shutdown flush or durable pending protocol. The renderer neither takes refreshed pairs nor writes credentials; the legacy `store_password` command and renderer token-take route are unregistered. Change server uses native `accounts.update`.

`accounts.save` is the shared native persistence boundary for strict creation/import and explicit existing-account patches. It reads current credentials, reserves the complete account ID/logical-key/legacy-preservation scope without waiting for partial admission, merges intent under the existing credential serializer, then commits only prepared secret-free metadata under the full account-list/version fence. Import acceptance and duplicate mapping are independent of unrelated legacy preservation changes. Explicit absence guards and the two supported field removals keep reconnect client stamps and JMAP logins coherent. Mutation replies contain metadata, IDs, versions and host-change status; credential reads remain explicit.

For an `ifAbsent` import batch whose actual create targets include retired IDs, native admission can return one exact `retiredIdsRefused` result with `effects: none` before credentials or metadata change. It does so only after complete pre-effect proof and excludes logical-key skips. The transfer adapter validates this exact result and remaps only those retired targets once, then retries the entire unchanged batch; generic Busy, malformed replies and unknown outcomes never authorize replay. Accepted IDs alone enter imported settings, while the full source mapping reaches imported config. This is same-process compatibility, not persisted lineage or full removal.

The daemon also holds a process-local account lifecycle registry seeded from an authoritative account-document listing under whole-store admission. An ID becomes Open only from an unambiguous listing or its bound native create's confirmed document completion; an actual confirmed document removal retires it. The shared credential writer and native account-document owners carry finite lifecycle authority through their real backend, document, finalizer and event children, including after a caller stops waiting. Original read stamps and finite publication permits are available for later mail-producer attachment. A private Closing claim blocks new authority and waits only for already admitted finite local publications. This first boundary does not yet cover all mail producers or implement full account removal, so a retired ID is an admission fence rather than proof of drained writers or erased data. An uncertain native create remains nonpublic until an explicit account-list refresh recovers its exact bound metadata from a fresh authoritative listing.

The next finite publication slice carries each account's original lifecycle stamp from sync, body fetch, provider listing, contact observation, key resolution and legacy import into the child that commits local state. Cache SQL, vault files, decrypted copies, attachment marks, JMAP UID ledgers, contacts, hoarder completion and eviction obtain short permits at their actual mutation. Network waits, IDLE sockets and key waits hold no lifetime permit; a child already admitted keeps its permit even if its caller stops waiting. Lifecycle refusal is distinct from an ordinary cache-policy skip. The one-time custody import waits for a successful bootstrap handoff, then its named OS thread owns one finite unscoped operation through every import unit and report. Named SQL units also retain their original account stamp; an unknown legacy cache rename uses only the unscoped owner. These fences cover the named local producer paths; the later compose, send, scheduled, draft and deleted-mail slice is described below, while cross-process and old-binary compatibility remain outside this process-local boundary.

Compose staging and receipt cleanup, scheduled row publication and due attempts, accepted sends, local draft copy-on-write, and deleted-message recovery now carry their original account stamps into the real publishing children. A short local permit covers each file, ledger, custody, bin, and receipt mutation. A finite operation permit covers transport and its surviving Sent append, recovery, landed, bookkeeping, and event children; scheduled attempts acquire it after prompt-capable preparation and keep terminal maybe-sent outcomes terminal without resending. Draft saves admit every account actually touched by requested, current, pending, prepared, and cleanup state. Provider-backed recovery keeps the same owner through JMAP UID ledger work and bin removal. A caller losing its reply does not release a child that still works. Closing refuses while an admitted child survives, and original-stamp checks reject a local publication prepared before retirement. These are process-local fences for the named paths; the complete account-removal route below uses their Closing drain, while cross-process writers and old binaries remain outside the guarantee.

Archive and bulk delete now admit their complete finite account scope before recording or launching work. Their actual custody, provider and bulk children retain the operation owner after a caller stops waiting. Restore and upload carry original account stamps into provider and disk children; finite migration, format conversion and import rehome runs keep their scoped or unscoped owner until the real runner finishes. Format journal adoption waits for a successful account bootstrap and the startup resume request, regardless of which becomes ready first. ZIP import reads one fresh authoritative account listing under short whole-store admission, owns every existing target through extraction and reserves new UUID targets before any file write. Each file uses its exact target stamp; unsafe account IDs cannot gain authority through path sanitization. New descriptors remain nonpublic in a process-local intent keyed by an opaque result reference. Complete ZIP metadata admission checks raw exact descriptors against that intent and uses one finite owner per reserved target under a complete lease. The real document child's confirmed MembershipDelta activates and consumes only those added targets, including after its caller disappears. Partial/unknown outcomes keep the intent private and the UI stops before settings or reload; restart loses it and fails closed. Cross-process retirement remains staged.

The in-process registry also covers per-record credential writers, the quiet refresh worker and legacy-preserving account primitives; whole-list mutations require exclusive admission. Reads do not acquire it. Backend and document tasks keep their native leases through actual finalization even after an RPC deadline or caller loss. Credential success followed by document failure remains an incomplete save with possible earlier effects, without rollback or replay. The matching shell/portable whole-blob mutation paths refuse, while read fallback remains. The legacy `store_password` command is unregistered; Change server uses native `accounts.update`. This does not fence another process or an old binary. Removal orchestration is native as described below.


`accounts.add/update` own native connection validation and saving for the normal add/edit workflows. The daemon uses a fresh coherent source, native defaults and timestamps, and the existing fresh IMAP, Graph or JMAP client. One 300-second reply budget contains at most 75 seconds for source/token resolution, 120 seconds for the provider probe and a reserved 90 seconds for saving; the shell waits 305 seconds. No account admission, credential writer or token flight spans a provider probe. A changed origin cannot reuse a stored secret without an explicit replacement. Submitted replacement credentials are tested directly, independent of the previous token cache, refresh flight and expiry.

After an omitted-token probe, a private source proof reaches the existing fresh credential mutation. It binds original account/context and the actual resolved token tuple while allowing an unambiguous distinct later refresh token from the same native grant chain. Same-refresh-token changes outside that proof require a fresh attempt. Explicit replacement instead binds its captured native preimage and does not depend on resolving the previous grant. These predicates run against the already-read current blob with complete legacy admission, adding no storage read. A refresh POST already sent remains owned through successful response retention and existing retirement/current-record validation even if its workflow waiter disappears; existing quiet persistence and exact acknowledgement retain ownership of adopted pairs. Pending results remain memory-only, with no durable journal or shutdown flush.

The current JavaScript workflows submit one native intent and publish only returned secret-free metadata. They retain view activation and alias scheduling after confirmed success. The DB adapter validates the finite success/classified-probe union and translates existing catalog keys while preserving error code, host and port. Malformed or unknown mutation completion keeps the existing uncertainty barrier, so retry cannot mint a second add identity or fall back to an old writer. Demo mode refuses these native workflows. Change server submits a full explicit password-IMAP replacement through `accounts.update`: the daemon checks the source, probes IMAP and then SMTP under the shared 120-second probe budget (with a separately clipped 15-second SMTP cap), and reserves 90 seconds for saving. Sparse edits, add, JMAP and Graph keep their prior probe rules. The dialog changes renderer state only after the native result, and a failed probe leaves the old endpoint and credentials intact.

`accounts.remove_local` is the sole local-account retirement route. It validates an exact account ID and the authorized configured vault root, obtains a fresh complete account listing and credential context, then holds a complete lease and a private Closing claim. Active operations return `{outcome:"busy",accountId,effects:"none"}` before effects; the local publication drain is bounded to two seconds without cancelling admitted children. The native 180-second deadline and shell 185-second wait bound the route. After the claim, it removes exact compose receipts first, then the account document, credentials, selected local mail/cache children and follow-up rows. Each started child retains claim custody through actual completion even if the RPC waiter disappears. A stage starts only while its deadline and waiter remain; failed or unknown effects retain Closing semantics and require explicit retry. Only settled work returns `{outcome:"complete",accountId}` and emits the final account change. A fresh authoritative absent-ID proof permits cleanup of residual local state after restart without opening the ID. Settings keeps membership, billing and follow-up projections on Busy/incomplete; it changes them only after the exact complete result. The renderer's old direct file/credential deletion path and permissive clear-all fallback are retired. This process-local fence does not cover another process, an old binary or arbitrary external filesystem writers.

After local cleanup, the same Closing claim owns native IDLE unwatch and any pooled IMAP logout through actual completion. The removal captures the target's connection context before deleting records and reserves finite equivalent logical keys for the pool's existing `email-host:port` encoding, so a late account cannot claim an equivalent resource while that lease lives. A known shared survivor keeps its pooled sessions; an absent retry with no context completes only when both idle-session maps are empty, while unattributable sessions remain and report incomplete. A trailing `-` key with a possible empty-host provider fallback is not treated as exclusive while matching sessions exist. The short filesystem deletion exclusion ends before IDLE or network work. Credential mutation waits keep their existing 5-second admission and 20-second read/write ceilings, clipped to the remaining removal deadline; a started write still settles under its owner before that owner releases custody.

Local removal captures the configured root's physical identity (including Windows volume and file ID), exact child entry spelling and selected child identities before receipt retirement, then rechecks them under the vault gate at deletion. A case alias or a different object at the same pathname cannot authorize another account's tree, legacy mailbox cache or selected sidecar. A legacy sidecar is eligible only when an exact account-bound custody mailbox projection names it and the current known account IDs provide no sibling collision; unprojected or ambiguous sidecars stay in place with an incomplete `headerCache` residual. For the actual selected filesystem deletion units, a private temporary whole-store admission exclusion ignores only the removal's exact retained lease and refuses while any other lease lives. Under that exclusion, removal reads a fresh complete account document, quiet credential snapshot, custody IDs and configured-root evidence before taking vault/cache locks; it retains the exclusion through the real unlink child and releases it before custody and follow-up bookkeeping. This is attribution against current authoritative state, not proof of exclusive historical ownership of a lossy legacy filename. Missing proof or a lost waiter before unlink preserves the selected files and requires explicit retry.


**Stage 2 account and credential ownership.** Account add, update, and local
removal are native workflows. `accounts.remove_local` alone retires a local
account; `accounts.remove` remains an internal AccountDoc operation and has no
public RPC. `accounts.replace_all` remains public only for nonretiring updates.
The renderer does not disconnect IMAP while completing removal: native
retirement decides whether a pooled session is shared. The daemon quietly
persists validated OAuth refresh pairs without a main window and emits
secret-free completion events. The renderer uses a fresh credential read only
to project a same-grant access token into its visible account copy; it neither
takes nor writes refreshed pairs. `oauth2.take_refreshed` and
`oauth2.credentials_changed` have no public routes. Native credential
completion still invalidates token trust and wakes waiting jobs. Ordinary
account writes and malformed legacy-entry cleanup use native account and
per-record credential workflows. Only `get_credentials` remains as a quiet
shell read fallback; the shell's `store_credentials` and `store_password`
commands are unregistered. Old, unavailable, or uncertain daemon mutations
never fall back to a renderer or whole-blob writer. An unsaved rotation can
still be lost when daemon memory ends and may require signing in again.

The daemon owns:

- IMAP, SMTP, Microsoft Graph, JMAP, OAuth2, and DNS mail-health operations, including sync, IDLE, and, as of Phase 5, every interactive one-shot call the UI makes too (fetch, send, folder management, connection tests, autodiscovery). There is no longer a separate app-side IMAP/SMTP/Graph/JMAP/OAuth2 client; `sync_engine.rs`'s calls and the RPC-routed interactive calls both go through the same `mailvault_core` functions and, for IMAP, the same pooled connections.
- Keychain credential reads for sync/IDLE (`resolve_account_credentials`, Phase 5 Task 5.1), with `get_credentials` retained as a quiet shell read fallback while native workflows own account and credential writes.
- **OAuth2 access tokens** (`oauth_tokens.rs`). The daemon owns token freshness: `oauth_tokens::access_token(account_id)` returns a token good for at least five minutes, refreshing it first with the stored record's own grant (refresh token, provider, Google client stamp `oauth2ClientId`, tenant, Graph scopes for a Graph account), one refresh per account at a time. No expiry on record means no refresh, and an account with no refresh token keeps its stored token, as the app did. `server::handle_request` puts the daemon's token into every request before routing it (`inject`): each OAuth2 account the params carry (`account`, `accountJson`, `sourceAccount`, `destAccount`, as an object or JSON text, by its `id` or the request's `accountId`, only when the stored record has the same address) and `accessToken` on a `graph_*` call naming `accountId`. A token the app sent survives only where the daemon has none (an account not saved yet) or the sent one carries a later expiry (Reconnect testing its new sign-in). A `graph_*` call naming its account when the daemon has no token for it is answered `E_OAUTH_SIGN_IN_NEEDED` or `E_OAUTH_KEYCHAIN_UNAVAILABLE` (catalog keys; the app's `oauthErrorState` shows the sign-in-required or credentials-unavailable state). A response that is a sign-in refusal (`XOAUTH2 auth failed`, a Graph 401) marks that token so its next use refreshes, but after a refusal-driven refresh no further refusal asks for one for 60 s, doubling to 10 minutes while refusals continue (a server that refuses even a valid token would otherwise cost a token POST per request); a request that goes through resets the doubling. Workers resolve through `oauth_tokens::resolve` (quiet or guarded, as their keychain reads were), the IDLE watcher renews its slot's token at every connect and sync, and Archive & delete jobs lease the daemon's token (`abd.set_token` stays as a fallback; a job parked for a token is woken by native credential completion). Tokens live in memory per daemon (`DaemonState.tokens`). One coalesced native worker persists validated unsaved refreshed pairs through the existing credential serializer, with immediate quiet admission, noninteractive backend reads and writes, fresh full-grant and expiry guards, and exact access/refresh/expiry acknowledgement at the current write generation. It never saves private completed responses before existing retirement and current-record validation adopt them, holds no token or account-flight lock across storage I/O, and only briefly tries the flight for acknowledgement. Failed storage attempts retain the pair in memory and retry with capped backoff; a new provider response, credential change or keychain recovery wakes the same worker. Empty eligible state does not poll storage. Main requests cooperative stop without aborting an admitted credential operation or extending the existing shutdown grace. Failed or unfinished pairs can still be lost at process exit; there is no durable token journal or shutdown-flush guarantee. No renderer take/save compatibility path remains; native guarded pair updates emit credential-change events only on an actual change. Ordinary acknowledgement requires the rotated refresh token too. Every successful credential write invalidates cached trust before a fresh stored-record read. The record and the held entry are reconciled on that read. A grant is its refresh-token chain (the record's refresh token and every one a refresh rotated in) plus the provider, Google client, custom client, tenant and transport: a record of another grant (a Reconnect, a switch of the Google sign-in app, IMAP to Graph) replaces the held entry and drops its unsaved pair whatever the expiries say; within one grant the later expiry wins, so a stale whole-blob write never rolls a refreshed token back. An offered pair names its grant by fingerprint (`chain`, SHA-256 of each refresh token with the client, transport, tenant and custom client); chain-bearing pair mutations require that stored grant and cannot shorten a newer stored numeric expiry. Full-record Save callers use the native account-workflow admission. A refresh that fails keeps a still-valid token; once it has expired the caller gets the expired token as a fallback, so the server's own refusal (the app's "sign in again" state) reaches the user as before, and no new attempt is made for 30 s (no answer) or 10 min (refused, unless a new sign-in replaces the grant). No token reaches a log line, an event or an error. The interactive sign-in (`oauth2_auth_url`, `oauth2_exchange`) is unchanged; `oauth2_refresh` stays routed for one release with no caller in the app.
- **The keychain gate** (`credentials.rs`, classifier in `mailvault_core::keychain`). A daemon keychain read that fails for a reason unlocking would fix (locked, a refused or cancelled prompt, or no answer within the read's clock) blocks that item; the next read of the same item that answers, even with "nothing stored", clears it, and the gate is blocked while any item is. Each item has at most one blocking read out at a time, which later callers join rather than start again, so a read parked on an unanswered prompt cannot multiply into a thread per retry. The daemon does not wait to be asked: a watcher task reads the blob once at start, and while the gate is blocked reads every blocked item again every 5 seconds, sleeping while it is clear; the clear wakes the scheduled-send worker. macOS's password prompt shows once per blocked episode: only a read that finds the gate clear, or `keychain.retry`, may raise it, and every other read while blocked runs with `SecKeychainSetUserInteractionAllowed` off and fails fast. That switch is process-wide, so one lock spans switch, read and restore, and a single-flight read never lets a quiet probe answer an interactive retry. Each blocked/clear flip is one `keychain-status` event, and `keychain.status` answers the current state for an app that connects later. On macOS the app shows a corner card for as long as the gate is blocked, with no dismiss; it stands in for the sidebar's connection notice and the keychain toast while it shows, and every third click past it starts its Unlock. Its Unlock is one `keychain.retry`, which first unlocks the default keychain with macOS's own dialog when `SecKeychainGetStatus` says it is locked (after a cancelled prompt macOS does not prompt that process again for item reads, so this is the only way back to a prompt), then reads (or joins the read already out for) both daemon items under a 120s clock and wakes the scheduled-send worker when they answer. The app itself never prompts: `get_credentials` reads with interaction off, so a locked keychain answers "unavailable" and the card covers it. Every blocked-to-clear flip, whatever caused it, runs the app's `retryKeychainAccess` once so its own "Password missing" state recovers and `sync.watch` registers again. While blocked, scheduled sends stay queued without spending a try, like offline, and the worker looks again at most every 5 minutes on its own. When a blocking transition reaches no receiver, the daemon posts a banner itself through UNUserNotificationCenter (at most once per 30 minutes); that relies on `NSBundle.mainBundle` resolving to `MailVault.app` from `Contents/MacOS` and is unproven until a signed build shows it.
- **The connectivity gate** (`netgate.rs`, probe in `mailvault_core::net`). A connect-shaped failure only raises a suspicion; the probe decides. It dials three public resolvers on port 53 and two of them on 443 as well, plus the mail servers every sync registers (`register_host`: deduplicated, at most 32, on their own ports, a host on this computer or the local network refused because it answers without the internet); any one answering means online. A failed sync result and a failed `imap_test_connection`/`smtp_test_connection` carry an `errorCode` from `net::classify_connection_error`, which the app words its message by. A failed test is a `success:false` result with the host and port, not an RPC error, so the code reaches the app; `api.js` turns it back into a rejection. A passing `imap_test_connection` answers the host, port, INBOX's message count (a read-only EXAMINE on the same session, null when it fails, takes over 5s, or the test needed its retry) and `fromAddress`; `addAccount` returns them beside the saved account, never on it, for the add-account form to show.

- **Learned classification rules.** `learning.*` (`handlers/learning.rs`, logic in `mailvault_core::learning`) records a user's category correction and learns a domain, address or subject rule from it, and lists, edits, deletes, counts, exports (anonymized: no addresses) and imports rules. Each account's rules and corrections are `<app_dir>/ai-feedback/<accountId>.json`, written under one lock; `classification_worker` reads the rules from the same file. The stored JSON shape (`type`, `pattern.fromDomain`/`fromAddress`/`subjectContains`/`bodyContains`, camelCase) is canonical: `learning` keeps rules as raw JSON for fixture fidelity, and `mailvault_core::learned_rules` is the one typed reading of it the classifier uses (matching, normalization, refusal of blank or short patterns, precedence). With no custody entry it writes the entry the app built from its row, which the app offers only for a message the vault holds. The app keeps the account resolution and the repaint of its rows.

The gate is taken per write, not around the run: each vault write takes the vault registry's mailbox lock and then the gate, and a mirror write takes a gate call of its own outside that lock. The mirror pre-sync takes neither, so a copy off a slow external drive cannot block the folder's reads; when it copied anything into the vault it invalidates that folder in the registry once, and the folder's next read lists it again. Before copying, it replays the folder's `.import-rehome.json` ledger on both sides (`mailvault_core::import_rehome`): old mbox imports that a folder read moved out of the server's uid range, in a background pass run once per folder, would otherwise come back from the mirror at their old uid. The same pass sets aside (into `orphaned/`, through the same ledger) an import copy of a message the server now lists, the copy a file imported into the folders and then restored to the server leaves behind; the upload job runs it for every folder it touched once its sync is done, and it never touches a vault-only folder. A run is fire-and-forget (`backup_run_account` returns a `runId`; progress and the outcome arrive as `backup-progress` events) with cancellation held per account in `DaemonState.backup_runs`. - **Compose send.** The daemon runs the send in two RPCs (`handlers/compose.rs`, row shape in `mailvault_core::compose`). `compose.stage` builds the MIME (`smtp::build_mime`), writes the copy into the account's Sent folder in the vault (flags `draft`,`seen`, the first free uid from now in seconds, `vault_files::free_local_uid`) and indexes it as a `local_draft` row; it is the one fatal step (`E_COMPOSE_BUILD:`, `E_COMPOSE_STAGE:`). `compose.send` sends the staged copy's own bytes, read back from the vault by uid (`smtp::send_staged` through `send_logged`), so every attempt is the copy the user keeps; only a copy the vault cannot prove as its own exact bytes is rebuilt under the staged id, and its sent copy then goes under a new uid: the staged uid is never rewritten or removed unless it held this message's own copy (there is no in-memory MIME cache between the two RPCs). Once the transport took the message nothing fails the call: it cancels the edited scheduled row the send replaces (`scheduled-send` event), records the follow-up reminder (`follow_up_worker::record_after_send`, not on Graph), rewrites the copy as sent (`archived`,`seen`, a `local_sent` row) and reports the server's Sent copy (`report_sent_copy`); once the server holds one, the daemon removes the staged copy before `send-server-append-complete` goes out (the event also names `vaultAccountId`, `stagedUid`, `localMailbox`). The app (`services/composeSend.js`) keeps what reads app state: the payload from the editor's HTML, the Sent folder (`resolveSentMailboxForAccount`), the fresh token, the Premium gate and own addresses, the undo-send and outbox queue (`composeSlice.js`), and the list's optimistic row, built from the row the daemon answers. It stages once per queued send and passes the same uid and Message-ID to every attempt.
  Native compose ownership uses normal `local_draft`/`local_sent` custody plus small typed receipts in the existing `app.db` meta table. Each receipt binds the exact account, local mailbox, UID, normalized Message-ID and raw-byte SHA-256; different byte digests at one tuple remain distinct and an unbound ambiguous original refuses. Stage writes native evidence before replying where storage permits; after-send records the actual replacement UID. Reads and mutations revalidate current bytes and custody under the existing mailbox lock and vault gate. Cleanup persists cleaned evidence before destroying the last custody entry, and a cleaned read proves the old exact local copy absent only after checking actual storage. Any occupied UID conflicts with cleaned evidence, even when the bytes are identical; a crash between cleaned persistence and deletion therefore remains unresolved. Cleanup follows the actual local byte digest, including when Graph adds Bcc to its transport bytes. Neither local proof nor its pseudo UID authorizes a server, mirror or scheduled-queue operation. Receipt persistence failure never converts transmitted mail into a failed send; ordinary custody remains usable and otherwise missing proof refuses. Future native pending work must retain the complete exact proof before conditional receipt retirement; a separate native-only reader revalidates that retained proof after restart without recreating the receipt. The explicit `compose.receipts.remove_account` route retires one account's evidence before the shared account deletion entrypoint mutates keychain, account files or Maildir; cleanup failure stops that removal attempt. Ordinary cache invalidation leaves receipts intact. Later account-file failure can conservatively lose optional receipt proof, and this narrow cleanup does not fence already running account work.
- **Sending from a Graph account.** An Outlook.com account signed in with Microsoft (`ImapConfig::uses_graph`, the app's `oauth2Transport === 'graph'`) holds a token with Graph scopes only, which SMTP refuses. `smtp::send_built` (compose) and `smtp::send_raw` (scheduled) both branch at their top to `send_via_graph`, before any SMTP host is asked for: the same MIME goes to `POST /me/sendMail` base64-encoded (`GraphClient::send_mime`, purpose "send", named for the account), with a `Bcc:` header written into it from the compose fields or the frozen envelope when the bytes lack one, because Graph takes no envelope, only the MIME. Graph files its own Sent Items copy, so the result says `server_saved_sent` and nothing is APPENDed: `smtp_send_email` and `compose.send` emit `send-server-append-complete` (`ok: true`, the message's `messageIdHeader`) right after the 202, and `compose.send` drops its staged local copy first; it does not wait to see the copy in Sent Items, since Exchange may rewrite the Message-ID. A send is never retried inside (a timeout after Graph took the message would send it twice), and a request that left without an answer (a timeout or a dropped connection: `SendMailError::Transport` with `maybe_sent`, anything but an error reqwest reports as a failed connect; the send's client, `GraphClient::for_send`, gives up a connect, TCP and TLS, after 20 s, so a connect that never opens fails as a connect well inside the request's own timeout and, like any send that never left, is not terminal) says the message may have gone out and is terminal: the scheduled worker checks terminal errors before its network probe, so neither the retry ladder nor the offline requeue can send it a second time. A body over Graph's 4 MB request cap is refused before any request, and refusals are worded in Graph's terms (sign in again, refused to send as, throttled, server fault); `smtp::is_terminal_send_error` is the one list of which of them end a scheduled row.
- **JMAP accounts: one client, one interception point.** A JMAP account (`ImapConfig::uses_jmap`, RFC 8620 core and RFC 8621 mail) is a first-class account kind with no IMAP or SMTP server behind it. `mailvault_core::jmap` holds `JmapClient`, one session over three tracked HTTP clients (reqwest through `net_activity::http_client_with`, every request sent through `Tracked::send` so it shows in Network Activity as the account's): API (method calls and the session fetch, 60 s total, redirects off), transfer (blob upload and download, a read-idle timeout, an upload also bounded by its bytes) and push (the EventSource stream, read-idle only). Credentials (`JmapAuth`: Basic username and password, or a Bearer API token) go only to https URLs, or to the loopback `MAILVAULT_JMAP_BASE` override in debug builds; the session URL and its redirects must stay on the host the user saw. There is no per-feature JMAP RPC surface: the app keeps calling the `imap_*` RPCs, and `handlers::jmap_bridge::intercept` is the one place they are answered over JMAP. `handlers::imap::route` (and `handlers::smtp::route` for `smtp_test_connection`) call it before their own `match`; it answers when the `account` param is a JMAP account and returns `None` otherwise, so an IMAP account never reaches it. Every answer has the JSON shape of the IMAP arm it stands in for, and an `imap_*` RPC the bridge cannot answer is `E_JMAP_UNSUPPORTED`, never an IMAP login with the account's token. Safety net: `imap::pool::refuse_jmap` is the first check of every `ImapPool` session-opening entry, so a path that forgot to branch on `uses_jmap()` fails with the stable code `E_JMAP_NOT_IMAP` instead of sending the JMAP credential to `imapHost`; the daemon logs every `E_JMAP_NOT_IMAP` refusal that comes back from an RPC (`server.rs` `handle_request`, one `[jmap] <method>: ...` warn line), and the e2e battery checks both that log and the app console for the code and expects none. `JmapSessions` (`jmap_sessions.rs`) keeps one connected client per account, its mailbox path to id map, and the ids this daemon put on the server itself, which do not count as arrivals.
  - Account-level sync: JMAP reports changes per account (`Email/changes`), not per mailbox, so `sync_jmap` applies one delta to every tracked mailbox under one account-wide lock in the engine's `sync_locks`, and `delta_only` runs it first for the bridge's status RPCs so `uidNext` and `highestModseq` are current. The bookkeeping (`JmapMeta`) lives in custody.db `meta` rows only: the account's Email state string, a per-mailbox monotonic counter that is the status RPC's `highestModseq`, and a capped per-mailbox flag log. A cold run (no stored state, or `cannotCalculateChanges`) rebuilds header rows from the newest page and announces nothing; it never deletes an `.eml`. Every mailbox a run touched is published with `note_change`, and the app raises banners from that feed only.
  - The uid ledger: a JMAP email has no uid, so `graph_ledger::allocate` issues one per (mailbox, email id) the first time a listing sees the pair and records it in `jmap_id_map.json` beside the mailbox's header sidecars (the Graph ledger's twin, `graph_id_map.json`; every clear path keeps both). Rows are never removed: a uid, once issued, belongs to that email for good, because a dropped row would hand a live uid to a second message and an op-journal replay would then delete the wrong one. Moves, label removals and destroys remove header rows only. `uid_to_id` re-checks the email's `mailboxIds` and answers `E_UID_GONE:` like the IMAP arms; a re-added label gets its old uid back. `uidValidity` is always 1.
  - The label-semantics delete rule: JMAP mail is label-like and `Email/set destroy` removes an email from every mailbox, so a delete is a label change unless nothing else holds the email. `jmap::ops::remove_from` is the one implementation, used by the bridge, the archive and delete engine's `JmapOps` (which rides the engine's id-based Graph path), bulk delete, snooze and the workers. Delete from X when the email also sits in a mailbox other than X and Trash: drop only the X label. Delete otherwise: move to Trash alone (no Trash mailbox is refused, never turned into a destroy). Permanent delete or expunge when X and Trash are all that holds it: destroy. Permanent delete otherwise: drop the X label (and the Trash label). Every delete is captured in the deleted bin first, as for IMAP.
  - Push: `jmap_push.rs` runs one task per JMAP account in the same task map as the IDLE watchers (so `sync.unwatch`, `sync.watch_status` and shutdown cover it), reading the session's EventSource (`types=Email,Mailbox`, pings every 30 s). After every connect the INBOX sync runs, since changes made while no stream was open raise no event; a `state` event whose Email state is not the stored one runs one account-wide sync. No bytes for `dead_after` (2 x ping + 5 s) is a dead stream, and it reconnects after 1 s, 2 s, 4 s, up to 5 min. A stream counts as healthy only if it delivered an event and then lived at least `dead_after`: a server that sends its initial state and hangs up must not reset the failure count, or the loop would reconnect and run a full INBOX sync every second and never fall back. Poll fallback: after 3 failures in a row the account syncs every 2 min and retries the stream every 10 min; a session without `eventSourceUrl` only polls. Inbox arrivals get their bodies cached as an IDLE watcher's do (blob download); other mailboxes wake the hoarder.
  - Sending: `smtp::send_built` and `smtp::send_raw` branch at their top to `send_via_jmap`, before any SMTP host is asked for (the Graph pattern). It picks the server's `Identity` for the From address (none: `E_JMAP_NO_IDENTITY` before anything is uploaded), uploads the MIME, `Email/import`s it into Drafts with `$draft`, and submits it with `EmailSubmission/set`, whose `onSuccessUpdateEmail` moves it to Sent and drops `$draft`. The server takes recipients from the headers (Bcc is written into the bytes, as for Graph) and files the Sent copy, so nothing is APPENDed. A refused submission destroys the imported copy; a submission with no readable answer may have gone out and is terminal, never retried. `aliases.discover` lists a JMAP account's identities, so send-as addresses come from the server.
  - Discovery and the host trust rule: `mailvault_core::jmap::discover` runs beside the IMAP autoconfig (`dns::resolve_email_settings_with`) with four concurrent probes bounded to 4 s, none carrying credentials: the Fastmail preset (the domain, or an MX at Fastmail: messagingengine.com or fastmail.com), `https://<domain>/.well-known/jmap`, `https://jmap.<domain>/.well-known/jmap`, and the SRV record `_jmap._tcp.<domain>`; the winner is picked by that priority. A probe follows at most 5 redirects, https only, and the session URL handed back is the final URL after redirects. A session host outside the address's own domain (an SRV target or a redirect) is never trusted silently: `host_is_trusted` compares hostnames only (the domain, its subdomains, and Fastmail's API host for Fastmail's own domains; the Fastmail preset, reached by domain or by MX, is trusted by definition), and anything else sets `needs_host_confirmation`, which the account modal and Change Server must satisfy (in their handlers, not only on the button) before the first authenticated request.
- **Scheduled send.** `scheduled_send_worker.rs` owns the outbox: the complete MIME is frozen into the vault's `Scheduled` mailbox at schedule time and the row in `app.db` points at it, `.eml` first so a row can never name a file that was never written. The worker runs a catch-up pass at start (the daemon dies with the app unless always-on is enabled, so "already due" is the normal case, never an error), then sleeps to the next `fire_at`. Sending replays the frozen bytes through `mailvault_core::smtp::send_raw`; `send_built` cannot, because lettre re-derives envelope and body from its own `Message`. Before it sends, the worker takes the account's token from `oauth_tokens` (refreshed within five minutes of its expiry with the record's own provider, client and scopes). A refresh that fails leaves the stored token while it is still valid; once that has expired nothing is sent: a refusal (the provider said no, or a Google client this build cannot pair) ends the row asking for a new sign-in (`smtp::SIGN_IN_AGAIN`), and no usable answer always runs the network probe (`NetGate::confirm_online`, not the wording-based `note_failure`, so the outcome never hangs on how the error is worded): offline leaves the row queued with its try given back, online takes the retry ladder. Offline is neither transient nor terminal: the row stays queued and the attempt is released. A row is claimed in-process for the duration of a send so `scheduled.send_now`, which skips the due-time gate, cannot dial out alongside the worker, and a send re-reads its row under that claim, so a cancel, edit or reschedule that landed after the due batch was read beats the stale copy. Editing a scheduled email reads the frozen `.eml` back out of the vault (the server never had it) and leaves the row queued until the edit replaces it: `scheduled.update` rebuilds the `.eml` in place under the same claim and refuses a row that is claimed or no longer `queued`/`failed` (`E_SCHEDULED_NOT_EDITABLE`), and `scheduled.cancel` refuses a claimed, `sending` or `sent` row the same way, so a message that went out is never relabelled cancelled; an edit sent immediately cancels the row only once the send has gone out. Compose preselects the recipient's zone from `scheduled.suggest_tz`, which answers facts, not a zone: the UTC offset of the newest cached Date header from that address (custody.db) and the zone last scheduled to them (app.db). The app picks the zone, because `Intl` holds the DST rules.
- **Snooze.** A snooze is a server-side move, so every client sees it: the app moves the message into the folder `snooze.ensure_folder` resolves (a plain `Snoozed`, created on first use) through its own move workflow, then records one `app.db` row per moved message (`snooze.create`) keyed by the Message-ID, with the move's COPYUID only as a hint. A message whose row cannot be written is moved back. `snooze_worker.rs` has the scheduled-send shape (catch-up pass at start, sleep to the next wake): it finds the message in Snoozed by Message-ID, clears `\Seen` there, moves it back, then syncs the destination and records it through `SyncEngine::note_change` like an IDLE arrival, which is what produces the new-mail notification. Not found means the user moved it elsewhere and ends the row quietly; offline or a blocked keychain waits without counting a try. `snooze.cancel` (unsnooze now, and the undo) is the same wake under the same lock. **Local mode**: when the server answers and will not host the folder (both CREATEs refused, `ALREADYEXISTS` for a name LIST does not show, a `BAD`, no hierarchy delimiter), `snooze.ensure_folder` fails with `E_SNOOZE_FOLDER_REFUSED:` (`mailvault_core::imap::SNOOZE_FOLDER_REFUSED`; a connection, LIST or auth failure stays a plain error, shown with its reason). The app then moves nothing and records rows with an empty `snoozed_mailbox`; `deriveDisplayRows` holds those messages (account, folder, Message-ID) out of the list and the inbox badge until the row wakes, re-deriving whenever the snooze rows change. The wake finds the message in its own folder, clears `\Seen` and moves nothing; that sync sees no arrival, so the worker's `snooze` event carries `woke: true` and the app raises the notification for that message from its header cache. Undo only ends the row (`woke: false`, no unread, no banner). Other clients still show the message in the inbox. IMAP only: the daemon stores no OAuth token and keeps none past the work that needed it (a scheduled send's in-memory renewal lasts that one send, and the Archive & delete job's in-memory lease the job's length), so the snooze worker has no Graph token to wake a message with, and the app does not offer snooze on a Graph account.
- **Follow-up reminders.** "Remind me if no reply" (Premium, IMAP only) is opted into per send in compose (1 day, 3 days, 1 week). After an immediate send succeeds, `compose.send` records one `app.db` row (`follow_up_worker::record_after_send`, as a scheduled send does) keyed on the Message-ID the message was staged with, never the SMTP reply's queue id, with every address the send was the user's under (its From, the login, the default From, the aliases); a retried send inserts nothing twice (`UNIQUE(account_id, message_id)`). A scheduled send carries `remindDays` and those addresses in its stored envelope and `scheduled_send_worker` records the row once the frozen bytes go out, keyed on the Message-ID in them. `follow_up_worker.rs` has the snooze shape (catch-up pass at start, sleep to the next `remind_at`, offline and a locked keychain wait without counting a try). At the due time it looks in two places and either answers: first the header cache, read once a pass for every due reminder of an account (no network: every cached folder but Sent and Drafts, by role or by whole-word name, one bounded page per custody lock with a foreground yield between pages; a row from an own address, folded like the app's `normalizeEmailIdentity`, marked `autoReply` (Auto-Submitted, X-Autoreply, X-Autorespond or X-Auto-Response-Suppress, which every header fetch now writes, "" for none) or titled like an automatic reply in any of the app's languages is no answer; the answer is Hit, Miss, or Unknown when the cache cannot be read or holds nothing for the account), then the server: `UID SEARCH` (In-Reply-To or References names the id, `NOT HEADER` for the same four fields, asked again without them where a server refuses them) in INBOX and the special-use `\All`, `\Archive` and `\Trash` folders that exist, a hit counting once a FETCH of its From shows it is not an own address (`NOT FROM` cannot fold addresses). A refused INBOX, or a refusal the server marks temporary ([UNAVAILABLE], [SERVERBUG], [INUSE], [LIMIT], [EXPUNGEISSUED], "Server Unavailable"), is a try to repeat; another folder or criteria refused is passed over, and with every search refused only a cache Miss settles "no reply" (Unknown tries again; offline still waits). A reply ends the row (`replied`); none, it finds the Sent copy by Message-ID (the folder the app named, then the server's `\Sent` when that one refuses) and the row goes `due` with that folder and uid, or `gone` when no Sent copy is left. Nothing is moved or flagged on the server. The `follow-up` event carries each state change. The app (`stores/followUpStore.js`) pins each `due` row above the INBOX and All inboxes lists (`components/FollowUpPinnedRows.jsx`), never as a row of the list: a list row is acted on by its (account, folder, uid), and the reminder's is the Sent copy's, which the bulk ranges, select-all, keyboard delete and j/k would all reach. A pinned row opens the Sent message as the Sent folder does (its reader actions act on that message) and marks the reminder read (`follow_up.mark_seen`); its own x dismisses it (`follow_up.dismiss`). An unread reminder counts in the inbox badge, and the app notifies once (`follow_up.mark_announced`). Graph accounts are not offered it: the daemon has no Graph token to search with.
- **The deleted-mail bin.** Every delete is recorded first: a row in `app.db` (`deleted_messages`, schema v7: account, folder, uid, Message-ID, flags, the list row, `deleted_at`, the Trash folder and uid the delete moved it to, and `has_eml`) and, when the bytes are kept, `<app_data_dir>/deleted/<id>.eml`. `imap_delete_email`, `bulk_delete_emails` (five at a time, background lane), `graph_delete_message` (when the app names the account, folder and uid) and `maildir_delete` with `bin: true` (a local-only message) capture before anything is removed (`handlers::deleted::capture`). The bytes come from the vault or in-memory copy (the original, never a decrypted copy). Only a permanent delete downloads them when nothing local holds them, without writing a vault cache copy: a move to Trash with no local copy is recorded byte-less, since Trash holds it and a bulk delete must not become a bulk download (a byte-less row needs its Message-ID, or nothing is recorded). A Graph delete keeps local bytes only, because the daemon could never fetch the Deleted Items copy back. A permanent IMAP delete, or a local-only one, that cannot be captured is refused (`E_BIN_CAPTURE:`, which the app shows as the catalog's `errors.E_BIN_CAPTURE`), because the bin would be its only copy; a bulk run counts it as an error and leaves it on the server. A failed move to Trash drops the capture it made, a failed permanent delete keeps it (its EXPUNGE may have landed with the reply lost), and a retry or replay finds the one already made, even when the server no longer holds the message. `bin: false` opts out: a purge of every copy, archive-and-delete and cleanup rules (their vault copies are verified first). Once a bulk delete finishes, the daemon takes the uids the server actually lost out of the header cache (the app's own `removedUids` write, so `appRemovedSinceSync` keeps the list complete) and stamps `serverDeleted` on their custody entries, so a reopened folder does not list them as plain archived mail; a uid that failed to delete is neither pruned nor stamped. The bin sits beside `app.db`, never in the vault, so no folder list, vault walk, header cache, search index, count, unified view or backup ever sees it, and the daemon needs no file entitlement for it. `deleted.recover` puts a message back on the server (moved back out of the recorded Trash folder when a Message-ID search still finds it there, else APPENDed with its flags to the folder it left, and a kept vault copy rebound to the new uid; a byte-less row gone from Trash answers `deletedBin.goneFromTrash`) or into the vault as a kept copy custody marks `serverDeleted` (a byte-less row's bytes are read from the Trash copy then); `deleted.discard` removes it; `deleted.list` answers newest first. An hourly task (and every list) purges what is older than `deletedRetentionDays` from the settings file (1 by default, at most 30); unreadable settings purge nothing. Graph accounts recover locally only: the daemon keeps no Graph token to recover with (a running Archive & delete job holds one the app pushed, and a scheduled send renews one for that send alone, both in memory). In the app, a permanent delete with a bin copy gets an undo slot that recovers it, an undo that moves a message back out of Trash discards its bin copy, and Cmd+Z (Ctrl+Z off a Mac) runs the undo slot while it holds something and otherwise recovers the last delete's bin copies (`undoLastAction`). Settings > Storage > Deleted emails renders the list and the retention.
- **Lifecycle messages.** MailVault's short notes about Premium (`trial-ending`, `checkout-left`, `plan-ended`, `free-nudge`) are decided and remembered by the daemon (`mailvault_core::lifecycle_mail`, `handlers/lifecycle.rs`), never composed or timed by the app. The app calls `lifecycle.sync {state}` on launch, on a window focus after ten minutes, and whenever billing, onboarding or the on/off switch changes, handing over only the four facts the decision reads (`lifecycleMessages`, `onboardingComplete`, `lifecycleCheckoutAt`, and `billingProfile`'s `premiumAccess`, `hasSubscription`, `status`, `currentPeriodEnd`), not a read of the settings file: the app persists settings on its own schedule and a file that has not caught up with a billing refresh would miss it. `evaluate` delivers at most one message per call and never within a day of the last one; each is keyed to its occasion (`trial-ending:<day of the trial end>`, `checkout-left:<checkout time>`, `plan-ended:<day of the end>`, `free-nudge` once ever), so a dismissed message is kept on file and never delivered again. `free-nudge` counts four days from the first sync that saw a finished onboarding and no subscription (`freeSinceMs`, stamped by the daemon, so users from before this feature are counted from their first launch of it). State is `<app_dir>/lifecycle.json`, written atomically, a damaged file reading as empty. Nothing is sent: the messages are rows the app pins above the INBOX and All inboxes lists (`components/LifecyclePinnedRows.jsx`, never rows of the list, for the reason follow-up reminders are not) and opens in the reader (`components/LifecycleMessageView.jsx`, text from the catalog keys `lifecycle.*`); they are not counted in the inbox badge. The App Store build never calls the daemon for them. The same four kinds are what a later server-side email would send.
- **On-demand mirror copy (Archive, Back up & Delete).** A plain archive writes only the vault; a whole-account backup run is the other thing that fills the backup drive. `backup_copy_uids` (`mailvault_core::backup::copy_uids_to_mirror`, `copy_uids_to_mirror_listed` with a caller-owned `MirrorListing` so a batching caller reads the drive folder once) copies chosen vault files onto the mirror under their own Maildir names, one atomic temp-dotfile-and-rename unit per file, never overwriting a different message, and then checks every drive copy against the vault file (same length and Message-ID) before reporting it `verified`. A fresh drive copy is written durably (temp dotfile, `sync_all`, rename, folder sync where the filesystem supports it), since a server delete rests on it; the Archive & delete job passes its own vault listing (`copy_uids_to_mirror_from`), so no batch lists the vault folder. It reads the vault and writes only the mirror, so it takes no vault lock; the daemon handler runs it on the blocking pool behind the read-side vault gate, and the shell forwards it like the other mirror commands (bookmark resolved and held for the call). `BulkOperationManager`'s `archive_backup_delete` runs archive, vault verify, `backup_copy_uids` in batches of 100, then a permanent `bulk_delete_emails` (`bin: false`) of only the uids verified in both places; a drive that cannot be reached or a copy that does not match keeps those uids on the server and the result says why. The option is Premium (as is the bulk Archive & Delete) and needs a backup folder set.
- **Archive & delete jobs.** "Archive, back up & delete from server" and "Archive & delete from server" (Settings > Backup & Restore, Premium, app-checked only: a lapse never stops a running job, which was paid for at start and verifies every delete anyway) save a chosen scope of one account, folders plus dates, into the vault (and, in backup mode, onto the backup drive) and then delete it from the server. The engine is generic over a server-ops trait and a local-store trait and lives in `mailvault_core::abd` (state and plan types, planning, the engine, `throttle.rs` error classification, `ImapOps`, `GraphOps`), so its state machine is tested against fakes and against `src-mock-imap`; the daemon side is `abd_worker.rs` (worker, job registry, resume), `abd_local.rs` (the vault and mirror half) and `handlers/abd.rs` (RPCs). A dry run (`abd.preview`, then `abd.summarize` on the held listing, no server call) buckets the listing by the person's calendar years, so the summary and the job agree. Job state is `<app_dir>/abd/<account>/`, never `app.db`: `job.json` (small, mutable, rewritten after every batch and status change), one immutable columnar `plan-NNN.json` per folder and, for Gmail, `allmail.json`, all written atomically; an unreadable `job.json` is reported and left alone, never replaced. Uids are compact range sets. Invariants, each with a core test: **I1** nothing is deleted until its vault copy (and, in backup mode, its drive copy) is verified by Message-ID, its folder is not stale and, on Gmail, every scoped copy of that message is verified too; **I2** nothing verified is downloaded again, and a vault file already on disk stands for a planned message only when the vault folder is keyed under the plan's UIDVALIDITY (`maildir::read_generation`) and the message has a Message-ID to check it by (otherwise it is fetched, and a file already there counts only if it holds the fetched bytes exactly); a uid whose Message-ID the server did not answer at plan time fails the plan, never becomes "has none"; **I3** every file is re-verified by its exact path right before each delete batch (no directory listing per batch, and the persisted verified sets are never the sole proof): an expected Message-ID must be read and equal (`maildir::verify_listed_strict`), and a message without one counts only when this run wrote its vault file (or found it byte for byte) and, in backup mode, the drive copy matches the vault copy byte for byte; **I4** the delete intent is persisted before the server command, so a crash between verify and delete deletes nothing, and a persisted intent is reconciled on resume by asking the server what is still there; **I5** UIDVALIDITY is checked before every delete step and again on the destructive command's own SELECT (`UID MOVE`, its COPY fallback, the Trash expunge refuse with nothing sent when it differs); a changed folder, or one whose UIDVALIDITY cannot be read (after a few tries), deletes nothing more and its remaining messages are kept, and a persisted intent is never reconciled against an unreadable generation; **I6** an empty step only expunges the exact Trash uids of messages the job moved, re-read and matched by Message-ID, and never sends a plain `EXPUNGE`; **I7** a mirror error in backup mode pauses the job (`drive_unavailable`), never a vault-only delete. Delete is a batched `UID MOVE` to the resolved Trash (COPYUID kept; never created if absent) or, with neither MOVE nor UIDPLUS, refused up front; on Graph it moves to Deleted Items. "Move to Trash and empty it" then expunges exactly those moved uids (UIDPLUS `UID EXPUNGE`; Graph `permanentDelete` of the moved ids) and is refused without UIDPLUS. On Gmail (host, `X-GM-EXT-1` and a `\All` folder) label folders go first, the delete targets the All Mail copy so every label goes with it, and All Mail is handled last (only its unlabelled mail is in scope when ticked). The deleted-mail bin is opted out (every message has a verified vault copy) and each confirmed batch removes its rows from the header cache. Jobs resume at daemon start (`Running` and `Waiting` continue, a user pause stays paused, the other pauses are retried once when the token, drive or vault may be back; a job killed while it was still planning has no frozen plan to continue, so it is marked failed with "Interrupted while preparing. Start a new job."); pause, resume and cancel act between messages on one task per job, never a second run. Waiting never fails a job: the background allowance (Transfer accounting) waits for the next UTC midnight, a provider limit retries hourly, throttling and dropped connections back off, offline and a locked keychain poll. The job's session is released before any wait over 30 seconds. Progress is `abd-progress` frames (at most one a second, plus every status change and one terminal frame) that the panel renders; `abd.status` returns each job's last frame so a launching app re-attaches. A job never refreshes an OAuth token (the one refresh the daemon starts on its own is a scheduled send's, for that send), so for Graph and for XOAUTH2 IMAP a running job holds an in-memory lease the app pushes with `abd.set_token` (on start, on a timer while a job runs, and on an `abd-token-needed` event); it is never persisted, framed or logged, and a missing or refused token pauses the job `sign_in_needed` until a new one arrives. Graph bytes are not wire-counted, so a Graph job keeps its own per-UTC-day tally in `job.json` and subtracts it from the allowance.
- **Unsubscribe and BIMI.** The header page fetches `List-Unsubscribe-Post` beside `List-Unsubscribe`, and `mailvault_core::unsubscribe` parses both. The `unsubscribe` RPC POSTs `List-Unsubscribe=One-Click` itself only when the message offers an https one-click link and its Authentication-Results claims `dkim=pass` (RFC 8058 needs the headers DKIM-covered; the app cannot re-verify the signature); otherwise, or when the POST fails, it answers the browser or `mailto:` fallback for the app to open. Every request leaves the daemon through `export_fetch::send_guarded`, the one SSRF gate (resolved-address check on every hop, at most 3 redirects, no cookie store), with `https_only` for one-click and logos. Each answer is recorded in `app.db`. `unsubscribe.senders` pages an Insights snapshot in-process (`handlers::insights::begin_snapshot`) instead of scanning the header cache a second way. `bimi_logo` shows a sender logo only for a message whose Authentication-Results claims a DMARC pass for its From domain, and only when that domain's DMARC policy enforces (quarantine or reject at pct 100); the VMC certificate is not validated. SVG only, 64 KB cap, cached per domain in `app.db` for 7 days, a definitive "no logo" for 1 day; a failed lookup is not cached. The app shows it as an `<img>` data URI, so its scripts never run.
- **The AI provider layer.** `llm.rs` answers one question — `generate(provider, prompt, system, max_tokens)` — for three providers: the GGUF engine in `inference.rs`, a user-configured OpenAI-compatible endpoint, and Apple's on-device model through `mailvault-fm-helper`, a weak-linked Swift sidecar spoken to in one JSON object per line. Only the endpoint arm constructs an HTTP client; the two on-device paths cannot reach the network by construction, and a test asserts it. Quick replies, compose actions and auto-tag verdicts all go through this one layer. Mail from a Google account only ever reaches an on-device provider (Apple's model, the GGUF, or an endpoint whose host is loopback; `mailvault_core::ai::provider_allowed_for_google_mail`), because Google's API terms bar sending Google user data to third-party AI. `ai_gate.rs` is the daemon's one check, and it fails closed: `ai.generate` takes `accountIds`, and a cloud endpoint is refused unless the request names its accounts and every one resolves (`accounts.json`, then the keychain record) to a non-Google account (`is_google_account`: Google OAuth, or an IMAP host on `imap.gmail.com` or `imap.googlemail.com`); a prompt with no mail in it says `noMailContent` instead. Auto Tags check per message account in `evaluate` and skip a Google account's batch with one log line. The app's `aiClient.providerForMail` swaps a cloud endpoint for an available on-device provider before asking, so the refusal (`E_GOOGLE_MAIL_ON_DEVICE_ONLY`, shown through the `ai.googleMailOnDeviceOnly` catalog key) is only the backstop. Any new AI feature must pass `accountIds`.
- **OpenPGP decryption.** `mailvault_core::pgp` (rPGP, pure Rust, no gpg) detects PGP/MIME and inline-encrypted mail and decrypts it; `handlers/pgp.rs` owns the `pgp.*` key RPCs and `render`, the hook `maildir_read`, `maildir_read_light` and `imap_get_email_light` run a message's bytes through. Secret keys and their passphrases live in one split keychain entry (`pgp_secret_keys`); the app reads a picked key file itself and sends the text. The first decryption of a vault message writes `Maildir/<account>/<mailbox>/.decrypted/<uid>.eml` (original headers, decrypted body, `X-MailVault-Source` hash of the original): no `:2,` info part and not under `cur/`, so no walk, count, registry, backup, export or restore sees a second message. Every body and attachment reader goes through `pgp::readable`, which serves that copy when the hash matches, so later reads need no key; the index sweep indexes the copy's text, and `reconcile::forget_file` plus a nudge makes it re-read the message once the copy lands. Deleting the original removes the copy. The raw-source view and `.eml` export keep the encrypted original. Decrypt only: no encrypting, signing, signature checks, key lookups or S/MIME.
- **Auto tags.** `auto_tag_worker.rs` is a level-triggered sweep, not a queue: on every wake it re-derives what still needs a verdict from durable state (header cache, `enabled_at`, `auto_tag_decisions`), so it is self-healing across restarts. A rule's deterministic constraints are the prefilter and run before any model is asked; `enabled_at` bounds the sweep to mail arriving after the rule was switched on, which is what keeps an enable from becoming an implicit unbounded backfill. Only a verdict the model actually returned is recorded — a failure to ask (no model downloaded, an endpoint that timed out, a remote provider the rule may not use) leaves the message undecided, or that mail would never be judged once the model exists. `inbox_action: hide` is a local fact only: the daemon moves nothing, and the app does the hiding. A rule saved without "Allow a remote AI provider" carries `provider: null`, which means this computer's on-device model, resolved per batch (`mailvault_core::ai::on_device_provider`: Apple's model, else the downloaded GGUF); with neither, the worker skips the batch undecided and preview/backfill answer `E_NO_ON_DEVICE_MODEL`. Every tag the daemon assigns on its own (the worker, a backfill) is announced as `tags-assigned` `{tagId, items: [{accountId, mailbox, uid}]}`; the app adds the tag to those rows only where its render cache already holds them, so a row already on screen shows the chip without a reload. An undo answers with its `tagId`, and the app drops the cached rows carrying it so they ask again.
- **Download modes and eviction.** An account's download mode (`fetchMode`/`fetchModes` + `localCacheDurationMonths` in the frontend settings) is one rule, `mailvault_core::fetch_mode::FetchPolicy`, held to one shared fixture. Every body download gate asks it: the app's pipeline (`_getUncachedUids`, which reads the daemon's answer through `policy.accounts`: `fetch.keep` is `none`, `all` or `since` an instant, an unknown date kept, from `FetchPolicy::keep_bodies`) and the daemon's `auto_cache` (after a light fetch and for IDLE arrivals) and `graph_cache_mime`. `eviction_worker.rs` is the only thing that deletes working-cache copies (level-triggered, daily and on `storage.fetch_mode_changed`). A non-archived copy can be the last copy, since a server expunge prunes only the header cache, so a copy is deleted only when a server listing taken in the same pass (background lane, same UIDVALIDITY as the header cache) has its uid AND the header cache lists that uid with the file's own Message-ID; `A`/`D` copies and `orphaned/` are never touched (`vault_files::evict_files` re-reads flags at delete time). Deletes run per chunk under `with_mailbox_write`; the registry's change hook nudges the search index, which keeps an evicted message's row while the header cache lists it. Any error evicts nothing in that scope. Graph accounts are not evicted (the daemon keeps no Graph token to list a folder with; it renews one only for a scheduled send). The one proactive downloader is `hoarder_worker.rs` (Premium: runs only for a Hoarder account whose persisted `fetchModePremium` is true, so a lapse stops it and deletes nothing): level-triggered like eviction, each pass takes one STATUS per folder and lists only what may be new (nothing for a folder whose UIDNEXT has not moved since it was last left complete, `UIDNEXT:*` when it has, a full `1:*` on a new UIDVALIDITY or once a day), then fetches the server uids the vault has no file for through `auto_cache` (never `A`), one message at a time on the background lane, paced in batches, re-reading the policy before every folder and batch. Bodies and (estimated) listings spend a per-account daily byte budget persisted in `<app_dir>/hoarder-budget.json`, so a restart grants nothing; a provider bandwidth-limit error spends the rest of the day, and a refused sign-in ends the account's pass. With a `\All` folder (Gmail All Mail) the `\Flagged`/`\Important` subsets are skipped and All Mail goes last. Woken after launch, by `storage.fetch_mode_changed`, by a sync with real arrivals and every few hours; Graph accounts and the e2e harness (`MAILVAULT_DISABLE_HOARDER`) never run it.
- **Whole-message reads when the vault has no copy.** Every route that needs a message's raw bytes (attachments, inline `cid:` images, View Source / `.eml` export, `cache_attachment`/`cached_attachment_path`, `export_attachments`, `views.export_attachments`) goes through one daemon helper, `raw_message.rs`: the vault file when the registry has one; else the in-memory copy On Demand keeps (`fetch_mode::RawLru`, fed by opens that wrote nothing); else the server on the priority lane with the keychain's credentials. A fetched or remembered message is used only when its Message-ID agrees with the header cache's row (`fetch_mode::same_message`), and a fetched one is kept like an open (`auto_cache`, opened: every mode but On Demand, never `A`). Any server failure answers the vault's own "not found" error; a header cache that cannot be read refuses the bytes. One download per message at a time, the whole fallback bounded at 60 s (the app's reply budget for these routes is 75 s), a failure remembered for 30 s; local-only folders (`Scheduled`) never fall back. Graph: only the in-memory copy (the daemon keeps no Graph token to fetch with; it renews one only for a scheduled send). `cached_attachment_path` (the mount-time probe) and the light/`maildir_read` probes stay vault/memory-only: they answer "is it local". The eviction worker's daily pass also removes `attachment_cache` files a day old whose message is in neither the vault nor memory.
- **Attachment saves are jobs.** `export_attachments` (one message) and `views.export_attachments` (a view, a narrowed month or year of one, or a search's rows) take a client-made `jobId`, answer `{ jobId }` at once and do the reading and writing on a daemon task, reporting `attachment-export-progress` frames (`done`/`total`: files for one message, messages for a view, at most one frame per percent) and a last `finished` frame carrying the `result` or the `error`. The app (`src/services/attachmentExport.js`) listens before it sends, holds the save's progress under a key the attachment rows and timeline buttons read to stay locked, and treats a `daemon-reconnected` or a `daemon-events-lagged` as a failed job. The destination is a folder the person picked in the app's native folder dialog, started through the shell's `attachment_export_start` bookmark forwarder (see Shell) so the folder's access is held for the job. When a one-message job is refused a write there, the app writes the remaining files itself (`save_attachment_to`, skipping a file the job already wrote at the same size) as a last resort; any other failure, and every view save, simply fails.
- Vault-location file work (Phase 6): folder classification, the copy/verify/marker pipeline behind `vault_get_status`/`vault_adopt`/`vault_move_to`/`vault_move_to_default` (`mailvault_core::vault_ops`, `src-daemon/src/handlers/vault.rs`). The four Tauri commands (plus `vault_reset`, which has no file work to move — clearing a bookmark is its entire body) stay registered as thin forwarders: the app still owns the security-scoped bookmark (spec §3.4) and the `vault_close`/`vault_reopen`/`stop_daemon` restart choreography around each call, unchanged in shape from before Phase 6. A move is two RPCs, not one — `vault_move_to`/`vault_move_to_default` copy and verify but never delete, because the app cannot know whether to delete the source until it has saved the new bookmark and confirmed it actually resolves; `vault_move_finalize` (internal, never called from JS) commits (deletes source) or aborts, guarded by a `moveId` so a stale or mismatched finalize can never commit a move it wasn't answering.
- **MBOX import: three modes, one router.** The Import MBOX dialog (`MboxImportDialog`) only collects choices; `import_mbox` (`handlers/mbox.rs`) takes them as `mode`: `local` (the default: mail into the account's existing folders), `folder` (a vault-only folder, next bullet) or `server` (the upload job, below). `mbox_probe` reads a capped sample (200 messages or 8 MiB) so the dialog can tell whether the file carries `X-Gmail-Labels` and whether the account's cached folder list is known, and offers labels only when both hold: an unreadable list fails a label import, and a missing one would file everything in the fallback folder. Routing is pure code in `mailvault_core::takeout`: `labels_of` reads the header (RFC 2047 decoded, folded lines unfolded), `attrs_of` turns Starred into a flag and Unread into unread (Unread beats Opened; neither reads as read), and `home_folder` gives each message one home in a fixed order: Inbox, Sent, Drafts, Spam, Trash by special-use role, then a custom label, then the fallback folder. Important, Opened, Unread, Chat and Category labels never name a folder. `local` lets a custom label choose only a folder the account's cached listing already has (`folder_refs_from_listing`); `server` sets `create_missing`, so its first custom label makes the folder on the server. Gmail's All Mail is found from the raw `\All` attribute on the listing, not by changing `special_use`, whose value many Rust and JS consumers read. `local` and `folder` run inside the RPC on the blocking pool, one message per unit, and report `mbox-import-progress` by bytes read; `server` events carry `mode: "server"`, which is how the app tells the two apart. Every message is written with `fsx::write_atomic` (a dot-prefixed temp that parses as no uid, then one rename) under `common::with_mailbox_write`, so the backup mirror and pre-sync, which take no lock, never copy half of a message. Each destination folder has its own allocator in the import uid range (`IMPORT_UID_BASE`, re-checked under the lock, so an import never takes a number the server or another writer holds) and skips a duplicate: against that folder's vault files by Message-ID, Subject and body (`same_as_copy`), against the server rows in the header cache (read a chunk of uids at a time) by Message-ID, Subject and Date. A folder that cannot take a message (a name the file system refuses, a file where its dir belongs) counts its messages as failed (`failedCount`) and the other folders go on; only a closed vault gate or a full disk stops the import. A folder's dir always comes from core `vault_dir_name` (the storage key on Graph), never straight from a label.
- **Vault-only local folders.** The `folder` mode's target exists only in the vault: a directory `Maildir/<account>/<dir>` holding a marker, `.mailvault-local.json` (`kind`, display `name`, `created`, `source`), written atomically by `mailvault_core::local_folder`. It counts as local only if it is a real directory (symlinks are skipped) whose marker parses and names that same directory (`vault_dir_name(name) == dir`); anything else is an ordinary vault dir. `create_import_folder` claims the name `MBOX import YYYY-MM-DD` (then ` 2`, ` 3`) with `create_dir`, so an existing entry of any kind, a server folder's dir included, refuses the claim and two imports cannot take one name. Its messages carry import-range uids and `A`, plus the Starred and read state of a message that has Takeout labels (labels never pick a folder here), and the folder has no header cache rows, which is what keeps sync, eviction and cache clearing away from it.
- **Vault directory names.** A mailbox is stored under `Maildir/<account>/<vault_dir_name(path)>` (`search_index::text`: every char outside Unicode alphanumerics, `.`, `-` and `_` becomes `_`, plus `avoid_reserved` on Windows). The mapping is many-to-one, so a directory read back off disk is not a path IMAP can SELECT: the app asks `policy.vault_mailboxes {dirs, mailboxes}` (`mailboxes_from_vault_dirs`: the first listed path that produces the directory, else the directory itself) for its local scan and for `vault_search` rows, and holds no copy of the sanitizer.
  - Listing and use: `list_local_folders` reads the account's dirs for markers, with no per-message work and no lock. The app keeps the answer in `localFolders`, apart from the server's `mailboxes`: a local folder is never saved as a server folder, a move target or a unified-view member, and the sidebar draws it under "On this computer". Opening one is a vault scan. Opening a message, starring and marking write to the vault only, and delete goes to the deleted bin; the app's guards (`isLocalMailbox`, `inLocalFolder`) refuse whatever would reach a server (move, spam, snooze, purge, unarchive, a body fetch).
  - Delete: `delete_local_folder` refuses a dir without an `import` marker, captures each message in the deleted bin (`handlers::deleted::capture`, source Local) and removes it, then removes the marker and folder last and only when no mail is left under it. A partial delete keeps the marker, so the folder still lists and can be deleted again. It asks the search index for a full pass.
  - Search: the index treats a marked dir as its own authority. In `search_index::sweep` the listing closure answers "no server lists anything here" for it, so a file that has gone drops its row and the fresh-index mark clears, instead of waiting on a header cache that never exists for it. The app names local folders among a search's `knownMailboxes`, so hits carry the display name, and sends them to the local lane only.
  - Backup: unlike the two-way mirror pre-sync a server folder gets (see the backup bullet above), `mirror_local_folders` (`mailvault_core::backup`) copies a local folder one way. It runs at the start of every account run, IMAP and Graph, before the server folders, so a failed LIST cannot keep it off the drive, and copies `cur/` into `<mirror>/<account email>/<dir> (<created>)/cur`. It reads the vault and writes the mirror, outside the gate like the pre-sync, checks the cancel token before every file and reports a frame every 500 copies. One way is deliberate, because a message deleted from a local folder is binned, not purged from the mirror, and the two-way sync would bring it back; the marker's stamp in the mirror name stops a freed and reused name from inheriting the old folder's mirror. Nothing prunes a local folder: the index walk lists it, Clear cached emails keeps `A` copies, eviction never touches them and sync removes no vault dir. The ZIP export walks its `cur/` too, without the marker.
- **The MBOX upload job.** `import_mbox` with `mode: "server"` validates, reads the account's credentials with the daemon's own resolver, refuses a Graph account (`E_MBOX_SERVER_GRAPH`) and answers `{jobId, started}` at once. There is one job per account (`E_MBOX_UPLOAD_RUNNING`), and a journal of the same file (path, size, mtime) refuses a fresh start (`E_MBOX_UPLOAD_RESUMABLE`) until it is resumed or discarded. The work runs on an `mbox-upload` thread of its own (see Process and Thread Model), never on the RPC path.
  - Pipeline (`mbox_upload.rs`): one connection of its own, uncompressed, inside the account's connection budget, with LITERAL+ only when the server advertises it. Per message it picks the home folder with `takeout::home_folder` (labels first encoded to modified UTF-7, so a label cannot split a command), creates a missing folder once, and skips a message the folder already holds (the folder's cached header rows first, then, unless they are the whole, fresh folder, `UID SEARCH HEADER Message-ID` plus a header FETCH, judged by the same Message-ID, Subject and Date rule as `local`). It APPENDs with flags and INTERNALDATE, learns the uid from APPENDUID or a Message-ID lookup, and stores a vault copy at that server uid, so the message lists as a server row. On Gmail (`X-GM-EXT-1`) the message's other custom labels are then added with `UID STORE +X-GM-LABELS`. That is best effort: a refusal is counted (`labelWarnings`), never retried and never changes the outcome.
  - Journal: `<app_data_dir>/mbox_uploads/<jobId>.json` (atomic and versioned: account, file identity, options, counters, state, the folders touched and created) holds a byte-offset checkpoint, the start of the first message not yet finished, and `<jobId>.tail` holds one 8-byte content fingerprint per message finished since. A resume seeks the reader to the offset (`mbox::for_each_mbox_span`) and answers a message met again from the tail, so a crash between an APPEND and the next checkpoint cannot upload it twice, with or without a Message-ID. A checkpoint is written every 50 messages or 10 s and at every hold and end. A changed file restarts from byte 0 and the server-side skip covers what already landed. A journal left `running` reads as paused, and nothing resumes without an RPC. It sits beside `app.db`, never on the vault drive.
  - Control: `mbox_upload_status`, `_pause`, `_resume`, `_cancel` and `_discard` answer at once. Pause and cancel act between messages (an APPEND in flight finishes or hits its time bound); pause closes the connection, cancel keeps the journal for a resume, discard deletes it. Resume of a live job continues in place; of a journal with no worker, it starts a worker at the offset, and the app passes `sourcePath` again when the daemon, which holds no file entitlement of its own, can no longer read the stored path.
  - Backoff: a transient failure (throttling, a bandwidth limit, a lost connection) waits with exponential backoff and jitter between 5 s and 5 min, the level carrying across messages so a long throttle does not restart at 5 s each time; after 8 tries a message counts as failed and the job goes on. A refused sign-in reads the credentials again once, quietly (a background job never raises the keychain prompt); refused again, the job holds as `needsSignIn`. The job never refreshes an OAuth token (the one refresh the daemon starts on its own is a scheduled send's, for that send), so the app does that before a start or resume.
  - Events: `mbox-import-progress` with `mode: "server"`, at most two a second: bytes (journal offset over file size), counts, `paused`, `throttled`, `needsSignIn`, `labelWarnings` and the ETA, which the daemon computes and leaves `null` until five samples span 20 s. The last event (`active: false`) carries `foldersChanged`. The app renders a chip (`MboxUploadProgress`), asks `mbox_upload_status` at start and on `daemon-reconnected` for journals a quit or a crash cut off, and computes no estimate of its own.
  - Completion: every touched folder is synced through the sync engine and announced with `note_change` (no new-mail count, so no banner), the cached folder list is marked stale (`fetchedAt: 0`) when the job made a folder, and the search index is asked for a sweep. The app then refreshes the view it shows.
- **Messages not yet in the vault.** `vault_gap_count {accountId}` counts, per folder, the cached copies the vault does not hold (a message in two folders counts once in each): the header cache's uids, less the uids the vault registry lists for that folder (`uid_sets`, no file read), less what the account's download mode leaves on the server (`FetchPolicy::promises_copy`: nothing is counted for a hidden, On Demand or Index Only account, and Keep Recent leaves out mail older than its window), less import-range uids. The merge (`mailvault_core::vault_gap`) walks two sorted lists and pages the cache by uid, one page per custody unit, on a `vault-gap` thread at background QoS, and asks the registry only outside a custody lock. It writes nothing and caches nothing. The reply is `{count, vaultReachable, reason, partial, byMailbox}` and never claims zero when it cannot know: `count` is `null` when the header cache cannot be read, and `partial` marks a floor, when a cached folder holds fewer rows than the sync recorded or two cached folders share one vault dir. `vault_gap_save {accountId, accountJson}` registers in `backup_runs` (it joins a backup already running rather than starting a second), answers at once, and runs `backup::run_imap_uids`, which fetches exactly the missing uids through the backup's per-message step (archived copies, registry and custody updates) and reports the backup's own `backup-progress` frames; `backup_cancel` stops it. Graph accounts can count but not save. The app shows the reply on each account's card in Settings > Backup & Restore > Backup Schedule and computes nothing.
- **The message store and the storage formats.** Every read or write of a vault message, and every "which uids are taken" question, goes through `mailvault_core::message_store`, with the JMAP format's code under it (`jmap_store::record`, `jmap_store::blobs`). A vault keeps its messages as Maildir files or as JMAP records over shared blobs (the layout is under Core Data Model), chosen by its marker's `storageFormat` row and changed only by the conversion job below.
  - Guards: `src-core/tests/message_store_guard.rs` fails any file outside the store's owners that builds a `cur/` path, finds a file by uid, parses or builds a vault filename or scans the uid space itself, and its `no_store_item_imports` refuses a `use` of a store item, so every store write stays path-qualified (`message_store::write(`). `vault_registry_guard` counts those store writers as vault file writers that must keep the registry current.
  - Reading and writing: a mailbox may hold both formats at once and every reader reads both; where one uid has both, the record wins. Writers write the vault's current format and never remove the other format's file. Only two callers do: `write_replacing` (the ordinary writers: sync, fetch, flags), after reading the new copy back, and `remove_other_format` (the conversion), after its verify. Every "highest uid" or "which uids exist" question covers `cur/`, `jmap/` and `orphaned/` (`message_store::uids`, `highest_uid`). Listing reads the disk only and never calls the registry, so it is safe inside `with_mailbox_write`. A record's name holds no flags, so the registry and the search index keep its flag letters beside the name and read flags through `message_store::flags_name`.
  - Prepare, then commit: in a JMAP vault the parse, the hash, the record build and the blob write run outside the mailbox lock (`message_store::prepare`, `vault_files::prepare_store`), and the lock covers the commit alone (`vault_files::store_prepared`). The conversion job, `auto_cache` and `graph_cache_mime` work this way; the other `vault_files::store` callers still store inside the lock.
  - Blob garbage collection is mark and sweep only (`message_store::sweep_blobs`): the mark walk reads every record's blob id, and an unmarked blob goes only when it is still older than the grace (24 h). No refcount is stored and `remove` never deletes a blob: the vault registry is per host and droppable, and a vault on a NAS can be shared by two hosts, each blind to the other's records. The touch-before-name rule keeps a sweep safe beside writers: a writer makes a blob young (`blobs::put` refreshes a blob it reuses, `rebind_uids` touches one) before any record names it, so a record the walk missed never names an old blob, and any new record writer must keep the rule. A partial listing (blobs with no `Maildir/`, an account or mailbox that vanished or will not stat, a `jmap/` that will not list, a record that will not read) stops the sweep with nothing removed. A record that reads but will not parse, or names no blob, does not: every blob id in its text (`sha256-` and 64 hex digits, read as bytes) is kept, so no blob it may name goes, and the record stays where it is. It runs at the end of each conversion (an error is logged, and the next pass retries) and from Settings > Storage (`storage_reclaim_space`, refused while a conversion is live), offered in JMAP format and, in Maildir format, while the vault has a blob store (`storage_format_get`'s `blobs`, one stat): a convert back leaves the blobs younger than the grace. In Maildir format a Reclaim then removes the store's empty directories, and the store once it is empty, under the registry lock (`message_store::prune_blob_store`, `remove_dir` only), so the offer ends.
  - Server ids: a record of a JMAP account's message carries the server's `emailId`, `blobId` and `threadId` (`server`). The fetch paths (the bridge's body fetch, the hoarder, push arrivals, the raw-message fallback) set them in the same commit (`Prepared::with_server_ids`), or on a uid already held only when they changed, and the JMAP backup run sets them on each message it writes. A rewrite without ids keeps the ones the record had. The writers that leave them unset are under Known Gaps.
- **The storage format conversion job.** `storage_format_convert {to, oldFiles}` (`format_migration_job.rs`, routes in `handlers/storage_format.rs`) answers `{jobId}` at once and runs the vault's one conversion on its own thread (see Process and Thread Model).
  - Markers: a start or a resume writes the target into `storageFormat`, so from then on every writer writes it while readers read both, and the job id into `storageMigration`, which is emptied when the job ends.
  - Journal: `<app_data_dir>/format_migrations/<jobId>.json`, written atomically: the vault, the target, the old-files mode, each mailbox's state (`pending`, `done`, or `waiting` for its first import rehome), the counters and the messages left behind, checkpointed at least every 200 messages, at each folder's end and on every change of state. A done job's journal goes; a cancelled or failed one stays, so Settings can offer Resume and Convert back, until the next conversion of the vault replaces it.
  - One message: the read, the hash, the record or file build and the blob write run under the vault gate's shared side, outside the mailbox lock. Then `with_mailbox_write` is held for that message's commit only: the source is found again (gone: skipped; changed since the read: read again, three tries at most), its flags are taken as they are now, the new copy is written and verified, and only then is the old one set aside (`oldFiles: "retire"`, under `retired/format-<stamp>/<account>/<dir>`, by hard link when the volume takes one) or deleted (`"delete"`). The verify: a record re-parses and names the blob hashed from the old bytes, and that blob is there and hashes to its id; a Maildir file reads back as exactly the old bytes. A copy that does not verify is removed again and the old one stays. A uid with a copy in each format already: the same message keeps the new format's copy; two different messages are both kept in delete mode and the uid fails (`E_FORMAT_CONFLICT`), while retire mode keeps the record and sets the file aside.
  - Order and outcome: a folder goes into records only once its first import rehome has run (the rehome renames Maildir files only); until then it is `waiting`. A record's `receivedAt` is the header cache's INTERNALDATE, read before the folder's messages and never under a mailbox lock. A run that leaves messages or folders behind ends failed (`E_FORMAT_UNVERIFIED`, `E_FORMAT_REHOME_PENDING`) with its journal kept for Resume, and a full disk stops it (`E_FORMAT_DISK`). A record that will not parse is no message gone: in either direction it is left as it is, never removed or written over (`message_store::record_damaged_at`), and the run that meets it first ends failed (`E_FORMAT_DAMAGED`, with how many) once; the journal keeps it (`damaged`), so Resume passes over it and ends done. Retire mode refuses to start without the old files' size plus 10% free (`E_FORMAT_NO_SPACE`); a volume whose free space is unknown is let through. The app shows every `E_FORMAT_*` code as a catalog sentence.
  - Controls: `storage_format_get`, `_pause`, `_resume` and `_cancel`. Pause holds the worker between messages and cancel ends it; nothing is rolled back, so the vault stays mixed and readable, in the target format. Convert back is a new job the other way. A start toward the vault's own format is refused (`E_FORMAT_SAME`) unless a stopped job is pending or the vault still holds a message in the other format (`message_store::holds_format`: names only, outside the registry lock, stopping at the first; a damaged record is none, and a folder that will not list lets the start through). Settings offers it as Convert remaining, with the old-files choice picked anew, for a stopped run that left messages behind (a delete-mode `E_FORMAT_CONFLICT`, which a retire-mode run settles) and while the marker's `storageLeftover` row is set (`storage_format_get`'s `leftover`, one row). The generation repair sets that row when it turns a JMAP vault's records into Maildir files; every new job empties it (a resume keeps it, since it plans only the folders its run has not finished), and so does a same-direction start that finds nothing left; a move or a portable copy carries it (`carry_format`). `storage_format_retired` sums `retired/` and `storage_format_purge_retired` deletes it; a purge and a Reclaim are refused while a job is live (`E_FORMAT_BUSY`). Progress is the `format-migration-progress` event, four a second at most, which the app shows as a chip.
  - A vault out of reach holds the job: closed by the app (before a move, a portable copy or an adopt) or gone (its marker file is not there, as on an unmounted volume, whose folders would list as empty and whose messages would read as gone). No step's result is trusted while the vault is away: the job keeps its journal `running`, records nothing as failed, gone or done, waits outside every lock and looks again every 250 ms, then tries the same message again once the vault is back. A held job is a live job, so a move stays refused. It is settled, so a quit returns at once. A cancel ends the run, and the end's marker write goes through the vault gate, so nothing is written into a closed vault.
  - Moves and portable copies: `message_blobs` and `retired` are in `VAULT_DIRS`, so both carry them. A move is refused (`E_FORMAT_MOVE_BLOCKED`) while a job is live or the vault's journal says `running` or `paused` (`move_blocker`), never by the `storageMigration` row alone: a row no local journal explains (another host's job on a shared vault, a reset app data dir, a failed marker write) would hold the vault in place for good. A cancelled or failed job's journal follows a committed move (`follow_move`). The copy re-copies every record and byte-compares it, and checks every blob's bytes against its name, before `remove_sources` may run. `carry_marker` (`carry_format` for a portable copy) gives the destination the source's `storageFormat` (`maildir` when it has none) and an empty `storageMigration`, fails with `E_FORMAT_MARKER` when the source marker will not read, and drops the format this process cached for that root, as an adopt does.
  - Counters: `vault_files::storage_stats` counts a message once (its record when it has one), a blob's bytes once however many records share it, and the bytes of a Maildir file still beside its record; a copy set aside in `orphaned/` is no message and counts nothing.
  - e2e seams: a debug daemon waits `MAILVAULT_E2E_FORMAT_MESSAGE_PAUSE_MS` before each message, outside every lock (a release build compiles it out), so a spec can act while a run is in progress; under `VITE_E2E`, the storage location's folder picker takes `window.__MV_VAULT_FOLDER__` instead of the native panel.

**Sync observation.** `sync.probe` and `folders.status` are strict daemon-owned RPC families. They reject unknown fields before generic OAuth request injection or credential work. `mailvault_core::sync_policy` holds the ordered probe decision and first-50 preorder folder selection. The daemon keys its 10-second probe marker to the original account epoch, authoritative origin, mailbox, current native cache owner and invalidation generation. A check never marks itself: only its source-bound proof or a successful completed sync ticket can do that. Original-stamp permits fence publication after retirement, including JMAP delta custody writes; provider waits keep finite operation ownership without holding a commit permit. The 60-second folder throttle is consumed before the real provider sweep, including a failed sweep. IMAP and JMAP status reuse their existing provider paths, and JMAP observation opens no IMAP session. Provider children run as heap tasks on a dedicated 8 MiB background worker; its blocking pool also receives background QoS, and work yields at foreground boundaries. The routes bound whole check and folder refresh work to 25 and 120 seconds; shell replies allow 30 and 125 seconds. The renderer adapters allow 31 and 126 seconds, order issued probe mutations per account, and merge only current folder rows for an account that still exists with the same raw `accountExpectedContext`. A temporary store observer latches removal or source changes until the reply, while credential hydration may replace the account object without discarding valid rows. Native origin and lifecycle checks remain authoritative. A failed probe mutation makes the account uncertain until a whole-account invalidation succeeds within its adapter budget; a late success from an expired operation cannot restore trust. The original JavaScript exports remain archived as the frozen parity oracle.

**Native refresh foundation.** `sync.refresh`, `sync.refresh_status` and `sync.context` are strict daemon RPCs. An accepted refresh gets a process-local receipt and an original-account snapshot before its provider work enters one background header queue. The request socket can close while the receipt and work continue. IMAP, JMAP and Graph header writes use the existing native cache custody and source checks; the change ring records only proved arrival UIDs. A failed later page may retain confirmed earlier headers and emit one source-qualified repaint without claiming Complete. The worker runs on an explicit 8 MiB background thread, and provider waits do not hold the account write lease. The context route activates native schedule and existing watcher reconciliation only after an explicit renderer lifecycle observation. In this slice the production renderer still owns its existing refresh and scheduler, so ordinary startup never activates the new native timer or watcher discovery. `channel.open` may carry a short-lived sync view owner; the current channel generation controls view priority, while receipt and schedule state survive detachment. Settings and account events reset future deadlines, and a NetGate transition wakes one pending due attempt. The shell gives each new RPC a 30-second reply budget; provider work is observed later through status.

**Native unread projection.** `mailvault_core::unread_counts` owns the pure inbox visibility, reminder, shift, merge and presentation rules. The strict read-only `counts.unread` daemon route accepts a current count baseline and minimal raw UI observations, reads only missing predicate categories from app.db, and scans native-owned INBOX predicate fields in bounded custody pages for cache recounts. Original account, source and cache-owner checks fence publication; the route neither resolves credentials nor writes settings, headers or app.db. `src/services/unreadCountsClient.js` serializes requests, takes the settings baseline at execution, and publishes validated answers through the existing settings setter. `src/stores/unreadCounts.js` only gathers raw transient snapshots and exposes promise-based caller helpers. The scheduler awaits native rows and total for tray and dock updates while retaining its two-second debounce. Archived JavaScript and the immutable 67-case oracle retain the former decisions for parity checks. Cache recount replies label complete coverage, partial arrival fallback or no write. A same-owner cache generation change may re-read once against the originally captured account within the existing route deadline; owner or source replacement and a second generation change refuse publication. Raw shifts are not retried. If a complete cache read overlaps a later raw local shift, the lane applies valid shifts first and makes one fresh original-bound cache read. A failed fresh read retains those shifts but may leave unrelated arrivals stale until a later observation.

Every long-running job runs on its own thread or worker, never inline on the RPC handling path, so one slow account, drive, or index pass cannot stall other requests. Which thread owns what is set out under Process and Thread Model below; the socket itself has a thread and a runtime of its own. Jobs are resumable where practical (level-triggered reconciles, batched commits) and report progress as events; the frontend renders that progress and never computes it.

Daemon RPCs should expose cohesive operations. Prefer a small number of meaningful operations over many thin wrappers around internal functions.

Account transfer (Settings > Accounts, "Move to another computer") is split along the same line. The daemon owns the file format and the crypto: `transfer.export` encrypts a bundle the app hands it, `transfer.decrypt` opens one, and `transfer.apply_config` merges the bundle's app.db config (tags, fields, views, auto-tag rules) under an account id map. A `.mvtransfer` file is `MVXFER`, a version byte, the argon2id parameters (export: m=64 MiB, t=3, p=1), a 16-byte salt and a 24-byte nonce, then XChaCha20-Poly1305 ciphertext with the whole header as AAD (`mailvault_core::transfer::crypto`). The daemon never receives a user-chosen path: the app picks the file through the native dialog, writes it with `save_attachment_to`, and reads it with `read_file_base64`, a thin Tauri command that only opens `.mvtransfer` files. The account import adapter `saveAccounts` (`services/db/accounts.js`) sends a native per-record credential batch and a secret-free account merge, rejecting partial or unknown failures, and frontend settings travel through an allowlist (`services/transfer/settingsTransfer.js`) that leaves machine-bound state behind. Export and import both run in the main window only (`components/transfer/ExportModal`, `ImportModal`, raised through `settings-window-action` from a detached Settings window): the detached settings window forwards these workflows to the main window, which owns the settings/import UI and reloads when an import lands. Native per-record writes preserve imported accounts across detached windows, and credential events refresh presentation caches. Old-daemon whole-blob compatibility retains its cross-window race even with a fresh quiet read.

## Native backup scheduling and lifecycle

`mailvault_core::backup_schedule` provides bounded local-machine Date policy, validated schedule configuration, entitlement/idle/loading gates, concurrency, retry/limit-hold and snapshot-cadence decisions. Its local setters are pinned against an immutable real-JavaScript corpus in UTC, Europe/Vilnius and America/New_York, including DST gaps/folds. Each native configuration read obtains the machine zone again: a present TZ override uses Jiff name/POSIX/TZif rules with fresh file reads; otherwise macOS/Windows query the existing native-name library and non-mac Unix uses the authoritative current localtime link/file. Rules continue to come from bundled Jiff or the selected TZif file; no offset is persisted. `backup.schedule.get/set` run settings/account file work off the RPC runtime, preserve strict unavailable configuration, and patch only the allowed schedule/config subkeys through versioned SettingsDoc writes. Their `version` is the settings document version. Configuration and lifecycle views name `owner: daemon` and `automaticOwner: daemon`. The worker admits automatic work at startup and at native idle/retry/settle deadlines, using current settings and accounts. Settings document version and native lifecycle event revision are separate.

A dedicated background-QoS `backup-worker` owns the native manual queue and its spawned admission/provider tasks. `backup.run_now` acknowledges durable request/run identity, joins a pending or active account attempt and replays retained outcomes without starting replacement work; cancel/stop/status have finite control budgets and do not wait for provider completion. Automatic and manual admission share this native owner. Accounts and current credentials are resolved at admission, with Quiet automatic reads and guarded manual reads. Only a fallible native-slot read proving external backup unconfigured permits a local-only run; configured or unreadable access stays pending before kickoff. The shell supplies authorization through private execution-bound attach/status controls, rejected by the webview bridge before either forwarding path. Each native acquisition is keyed by daemon incarnation, logical run, execution, channel-owner session and local acquisition identity. The saved native slot is read fallibly before and after resolution on every platform; a changed slot releases the unsent acquisition and permits one fresh resolution. The worker revalidates that slot before consuming a root. A pending-access no-start result carries its observed native attempt; a result decided before a newer attach cannot retire that acquisition. Only after the original probe returns may the same execution requeue for fresh slot/owner validation. Real provider completions retain their actual joined-drain path. Roots and sessions remain in memory; only pending intent is journaled.

Legacy backup, native work and gap-save share one atomic account claim. The adapter captures correlated terminal-limit metadata but settles only the actual joined provider result. IMAP/Graph batch errors cancel and join their siblings, including awaited blocking mirror work, before releasing admission. A provider panic or an interrupted supervisor retains the real claim as explicitly uncertain until daemon restart. Stop and cancellation acknowledgements never release an undrained claim. Full IMAP backup body fetches use the background pool lane; the existing shared seven-socket budget still applies, so this does not promise a foreground socket under every workload. E1 mirror units and E2 protected purge/drain sequencing remain unchanged.

Scheduler intent, holds, correlation and retained outcomes use the existing app.db schema-11 metadata namespace. A retained outcome precedes a targeted versioned SettingsDoc update with an account run marker; replay after settings success but metadata-ACK failure cannot double count. Applied outcomes and settings history retain the newest five per account, while request receipts preserve idempotent manual replay. Credential failure adds failed history without advancing lastBackupTime; cancellation and limit holds add no ordinary failed history. A provider's cancelled result with an error updates failure status only. Recovery never treats an unknown folder ordinal as skip authority and resumes incrementally from zero. Access receipts independently retain exact rejection/fence and actual joined-drain evidence through lost events, ACK timeouts, retries and failed settings application. Correlated progress and cancel ACKs cannot release native scope. Reconnect/lag schedules bounded reconciliation off the event pump without releasing all holds. Read-only and foreign-incarnation access status do not re-probe unrelated pending admission. Unavailable/unknown native observations also stay passive, so an unchanged disconnected drive cannot publish its own next resolver trigger. Authorized or confirmed-absent attach and successful fence retain their wake; real reconnect, manual, configuration and maintenance triggers can retry the same pending intent. Loss of the native authorizing channel conservatively interrupts its execution; its scope and account claim stay held until actual drain, or remain uncertain until process exit. A replacement shell must acquire fresh native access, and a replacement daemon has a new incarnation. Independent acquisitions of the same path each release once; legacy account holds stay isolated. UI ownership and automatic snapshot cutover remain later stages.


Every webview publishes sequenced backup facts through `backup.context`: an explicit surface/session attach, ordered updates, and terminal retirement. Native window destruction retires the shell/window generation even if JavaScript cleanup never runs. Loading is aggregated across live surfaces; latest actual activity survives retirement. Empty surface membership is not sleep, offline or activity. Native timers retain the greater-than-150-second heartbeat fallback and wake/visibility settling. Ordinary activity gates future automatic work without cancelling active work. Stop fences prior intent and timers; sensor updates cannot rearm it. These surface identities carry no external-location authority.

`services/backupScheduler.js` is an observer facade. One request ID owns each pending manual click, duplicate clicks join it, and only its exact native retained receipt settles the promise. ACKs, progress and empty active slots are not completion. Incarnation/revision and subscription generations fence reconnect queries and events. UI detachment leaves native runs intact. Progress and Done timers only render state. Main alone presents retained completion descriptors through the existing notification policy and cosmetic prompts; delivery failure never changes a backup outcome. Backup config changes use targeted versioned merge patches through the existing main settings writer, including child relays, while unrelated settings retain their field-delta rebase and compose acknowledgement contracts.

Automatic Time Capsule manifests run through the existing synchronous helper on a separate blocking task. A retained backup outcome records its decision, queued/dispatched state, created receipt and timestamp application independently of successful backup history/manual settlement. At most one automatic scan runs at a time. Dispatch is durable before the helper is called; known created receipts retry settings only, with timestamps that cannot regress a newer value. A crash after dispatch but before a created receipt is uncertain and is never blindly repeated. Already applied pre-cutover outcomes are skipped; retained unapplied and new outcomes acquire an explicit undecided state. Stop fences queued manifests while an actual scan may still complete truthfully. Manual snapshot wrappers, gzip format and existing scan consistency remain unchanged; no arbitrary-crash exactly-once guarantee is made.

## Process and Thread Model

ABD previews carry an original account stamp through listing; only a confirmed start acquires a finite operation before job registration and the first job-file write. Unfinished jobs keep that owner while parked. Startup adoption waits for successful authoritative account bootstrap and refuses mismatched, missing or retired account files before mutation or provider work. The runner and started archive, custody, ledger, mirror and delete-bookkeeping children retain the same owner through their actual completion, including after timeout or waiter drop. Cleanup captures each selected account's original stamp with its cache snapshot, admits one account at a time before credentials or provider work, and releases the held-account flag through RAII on completion or unwind. A stale account is counted skipped while later accounts proceed. No account owner spans the global last-run save or daily idle wait; mirror copies remain shared backup data outside account erasure.

One box, one thread. Every separate action runs on a thread of its own, and nothing that can be slow shares a thread with the socket.

**App process (Tauri shell).** The webview owns the UI thread and never does file work. Each `daemon_rpc` call opens its own connection (Unix socket, or named pipe on Windows) on the app's runtime, so one slow reply cannot queue behind another; the long-lived event channel (`daemon_channel`) is a separate connection with its own pump. Spawning, build-checking and token reads for the daemon go through `spawn_blocking`, never the UI thread.

**Daemon process.** Standing owners each have their own thread, alongside job threads that exist only while their job runs:

- **`ipc-server` thread, its own tokio runtime** (`server::spawn_on_own_thread`) — the socket: bind, accept, per-connection framing, RPC dispatch, and the long jobs handlers spawn (restore, migration, backup, `mail_search`, reclassify). Nothing else is on this runtime, so no background work anywhere else in the daemon can delay an accept or a reply.
- **`sync-observation-worker` OS thread, its own tokio runtime**: the probe and closed-folder provider children. It has an explicit 8 MiB stack, Mac background QoS and a background-QoS blocking pool. Each long run is heap spawned, retains its original finite operation owner after its waiter stops, and yields to foreground activity before provider work. JMAP observation yields again after its account delta and between folder-count units.
- **Startup runtime** (`daemon_main`) — the periodic and long-lived workers: the sync engine, the IDLE watchers, the classification queue worker, the contacts flush, transfer stats and the Insights snapshot sweeper. It binds nothing and answers nothing. Its own disk work leaves it too: every sync cache step (the metadata read and cached count, the header writes, the flag patch, the prune, the hole restore and the contacts observation) goes through `sync_engine::cache_io`, one blocking hop per step, and the op-journal read behind the restore takes a blocking hop of its own (a sync's UID listing also puts back rows the header cache lost while the server still lists them, inside the span the cache holds, never a uid the journal still owes a move or delete: `sync_engine::heal_holes`), and the cached-header walk behind classification and the local scan behind a restore do the same.
- **`search-index` OS thread** — the index worker, sole owner of the search index's SQLite connection: level-triggered reconciles, rebuilds, destroys and compaction, coalescing signals rather than blocking a caller. It runs at background QoS and yields to the user: `server::handle_request` stamps every foreground RPC (`search_index::is_foreground_method`: message reads, flag changes, deletes, moves, list and search reads), and the worker waits between batches and attachment parts until the UI has been quiet for 400 ms (at most 2 s per step, so steady activity slows a build and never stalls it).
- **`custody-import` OS thread** — the one-time legacy JSON import, taking the custody lock one mailbox at a time.
- **`mbox-upload` OS thread, one per running MBOX upload (at most one per account)**: the upload job's worker. It runs a current-thread tokio runtime of its own, whose blocking threads are at background QoS too, and itself runs at background QoS on macOS. Before each message it waits for the UI to be quiet (`search_index::yield_to_foreground`, the search index's own rule), and it holds no lock across a network call; the job registry's lock is taken only by the control routes and the worker's exit.
- **`import-rehome` OS thread, one per folder whose pass a read starts** (once per folder until its stamp, never two for one folder): the old-import pass at background QoS. It plans outside every lock, writes the folder's ledger in one hold of the mailbox lock and renames a chunk of 1000 files per hold. The upload job runs the same pass on its own thread.
- **`font-download` OS thread, one per family downloading**: a Google Fonts download at background QoS, with a current-thread runtime of its own for its few requests; it yields to the user between files (`search_index::yield_to_foreground`) and holds no lock.
- **`vault-gap` OS thread, one per count or save request**: the not-yet-in-vault computation, at background QoS. It is a thread of its own, not a pooled `spawn_blocking` one, because a lowered QoS would stick to a pool thread other jobs reuse.
- **`abd-worker` OS thread** — the Archive & delete jobs: background QoS, its own current-thread runtime plus a `LocalSet`, one `spawn_local` task per job, so a job never runs on the IPC runtime and cannot delay an RPC reply. The `abd.*` RPCs only validate, register and signal it over a channel. Disk work goes to that runtime's blocking pool; the small job, plan and allowance reads and writes the engine's traits make synchronously happen on this thread (files in the app data dir, never on a removable drive). It yields the way the index thread does, through `search_index::wait_foreground_quiet` (the UI quiet for 400 ms, at most 2 s per call, as a tokio sleep), before every server command and store, and works in units of one message per fetch, 25 messages per batch and at most 200 uids per move.
- **`backup-worker` OS thread** - native backup lifecycle: background QoS, a current-thread runtime and spawned account tasks. Provider, credential and blocking disk work stay outside the control loop's state locks; status and cancellation remain available while actual tasks drain. It owns due scans, source-fenced lifecycle deadlines and bounded automatic manifest dispatch.
- **`cleanup-worker` OS thread** - the auto-cleanup rules (`src-daemon/src/cleanup_worker.rs`): background QoS, its own current-thread runtime, one run at a time (`cleanup.run_now` and the daily check share one slot). The rules stay where the Storage settings form writes them (`mailvault-settings.state.cleanupRules`, through the settings document); the daemon only reads them. `mailvault_core::cleanup_rules` decides which server copies a rule names, from the account's mailbox and header caches, the way the old `cleanupEngine.js` did (pinned by `src-core/tests/fixtures/cleanup-rule-cases.json`), and the premium gate (`has_premium_access`). The delete itself is the Archive & delete engine, as one or two jobs per rule (move to Trash; empty only the Trash folder), with `keep_unarchived` for "delete" rules (nothing downloaded, only verified vault copies go) and `mirror_read_only` when a backup drive is configured (read, never written). A run leaves out copies composed here, copies custody marks gone from the server, uids an op-journal entry still names and accounts with an unfinished Archive & delete job (and while a run works on an account, `abd.start` refuses it); a copy an earlier rule names is left to that rule, except that a later archive-then-delete rule also gets what an earlier delete rule could not take, and each copy is counted once. A run whose vault or caches cannot be read is not recorded, so the next hourly check tries again. It never waits (a job that would sleep or pause is stopped and the rest stays for the next run). Its job files live in `<app_dir>/cleanup/jobs/` (never `abd/`, and no `abd-progress` frames), its last run in `<app_dir>/cleanup/last_run.json`, reported by `cleanup.status` and the `cleanup-run` event. The daemon cannot resolve the backup drive's bookmark: Run All Now goes through the shell's `cleanup_run_now` (`src-tauri/src/cleanup.rs`), a forwarder like `abd_start` that resolves the drive, passes it as `mirrorRoot` and holds it until the run's `cleanup-run` done event (or a lag or reconnect). The daily run has no drive, so with one configured it deletes nothing.
- **`format-migration` OS thread, at most one (the vault's one conversion)**: the storage format conversion's worker, at background QoS. Before each message it takes a pause or a cancel and waits for the UI to be quiet (`search_index::yield_to_foreground`). It holds a mailbox lock for one message's commit only, never across the read, hash and blob write before it. At a quit (`pause_all_and_wait`, 600 ms at most) it stops at its next message, or at once while it holds for the vault, with its journal still `running`, and the next daemon start carries it on once the socket answers (`resume_journaled`). A paused, cancelled or failed job waits for Settings.

- **Render worker child processes, at most two** (`mailvault-daemon --render-worker`, cargo feature `blitz-render`, `WORKERS` = 2, a `RenderPool` of `blitz::RenderHost`s, a doc pinned to a worker by its id; the limits below are per worker): the Blitz reader's HTML layout and painting, in a process of its own so a pathological message costs one worker and never the daemon. It is a mode of the daemon binary that starts no runtime and no logging, has no network and reads no files except the system fonts (the *Disk* bullet below says what keeps a message from naming any other), and speaks line-JSON on stdin and stdout (`open`, which carries the `theme`, `tile`, `hit`, `textRuns`, `serialize`, `fold`, `inspect`, `fonts`, `close` and `fetched` in; `reply`, `error`, `fetch`, `updated`, `font` out). It is spawned lazily by the first `render.open`. `open.theme` is optional: a missing, null, unparsable or light theme opens the document light, and a `dark` one runs the Dark Reader port (above) on the parsed document before the first layout. Inside it one thread, with a 256 MiB stack so deep nesting cannot overflow it on any OS (the memory is address space, committed only as it is touched), owns every document; a reader thread feeds it stdin lines. Each operation on a document (open, tile, hit, inspect, a fetched answer, a relayout) runs under `catch_unwind`: a panic drops that document, answers its caller (if one is waiting) with `render_unavailable` and leaves the other documents and the worker running. A line that is JSON for an `open`, `tile`, `hit`, `textRuns`, `serialize`, `fold` or `inspect` with a `req` but is not a valid one is answered `render_bad_request`. `fonts` has no `req` and no reply, but each family is acknowledged with a `{"kind":"font","family","ok"}` line: it registers each family it has not seen (a family is registered once, whole), a registration that panics is skipped without ending the worker (`ok` false) and the host then refuses that family (see the Mail fonts bullet of the Blitz section), and it then reopens in place the open documents that name a new one and answers each with an `updated` line. A timeout alone never kills the worker: the watchdog fires only when a call timed out AND the worker has written nothing for 6 s while it owes an answer. The silence is counted from the worker's last line, or from the moment it went from owing nothing to owing something, so a busy worker finishing a burst of tiles is left alone and one that sat idle is not blamed for it. A call that timed out stays owed (the worker still has to reply to it), so giving up on it does not restart the clock: a worker spinning in paint is killed by the next timeout, however much tile traffic keeps arriving. A worker that caught a panic in a document exits as soon as its last open document is closed (at once if none is open), so the host respawns a clean process rather than keep one whose shared state is suspect. The other exits are the reaper (idle for 120 s with no open documents, checked every 30 s) and a failed write to its stdin. A worker that crashed is noticed on the next call. In every case the next call spawns a fresh worker and every waiter fails with `render_unavailable`, which the reader shows as its failure view. Calls have budgets of 8 s (`render.open`), 4 s (`render.tile`, `render.textRuns`, `render.fold` and `render.inspect`), 2 s (`render.serialize`) and 1 s (`render.hit`, where a late answer means "no link", never an error); each is a little under the shell's own timeout for the same method. Document ids almost never repeat across daemon boots (a random 32-bit base per boot plus a counter, below 2^52 so JS holds them exactly).
  - *Limits.* `render.open` checks its parameters before the worker is touched and answers `INVALID_PARAMS` for an `html` that is not a string, a `cssWidth` that is not an integer from 1 to 4000, a `scale` outside 0.5 to 4 or an `allowRemote` that is not a boolean; HTML over 4 MiB answers with the message `render_too_large`. The engine clamps width and scale again itself (`MAX_CSS_WIDTH`, `MIN_SCALE`, `MAX_SCALE`). A document is refused as `render_too_complex` before any parse when it holds more than 300,000 `<` bytes or opens more than 256 unclosed `div`, `span`, `table`, `blockquote`, `font`, `center` or `section` elements (the parser takes superlinear time in depth), and after the parse when it has more than 150,000 nodes or nests deeper than 256. Height is clamped to 200,000 CSS px and tiles are 512 CSS px tall; a tile that would need more than 33,554,432 pixels, or an index past the tile count, fails (`render_too_large`, `render_tile_failed`). Decoded images are bounded by header: one over 16 million pixels, or one that would take the document past 64 million in total, is answered empty, and bytes with no readable size (CSS, fonts, anything unrecognised) pass only up to 64 KiB, except SVG markup, which passes up to 1 MiB. The same check covers every `data:` resource, so an inline `data:` font or stylesheet over 64 KiB is answered empty too. Relative and protocol-relative URLs resolve against `http://invalid.invalid/`, so they never fetch; `<iframe>` is switched off.
  - *Disk.* The worker is an ordinary process with no sandbox beyond whatever the daemon runs under, so what stops a message from reading files is that the one code path in it that could is closed. That path is usvg, blitz-dom's SVG renderer: by default it treats every non-`data:` image `href` of an SVG as a local file path, and on Windows a UNC path is a network share, so an unguarded SVG `<image href>` could draw a file of this machine into the picture, stream a device file until the worker is killed, or open a connection to an attacker's SMB host. blitz-dom is vendored (*Vendored engine* above) so that its one usvg entry point, `parse_svg_image` (inline `<svg>`, SVG `data:` images and fetched SVG bytes all go through it), installs an `ImageHrefResolver` of ours: the string resolver always answers nothing, so no path, `file:`, `http(s)`, `//host` or UNC href is ever opened, and the data resolver ignores the declared type, sniffs the bytes and admits only PNG, JPEG, GIF and WebP, checking the header size against 16 million pixels per image and in total per SVG parse before anything decodes, and refuses a nested SVG. Three layers stand beside it as defence in depth, each with its own test (`src-render/tests/svg.rs` writes a PNG to a temp file and names it by absolute path through inline `<svg>`, a `data:` SVG in `<img>`, a `data:` SVG in CSS `url()` and a fetched SVG, sweeps eleven hostile hrefs including `<use>` and `feImage`, and asserts that nothing is painted and the net provider was asked for nothing; the mutation of swapping in usvg's default resolver fails seven of them). (1) `RenderDoc::open` removes, after parsing and before the first layout (and before Dark Reader's measuring pass), every `image` and `feImage` that has an `href` or `xlink:href` which is neither `data:` nor an in-document `#id`, and the non-`#` hrefs of every other SVG element, in a flat pass over the node slab that never recurses. (2) `BridgeNet` refuses gzip (usvg inflates svgz without a cap) and admits SVG markup only up to 1 MiB (`MAX_SVG_BYTES`; it declares no pixel size, so the byte size is its cap), for every `data:` and fetched resource, whatever the URL or declared type said. (3) The daemon's `blitz::fetch` accepts `image/svg+xml` like any `image/*`, under the same 5 MiB read cap and the SSRF guard. Only `data:` and `https` bytes are admitted at all; `file:`, `cid:` and plain `http:` requests are answered empty. SVG images (`data:` or https, in `<img>` or CSS) and `data:` rasters inside an inline `<svg>` therefore paint in Blitz mode, including an SVG logo sent as an inline `cid:` image, which the reader inlines as a `data:image/svg+xml` URL; an inline `<svg>` `<image>` that names anything but a `data:` raster stays unpainted. `src-render/tests/svg.rs` must be re-run on any blitz-dom or usvg bump (usvg 0.48 today), like `tests/net.rs`. usvg's renderer decodes an SVG's embedded rasters again every time an element draws the tree, and one parsed tree is shared by every element using the same URL, so the raster pixels each parse admitted are also charged per use against a per-document budget of 16 million (`BaseDocument::admit_image_use`; a replaced use gives its share back): an inline `<svg>`, an `<img>` or a CSS layer past it is not drawn, which bounds the decode work of one paint. An SVG that declares an XML entity (`<!ENTITY`) is refused before roxmltree parses it, since roxmltree caps entity nesting but not the expanded size (a few KB of entity references ask for gigabytes); a DOCTYPE without one still parses. usvg expands `<use>` by copying the linked subtree, so a kilobyte of nested `<use>` becomes a million-node tree; the vendored `parse_svg_image` therefore refuses an SVG whose `<use>` expansion, counted from the XML before usvg builds anything, passes 50,000 elements (`expanded_element_count`), and one whose converted tree passes 50,000 nodes (markers, patterns and text expand too), and each document keeps at most 200,000 vector nodes in all its trees together (`BaseDocument::charge_svg_nodes`: a tree shared by URL counts once, a rebuilt inline `<svg>` gives its old share back). A refused SVG is simply not drawn. Known residue: filters and blur radii are bounded only by usvg's defaults and the byte caps, and an SVG that passes the first count can still cost its tree's worth of work once. The same resolver closes the old bypass of the image pixel caps through inline-SVG `data:` rasters.
  - *Network.* The worker reaches the network only through the daemon, and only for images. A `data:` request is decoded in the worker. An `https:` request is held and queued as a `fetch` line only if its URL is the resolved `src` of an `<img>` in the parsed document, or if blitz asked for it while laying out (where it asks only for CSS background images), and only when the open allowed remote. Every other request, remote stylesheets, fonts, `@import` and frames included, is answered empty at once with no network request, so a tracker in a stylesheet link, an `@import`, an `@font-face` or a frame cannot fire. CSS background images (`url()` in a style attribute or `<style>`) are fetched like `<img>` images when the open allowed remote, as they are in the iframe, whose CSP allows `https:` images. This classification rests on when blitz-dom asks, not on what it asks (the request carries no kind), so `src-render/tests/net.rs` pins every case and must be re-run on any blitz bump. The daemon fetches each queued URL through `blitz::fetch` over `export_fetch::send_guarded` (https only, the SSRF guard, no cookies or Referer, `image/*` (SVG included), 5 MiB read chunk by chunk and abandoned at the cap, 10 s), at most 6 at a time, recorded in Network Activity with the purpose "email images", and writes the bytes back as `fetched`; the worker relayouts once per drained burst and the daemon turns its `updated` line into a `render-updated` event on the event bus. The `render.*` RPCs only validate and forward. `render.open`, `render.tile` and `render.textRuns` are stamped foreground (`search_index::is_foreground_method`), so the search index yields to them; `render.hit` and `render.inspect` are not, because hover traffic would hold the index back and the inspector only runs under the parity harness, and neither are `render.serialize`, `render.fold` and `render.fonts`, which only follow a selection, a click or a font that arrived.

**Blocking pools.** Each runtime has its own, reached through `spawn_blocking` (`handlers::common::blocking`). Everything that touches disk goes there and nowhere else: directory listings, file reads and writes, SQLite queries, MIME parsing, ZIP and mbox passes, attachment extraction (with PDF text extraction in a separate process again, for crash isolation).

Rules this model exists to keep:

- Nothing is awaited between process start and the socket being bound. A migration or import that must run at startup runs on its own thread afterwards, and a store it has not reached yet reads as empty, never as wrong.
- No directory listing, file read or write, or SQLite call on a tokio worker thread. A vault walk is tens of thousands of files; parking a worker on it stalls unrelated work on the same runtime.
- A job spanning many files or mailboxes takes its lock per file or per mailbox batch, never once around the whole job, so a concurrent read waits for one unit rather than the whole run.
- Long jobs answer their RPC immediately and report progress as events; the RPC path itself stays request/response.
- **Background work never degrades the UI.** Selecting, opening, deleting, flagging or moving a message must feel instant while indexing, sync, backup, extraction or any other job runs, and a lagging click is a defect, not a trade-off. A background thread runs at background QoS, works in small units, and yields between them to foreground RPCs; it never holds a lock a foreground read waits on for longer than one unit (a foreground read that cannot get the lock degrades, as the list preview does, rather than waiting). Progress is a non-blocking chip or toast, never a modal, and never takes focus. A new background job ships with a test for its yield or its non-blocking UI.

## Core Data Model

The app is organized around a few durable concepts:

- Account: credentials, provider metadata, transport choice, and account-specific settings.
- Mailbox: server folder plus local cache metadata.
- Email header: list-level representation for loading, sorting, filtering, and threading.
- Email body: full parsed message content, loaded on demand or cached ahead of time.
- Local archive: the vault's message files, Maildir `.eml` files or JMAP records over content-addressed blobs, used for portability and offline access.

The message store (`message_store.rs`) is the source of truth for locally saved email content, in Maildir or JMAP format per vault. The SQLite stores and in-memory state are performance layers, not the canonical archive format.

### Message storage formats

A vault stores its messages in one of two formats, set by the `storageFormat` row of its marker (`.mailvault-vault.db`); no row means `maildir`, as in every vault made before the JMAP format. The mailbox directory, and everything in it beside the messages, is the same in both:

```text
<vault>/Maildir/<acct>/<vault_dir>/           mailbox dir in either format: .uidvalidity, orphaned/, .decrypted/,
                                              .import-rehome.json, .mailvault-local.json
<vault>/Maildir/<acct>/<vault_dir>/cur/       Maildir format: <uid>:2,<FLAGS>.eml
<vault>/Maildir/<acct>/<vault_dir>/jmap/      JMAP format: <uid>.json, one record per message
<vault>/message_blobs/<h0h1>/<sha256hex>.eml  JMAP format: raw RFC 5322 bytes, content-addressed, shared across
                                              mailboxes and accounts (a Gmail label copy is stored once)
<vault>/retired/format-<stamp>/<acct>/<dir>/  old files a conversion set aside, until the user deletes them
marker rows                                   storageFormat = maildir | jmap
                                              storageMigration = <jobId> while a conversion runs, else empty
```

A record (`jmap_store::record`, `format: "mailvault-jmap/1"`) holds the uid, the blob id (`sha256-<hex>`, always present), the size, the local state (`local.archived`, `local.trashed`: the filename letters A and T, never JMAP keywords), the server ids of a JMAP account's message (`server`, else null) and an RFC 8621 Email object with the metadata subset only: `id` (the server's, else `L<uid>-` and 12 hex of the blob hash), `blobId`, `threadId` (the server's, else `T` and 12 hex of the root Message-ID's hash), `mailboxIds`, `keywords` (D F R S as `$draft`, `$flagged`, `$answered`, `$seen`), `size`, `receivedAt`, the address and id headers, `subject`, `sentAt`, `hasAttachment` and `preview`. Body parts and `headers` are never stored: they derive from the blob. Maildir to JMAP and back gives every message back byte for byte, under the same uid and the same flag letters.

These stay `.eml` in either format: the external backup mirror (any tool can read it), ZIP and MBOX export, View Source and `.eml` download, the deleted-mail bin's `deleted/<id>.eml` in app data, `.decrypted/<uid>.eml` and `orphaned/`. The `Scheduled` outbox is a vault mailbox like any other.

The vault registry (schema `"2"`) and the search index (schema 5, unchanged) are derived from both formats. A record keeps its name and size through a flag change and a network volume's mtime is coarse, so both compare the flag letters they keep beside the name as well as size and mtime. How the daemon reads, writes and converts them is under Daemon (the message store and the conversion job).

### Where state lives

The app and the daemon resolve their directories through one module, `mailvault_core::paths`, never through Tauri's path resolver or plugin-fs `BaseDirectory` (the macOS log dir is the one exception). Tauri's `app_data_dir` and `BaseDirectory.AppData` are Roaming on Windows while the daemon was Local, and every Tauri resolver ignores the env; the Windows v2.16.0 draft split its state across both dirs that way.

- **App data dir** `<local data root>/com.mailvault.app`: macOS `~/Library/Application Support` (the container's under the sandbox), Linux `$XDG_DATA_HOME` or `~/.local/share`, Windows `%LOCALAPPDATA%` (Local, never Roaming). Holds `accounts.json`, `app.db`, settings, logs (outside macOS, which keeps `~/Library/Logs`), `daemon.pid`, `mbox_uploads/` (the journals of MBOX uploads to a server, never on the vault drive) and the default vault. The frontend's plugin-fs calls take absolute paths under `get_app_data_dir`, and the app allows that dir in the fs scope at runtime.
- **Logs**: the shell writes `mailvault.log.<date>` to its log dir, the daemon `daemon.log.<date>` to `<app_data_dir>/logs` (the same dir outside macOS). Both go through `mailvault_core::log_redact`: Standard (the default) is INFO with every address written as `<provider#4 hex of sha256(salt + address)>`, the 16-byte salt in `<app_data_dir>/log_salt` shared by both processes; Verbose is DEBUG with raw values. The setting is `mailvault-settings.state.logVerbosity` in `frontend-settings.json`: the shell applies it at start, on every daemon `settings-changed` that names `mailvault-settings` and on a fallback `write_settings_json`, the daemon at start and on `logs.set_verbosity`. The shell deletes both kinds of log older than 7 days at start, the daemon its own.
- **Settings** `<app_data_dir>/frontend-settings.json`: one JSON object, one top-level key per persisted store (`mailvault-settings`, `mailvault-theme`, `mailvault-privacy`, `mailvault-focus`, compose sessions). The daemon owns it (`mailvault_core::settings_doc`, `handlers::settings`) through the shared `mailvault_core::json_doc` engine: `settings.get {keys?}`, `settings.patch {patch, baseVersion?}` (RFC 7396 merge patch), `settings.replace {values, bases?, baseVersion?}` (top-level keys replaced whole; an accepted `bases.mailvault-settings` applies only the UI field delta within that shared store), and `settings-changed {keys, version}` (names only) after every change. Writes are temp file, fsync, rename, under one writer lock and `frontend-settings.json.lock` (which the shell's fallback writer takes too); the version lives in `frontend-settings.version.json` with the hash of the bytes it belongs to, and rises when another writer changed the file; `.bak1` (newest) to `.bak5` are taken when the file differs from `.bak1`: before the first write of a daemon run once `.bak1` is an hour old, then at most daily (a `.bak1` dated in the future is never due); a file that does not parse is recovered for the app from memory or the newest good backup and kept as `.corrupt` on the next write. Daemon readers (`SettingsDoc::read`) read the bytes every time, error on a broken file, never see a backup and never wait on a write (a separate writer lock holds the IO). `safeStorage` keeps its last accepted store separate from dirty/inflight snapshots and sends immutable values plus that baseline; the daemon and current shell fallback rebase atomically under the same document lock, preserving concurrent native backup history/state/snapshot times, explicit removals, nested null and persisted-store versions. A write reply can carry the applied or a later coherent document snapshot; the UI rebases mutations made during the write onto it. Ordinary flush remains a durable no-version operation, and compose ACK modes retain their numeric, narrow, fresh-read contracts. Every window hydrates with `settings.get` (the shell's read after 1.5s or on a daemon error, while it keeps asking the daemon) and writes nothing until it has seen a document: a store that hydrated from nothing holds defaults, and its queued change is laid over the document once one is read; the main window and an original-message window apply other writers' changes to their stores, while settings and compose windows take them into their cache only and stay on their owner's relay. JsonDoc owns the one cache, writer, version, recovery and backup implementation; SettingsDoc retains object validation and settings mutation policy. Its SettingsCompatible persistence profile keeps ordinary file creation and atomic, non-fsync version sidecars. The engine also retains tested array, scrub and PrivateDurable primitives (0600 creation on Unix and durable sidecars) for separately reviewed consumers; accounts are not migrated here. Unsupported advisory locks intentionally permit writes to continue under the JsonDoc process writer lock; the legacy raw shell fallback has no shared process mutex in that case. Normal writes retain a 10-second lock budget; the raw fallback retains 2 seconds and exact input bytes.
- **IPC dir** `<home>/.mailvault`: the token, plus `mv.sock` on unix. On Windows the endpoint is the named pipe `\\.\pipe\mailvault-<fnv1a of the lowercased IPC dir path>`, one per home.
- On Windows both roots honour `LOCALAPPDATA` / `USERPROFILE` when they hold an absolute path. In a normal session they equal the known folders; the override is the Windows equivalent of `HOME` for isolating a test run, pipe included.
- **Portable mode (Premium)** replaces both roots when a `MailVault Data` folder holding a valid `portable.json` sits beside the app (beside the `.app` bundle, the AppImage file, or the `.exe`), or `MAILVAULT_PORTABLE_ROOT` names one; `paths::portable_root()` resolves it once per process, so a pulled drive never flips the data dir back to the host. The app data dir becomes `<root>/data` and the IPC dir `<home>/.mailvault/p-<8 hex of sha256(root)>`, so an installed copy never reaches the portable daemon. The app passes the root to the daemon it spawns. A portable copy's secrets never touch the host keychain: `credentials::sealed()` switches every daemon credential read/write to `<root>/data/credentials.sealed` (the `.mvtransfer` container), locked each launch until `portable.unlock`, and the shell's quiet `get_credentials` read forwards there while native workflows own writes; a locked store answers "unavailable" and refuses writes. Login item, default mail app, updater and the bundle-id single-instance lock are off in a portable copy. `portable.create` (daemon) copies the app payload keeping symlinks, snapshots `app.db` with `VACUUM INTO` and clears its host folder slots, copies mail through `vault_ops::copy_and_verify` under `vault_close`, seals the host keychain's secrets, verifies all of it, writes the marker last, and only then removes mail, secrets and `accounts.json` from the host if asked. A drive that disappears closes the vault (`vault_closed`) and raises a banner; a restart is required. macOS WKWebView storage stays in the host container: durable frontend state already lives in daemon files.

Two SQLite stores hold everything that used to be loose JSON files:

- **`<vault>/custody/custody.db`** — records about the mail: custody entries (`vault_entries`), the header cache (`header_cache`, `header_cache_meta`), the per-account folder list (`mailbox_cache`) and the sender address book (`contacts`). Never derived, never deleted, never rebuilt: a store this build cannot read is reported and left exactly as it is. Opened EXCLUSIVE by the daemon, so nothing else in either process may open it — everything reads it through `custody::with_conn`.
- **`<app_data_dir>/app.db`** — what the app keeps about itself: the vault and external-backup locations with their security-scoped bookmarks (`external_locations`), wire-byte counters (`transfer_stats`), classification results/model/queue (a result goes when its mail leaves the server folder: every daemon write that takes a uid off the header cache, the app's `removedUids` save, a bulk or archive-and-delete job's delete, and a sync's expunge, reconcile or UIDVALIDITY wipe, calls `classification::forget_at`/`forget_mailbox`, and the queue worker writes only what it just classified, so a forgotten row is never written back), the scheduled outbox (`scheduled_sends`, schema v3), the auto-tag rules with their backfill batches and recorded verdicts (`auto_tag_rules`, `auto_tag_backfills`, `auto_tag_decisions`, schema v4), the snooze queue (`snoozes`, schema v5), the unsubscribe history and BIMI logo cache (`unsubscribes`, `bimi_cache`, schema v6), the deleted-mail bin's rows (`deleted_messages`, schema v7; the `.eml` files it keeps sit beside it in `deleted/`), Network Activity's kept events (`net_events`, schema v8), the follow-up reminders (`follow_ups`, schema v9), and the journals of confirmed-but-unfinished work (`pending_ops`, `pending_backup_purge`, and the single in-flight bulk operation in `meta`). Deliberately **not** EXCLUSIVE and with a non-zero `busy_timeout`, because two processes hold it: the app creates the bookmark that grants the daemon access to the vault, so it cannot wait for the daemon to exist.

A third SQLite file is derived, not kept: **`<app_data_dir>/vault_registry.db`**, the vault registry (`mailvault_core::vault_registry`, daemon only). Per `(account, vault_dir)` and uid it records the file name, size, mtime and parsed light row of every vault message, and it answers `vault_uid_sets`, `vault_light_rows` and the uid-to-file resolution behind every single-message route (body, light row, raw source, attachments, exists, delete, flag change). It holds nothing the vault cannot rebuild, so it is droppable: an open error, a schema mismatch or a different vault root deletes and recreates it, a failed recreate runs it in memory for the session, and it is never in custody. A mailbox is verified (listed from disk) at most once per daemon session; after that every vault writer updates its rows or invalidates the mailbox before replying. `src-core/tests/vault_registry_guard.rs` enforces the writer half: a function that creates a vault file must upsert, one that only renames or removes must make some registry call, and each exception is listed with its reason.

### The metadata layer (tags, and the fields and views to come)

Tags, custom field values and saved-view definitions are user-authored, so they
live in `app.db` (schema v2: `tags`, `tag_assignments`, `fields`,
`field_values`, `views`) and never in `<vault>/search_index/index.db`. That
index is rebuildable by design — the daemon worker may delete and rebuild it —
so anything a person typed would be lost with it. Nothing in this layer touches
an `.eml`, a server flag or an IMAP keyword: a tag is local, and works the same
on a provider with no label support.

Assignments are keyed by `app_db::identity::msg_key`: the `Message-ID` where
the message has one, and `u:<vault_dir>:<uid>` only where it does not. The old
`[accountId, mailbox, uid]` key (`localMailLabelKey`, and `emailKey` for the
render cache) does not survive a move — an IMAP uid is per-mailbox — nor a
Graph resync, where vault files are named by listing position. Two copies of
one message in two folders share a key, which is what "a tag is independent of
the folder" means.

The app computes no keys. It sends what its rows carry (account, mailbox, uid,
`Message-ID` when present) and the daemon derives the key, so the rule has one
home. The frontend's `tagStore.byRow` is a render cache for the rows on screen,
refetched per page, and deliberately keyed by something unstable.

`tags.migrate_legacy` re-keys the old settings-file labels. The app reads its
own `frontend-settings.json` and hands the rows over — the daemon never opens
that file — and the daemon refuses the whole migration while its index cannot
place an assignment for an account, because the app clears its legacy store on
a success reply.

### Custom fields

A field is a definition (`fields`) plus a value per message (`field_values`),
both in `app.db`, both keyed by `identity::msg_key`. `scope` is an account id,
or `*` for every account; values are always per account, because the same
message in two accounts is two messages to the person reading it. Sharing a
field is a scope change on the same row, never a copy, so the values already
given stay attached; copying a schema to another account makes new fields and
leaves the answers behind.

Two rules worth keeping: editing a field is an `UPDATE`, never
`INSERT OR REPLACE` — this store enforces foreign keys, so a REPLACE would
delete the row and cascade every value away — and clearing a value deletes the
row rather than storing a null, so "no answer" and "answered nothing" cannot
read the same to a filter. `fields.set` refuses a payload with no `value` key
at all: forgetting an answer has to be asked for. `fields.save` keeps the
position a field already had, so an ordinary edit can never renumber a schema
behind the person's back; moving one is `fields.reorder`, which renumbers a
whole scope group in one transaction and refuses to trade places across the
line between the shared fields and an account's own.

Views narrow on fields the same way they narrow on tags: `app.db` answers which
identities match, the index answers which rows those are, and the two sets
intersect. `field:` in the search box does the same over a search's frames.

A view that groups by a field (`def.group` of `field:<id>`) is the one place
the render cache is filled ahead of the rows: `openView` loads the values for
everything it is about to show before `showRows`, because values arriving one
rendered row at a time would group every row as "no value" and then reshuffle
the list under the reader.

### Saved views

A view is a stored `ViewDef` (`app_db::views`) plus an evaluation, never a
stored set of messages. `views.evaluate` builds one `SearchRequest` per account
from the definition, runs it through the same `search_index::query::search` the
search bar uses, and returns rows stamped by `mail_search::stamp_local_row` —
the same shape the search's index lane produces, so the list renders them with
no second path. The app never evaluates a view itself: a set difference against
a partly loaded list is a guess, not a view.

Accounts whose requests are equal but for the account run as one statement
(`SearchRequest::account_ids`): every FTS probe is uncorrelated and scans the
whole index, so a statement per account paid for the same match once per
account, on the index lock a click waits on. `views.counts` asks with
`limit: Some(0)`, which counts without reading a page. `views.evaluate` is a
foreground RPC; the app runs one `views.counts` at a time and shows skeleton
rows while a view evaluates, never the folder behind it.

Two rules the definitions follow, both learned from bugs of the same shape:

- **A starter stores no name.** "Needs reply" written into `views.name` would
  pin English into the database for every locale, and a later language change
  could not undo it. Starters carry a `builtin` id and the app translates it;
  only a name someone typed is stored.
- **Folders are excluded by special-use, never by name.** A mailbox's name is a
  per-mailbox word (a German account's bin is `Papierkorb`), so `exclude_special`
  names IMAP attributes (`\Trash`, `\Junk`, `\Archive`) and the app resolves
  them to server paths per account when it runs the view.

`ViewDef.query` is written in one notation both sides read: `a && b || c d` is
(a AND b) OR the phrase "c d". The editor writes it (`src/utils/queryGroups.js`)
and `search_index::query::boolean_groups` evaluates it, each `&&` word being a
required phrase. A query with neither operator keeps the plain `plan_query`
path, so views saved earlier and the search bar mean what they meant.

The index gained a `flags` column for this (schema v3): the Maildir letters live
in the file name and `index_doc_from_light` strips them from `row_json`, so
Starred and unread were not answerable before. The migration reads them back out
of the file names the index already holds — no re-read of the vault — and a
rename (which is what starring a message *is*) updates the column.

Metadata is forgotten when its message is. A reconcile pass reports the
identities of the rows it removed and the daemon prunes `tag_assignments` and
`field_values` for them — but only after checking no other folder of that
account still holds the same identity, because a move is a removal plus an
insertion and the halves can land in either order. That check runs while the
index lock is held, before `app.db` is opened, so no path holds both in the
other order.

A tag-filtered view resolves its identities from `app.db` first and passes them
to the index as a whitelist through a temp table; every `app.db` read happens
before the index lock is taken, so no path holds both.

**Hiding view mail.** With `hideViewMail` on (default off), a folder's list
leaves out every message some saved view holds. The daemon decides membership:
`views.hidden_members` runs each view in `hideViewMailViews` (the person's
pick; `viewIds` on the call, absent means every view, an empty pick asks
nothing and hides nothing) over each account through
`search_index::member_keys` (keys only, uncapped, no row JSON, one index lock
hold per view and account), unions the hits per account and mailbox, skips
local-only folders, and narrows them to the uids the header cache lists, read
in units of 900 with the custody lock released between units, counting unread
from the cached server flags. It is background work, not in
`is_foreground_method`. An index or header cache that cannot answer is
`available: false`; the app reads that, a failed call, or the setting off as
unknown, and unknown shows everything. An empty `members` is a real "nothing
to hide".

The app keeps the answer in `viewHideStore` as `account|mailbox|uid` keys plus
per-mailbox hidden and unread counts, and filters only through `rowVisibility`
(`viewHidden`): the folder list, every INBOX badge (accounts not on screen too,
through `useEmailScheduler`) and the Bulk Operations pool, which always applies
it, since its pool is the folder's whatever the list shows. The list never
applies it inside a view or a search: there the view's or the search's own rows
are the point. It is asked for only while the setting is on, one ask at a time
(an ask made during one gets the single ask after it), after each view count
refresh, and when the setting flips. The header's total is the server's less
the daemon's hidden count, derived for display only; store `totalEmails` stays
the server's. A closed folder's badge is STATUS unseen less the views' unread
there, never below zero.

An accepted limit: during a search or inside a view, Explorer's conversation
grouping draws a hit's siblings from the folder's (hidden) list, so a sibling
a view holds that is not itself a hit drops out of the conversation there.

**View builder.** The reader offers an email's distinctive words, to add to a
view or make one from. The daemon ranks them: `views.keywords` takes the text
the index stores for the message (subject and stripped body), keeps up to 150
candidate words (`search_index::keywords::candidates`: 4 to 25 characters, 2
to 8 when CJK, no numbers, ids, hashes, URL or address pieces, long blobs or
`>` quoted lines, subject words counted 3x) and scores each
`(1 + ln tf) * ln((N+1)/(df+1))`, sublinear so a quoted thread repeating a
word does not win on repetition. Each `df` is one probe of the trigram
`msg_fts` table (`msg_cjk` for a short CJK word), matched the way a search
matches, so it is a substring count: "invoice" also counts "invoices". From 50
indexed messages a word in more than a fifth of them is dropped, and each
probe stops counting at that cut (`df_cap`). A word the index never saw is
dropped only when the message's body is itself indexed. Every probe is its own
lock hold and calls `note_foreground`, so the indexer stays parked for the
whole loop and a click gets the lock between probes. The 15 best are kept. A
reply is cached (64 entries, keyed with the data dir and the Message-ID, so a
reused uid misses) only for a body-indexed message, since an earlier answer
changes once the indexer reaches it; the readiness gate runs before the cache,
and an index lost mid-loop answers `available: false`, never "no words".

A view also names its senders. `ViewDef.senders` allows only those, `exclude_senders` blocks them and `exclude_messages` drops single messages by `msg_key`; the three reach the index as `from_any`, `from_not` and `exclude_keys` and are ANDed with the words. A sender rule is one exact column compare, never a substring: a name with an `@` is a whole `from_addr_lc`, one without is a domain and takes its subdomains (`@d` or `.d` suffix), so `n@x.test` is not `ann@x.test`. `views.senders` answers who sends what the view finds with its sender rules left off (`core::query::sender_counts`, the same `where_clause` as a search), flagging the account's own addresses, so the builder can offer Allow, Block and Hide mail I sent. The app only sorts the answer into a standing per sender (`utils/senderRules.js`); the filtering is the daemon's.
`views.keyword_detail` runs one search for a word across the accounts (none
named is every account) and names the top ten senders and subjects among the
first 2000 hits, subjects without `Re:`/`Fwd:`. Both are foreground RPCs
(`is_foreground_method`): a person is waiting.

The app only picks among them. `ViewBuilderPanel` shows the words as chips and
`KeywordHovercard` asks `keyword_detail` once per word per panel, only once
its card has rested on the word (hover or keyboard focus). Senders and subjects go through `Private`, and a chip
through `PrivateWord`, which reads the lowercased word capitalised so a
surname is masked like a name. "Add to view" appends each word as an OR group
of its own (`appendTerms`): one more way in, never a narrowing, and the rest
of the query keeps its meaning, an operator-free query being rewritten as the
AND group it always was. A view that searched no words is narrowed by them,
and the panel asks first. "New view" goes through `createView`, so the free
cap is decided in one place, scoped to the email's account and, when asked,
its folder. Whether the builder is open is `viewBuilderStore`, not persisted
and shared by every reader, so it survives a change of email and the move into
a thread, where only the focused message shows it. With `hideViewMail` on, a
thread re-read keeps an open message a view has just come to hold, while its
folder still has it, so the email a word came from stays in the reader.

The one-time move of the pre-SQL JSON files runs on the first open of each store and retires each file to `<name>.pre-db-<stamp>` (never deletes it). `app.db`'s import runs entirely inside one `BEGIN IMMEDIATE` with a `legacy_import` marker set in the same transaction, because the app and the daemon can both reach it at the same launch and `transfer_stats` rows accumulate rather than replace.

Two files deliberately stay outside both stores: `accounts.json` (the frontend owns it, and a second writer would turn a same-process race into a cross-process one) and `email_cache/<account>_<mailbox>/graph_id_map.json` (the Outlook uid ledger, which needs a cross-process file lock and must travel with the vault). Those sidecar directories therefore still exist; they just hold nothing but the ledger.

### Contacts (people)

One Person per human, built from the user's own mail plus their edits. Logic is in `mailvault_core::people` (`src-core/src/people/`); the daemon exposes it as `people.*` RPCs (`handlers/people.rs` reads, `handlers/people_write.rs` writes); the app is a view over a Zustand store (`peopleStore`) that only calls those RPCs. Phase 1 is local only: contacts never go to a mail provider and nothing is read from one.

**Tables (custody.db, schema V4).** Durable, never rebuilt from mail: `person` (name, notes, vip/pinned/blocked flags, soft-delete stamp), `source_record` (the vCard-shaped data of a person: emails, phones, org, plus unknown vCard lines kept verbatim; `source_kind` is `local` or `import`, and is the hook for provider records later), `person_link` (record to person), `record_address` (the normalised address of each record, the join key to mail), `person_journal` (undo log) and `review_dismissed` (addresses the user declined). Derived: `message_addr`, one row per message, address and role (from, to, cc), keyed by account, mailbox and uid, with `counted` and a `msg_key`. It can be dropped and rebuilt from `header_cache` without losing anything the user typed. User and imported data never go in the older derived `contacts` table (`replace_account` wipes it).

**Journal and undo.** Every mutation (create, edit, delete, merge, split, import) writes the primitive steps that reverse it (`put_person`, `drop_person`, `put_record`, `drop_record`, `set_link`) in the same transaction as the change. Undo only reverses the newest entry that is not already undone, so an inverse never runs against state a later operation changed; there is no redo and no way to undo something older first. One import writes every entry under a shared `grp` id and undoes as one action. Merge keeps its records, so a merge can be previewed first and split apart again.

**Keeping `message_addr` current.** It is maintained inside the `custody::cache` header writers, in the same transaction as the `header_cache` write, so a message and its address rows cannot disagree. The legacy JSON import (`custody::import`) writes `header_cache` outside those writers and indexes each row it inserts itself. Vaults that existed before V4 are covered by the `people-index` background thread (`people_index.rs`): background QoS, at most 500 rows per custody lock hold, waiting for a quiet UI between chunks, idempotent and resumable (`people.list` reports `indexReady`).

**Counts and lists.** Counts exclude Trash, Junk, Drafts, Outbox, Templates and Bulk; Archive counts. Gmail's All Mail and Important are not excluded, because Gmail shows one message under several labels: counts and the by-date correspondence list dedupe by `msg_key` (the Message-ID, falling back to the mailbox and uid) per account.

**Own addresses come from the app.** The daemon stores none. Every request that needs them (`people.stats`, `people.messages`, `people.suggest`, `people.review.list`) carries `ownAddresses` (login, default From and aliases, from `src/utils/ownAddresses.js`), so a new alias applies at once. They are filtered at query time, never at write time.

**RPCs.** Reads: `people.list` (search, sort by name, total or last contact, VIP filter, paged), `people.get`, `people.stats`, `people.messages` (correspondence by date, filtered and paged), `people.suggest` (ranked with the reasons for each), `people.review.list`, `people.journal`, `people.proposals` (duplicate candidates) and `people.merge_preview`. Writes: `people.create`, `people.update`, `people.delete`, `people.merge`, `people.split`, `people.undo`, `people.review.accept`, `people.review.dismiss`, `people.import_vcf` and `people.export_vcf`. Anything that scans many rows or people is paged so each custody lock hold lasts tens of milliseconds, and the interactive reads (`list`, `get`, `stats`, `messages`, `suggest`, `review.list`) are in `is_foreground_method`, so background work yields to them. The vCard reader keeps unknown lines through an edit and tolerates a BOM, CRLF or LF, folded lines, several cards in one file, a huge `PHOTO` line and unknown encodings. Export writes name, emails, phones, org, notes and the flags as `X-MAILVAULT-VIP`, `X-MAILVAULT-PINNED` and `X-MAILVAULT-BLOCKED`, through the same folder-slot forwarder as every other export (`export_folder.rs`): the shell resolves and holds access, the daemon writes.

**Contacts seen in mail (compose pickers, privacy names).** Separate from the address book. The daemon's in-memory contacts index (`contacts_index.rs`, persisted to the derived `contacts` table) holds, per account, every address on a header in a non-system folder with its first name, count and last date. It is fed by the sync engine's header writes and by `save_email_cache` (rows new to the header cache only, so a re-save never inflates counts), and seeded once per account from `header_cache`. `people.contacts.top` (latest and most popular, per account or all), `people.contacts.search` (address prefix or name substring, the From account's contacts first, then most recent) and `people.contacts.names` (every name, own included, for the privacy dictionary) rank it with `mailvault_core::people::seen`, all in memory, no custody lock per keystroke. `people.suggest` does not serve compose: it knows only book people and addresses the user wrote to.

**Safety copy, backup, move and transfer.** The daemon writes `Contacts/contacts.vcf` in the vault (`people_snapshot.rs`, a background thread, about 30 seconds after the last change, a page of at most 200 people per custody call). Custody stays the truth; the file is what the other paths carry. `Contacts` is one of the vault directories, so a vault move carries it, and a vault with no people but a `contacts.vcf` (restored, moved or copied) gets them back once. The backup mirror copies it to `<mirror>/Contacts/contacts.vcf` next to the pending-purge and local-folder passes, and copies it back into the vault only when the vault copy is missing. Account transfer cannot reach custody through `app.db`'s snapshot, so the bundle's `appConfig.contacts` carries the contacts as one vCard text, filled on export and imported in chunks as one undoable group on apply.

### Storage tiers

Two distinct locations, not one:

- **Vault (working copy)** — the mail the app reads and writes. Defaults to the app data dir; the user can relocate it to any folder. `src-tauri/src/vault.rs` owns resolution, folder verification and the copy-verify-delete offload; every mail-data path goes through `vault::root()`. Only mail data moves (`Maildir`, `maildir`, `email_cache`, `attachment_cache`, `mailboxes`, `search_index`, `custody`, `contacts_index`) — accounts, settings, logs, `app.db` and the vault registry stay in the app data dir so the app can boot and report an unreachable vault. When the vault cannot be resolved, mail-data commands fail rather than falling back to the app data dir, which would fork the archive.
- **External backup (cold storage)** — a second, independent copy written during backups and never read for day-to-day use. Managed by `src-tauri/src/external_location.rs`; both locations persist through the same security-scoped bookmark slot mechanism (`SLOT_VAULT`, `SLOT_EXTERNAL_BACKUP`). A third slot, `SLOT_ATTACHMENT_EXPORT`, holds the folder the last export was pointed at (see External file access authorization); Show in Folder resolves any of the three to reveal a path inside it.

The daemon resolves the vault independently from `app.db`'s `vault` location row (it was `<app_data_dir>/vault-meta.json`) and keeps its own `app_dir` for logs, lock, models and classification state. A vault adopt/move/reset holds `DAEMON_SUSPENDED` (nothing may spawn a daemon onto a root mid-move), closes the daemon's search index and custody store together (`vault_close`), performs the move, then either stops the daemon so the channel respawns it on the new root, or, if the root did not change, reopens both in place (`vault_reopen`) instead. Every vault-rooted RPC route refuses while this gate is held, rather than falling back to reading or writing under the app data dir.

Custody opens once at daemon startup, before the socket is bound, so its startup status event always predates the daemon's first possible subscriber and is dropped by design: not a race, an invariant. The open itself is only the file and its schema; the one-time import of legacy JSON records (`custody::run_legacy_import`) runs on its own thread AFTER the socket is bound, taking the custody lock one mailbox at a time, and marks each imported mailbox in `meta` so later starts skip it without reading a file. Blocking the socket on that import is what made a large vault start with no mail and a "Helper Not Running" card for minutes (2026-09-20); a mailbox not imported yet reads as "no cached headers", never as wrong ones, because the import only inserts rows the store does not have. The frontend instead re-queries custody status on every `daemon-reconnected` event (fired on the first connection too, and again after any respawn), which is therefore the one channel that actually carries this state, not a patch over a race window.

### Transfer accounting

`mailvault_core::transfer_stats` counts wire bytes per account: a `CountingStream` wraps the TCP/TLS stream inside `connect_transport`, below COMPRESS=DEFLATE, so compression savings are reflected. Counters are process-global, keyed by account email (the only identity `ImapConfig` carries), and flushed every 30s (plus on shutdown) into `app.db`'s `transfer_stats` table, keyed `(account_id, day, source)` with `source` naming the writing process. Each process only ever touches its own rows, so the app and the daemon never clobber each other; readers sum both sources. The optional daily limit governs **background downloads only**: backup runs, the Hoarder and the app's download-ahead. Regular sync, IDLE arrivals and opening a message never stop for it (only a provider's own cut-off can stop those), and a backup or Hoarder that reaches it waits for the next UTC midnight instead of failing. `mailvault_core::transfer_limits` owns it: it reads the per-account settings from the settings document (`frontend-settings.json` through `settings_doc::SettingsDoc::read`, fresh on every call, nothing pushed), holds the provider defaults (Gmail is recognised by its IMAP host and defaults to 2,000 MB down and 500 MB up when the cap is on and the field is empty; nobody else has a default), computes the day's allowance (`background_allowance`: limit less today's wire bytes, `None` when no limit applies), decides what Settings > Data usage and the warning banner show (`display_limits`: the typed number, else the provider default, which is Gmail's own 2,500 MB down while the cap is off; `warning`: the worse direction at 80% of its limit, unless the warning is off), which the app reads through `policy.accounts` (`handlers/policy.rs`) and never computes, and owns the UTC-day clock, with an injectable `Clock` so the rollover is tested without waiting for it. A backup run that stops there ends with a `limit_reached` progress frame carrying `resume_after_ms`, and the app's scheduler runs it again after the reset. The Hoarder's daily allowance is what is left of the limit while the cap is on and its fixed 1,000 MB while it is off. Microsoft Graph traffic is not wire-counted and is not governed (an Archive & delete job on Graph keeps its own tally). The soft warning at 80% of the limit is only shown: the daemon decides it (`warning`) and stops nothing for it, and the app's banner polls `policy.accounts` and shows it. Archive & delete jobs spend the same allowance for their downloads and wait for the reset when it is spent.

### Network Activity

`mailvault_core::net_activity` records one event per connection the daemon makes: IMAP connections (reported when they close, bytes from the same `CountingStream` as transfer accounting), SMTP sends (a Graph account's send is an HTTP request with purpose "send"), DNS lookups, OAuth2 exchanges, and every HTTP request through `http_client` / `http_client_with`. `with_purpose` scopes what a connection is for; the IMAP pool's lane supplies a default where no caller did. `with_account` scopes whose it is, the same task-local way; `record` masks any address in the result text (the Standard log salt, so it matches the logs; the account stays its address, which the page shows), hands the event to the one process-global listener, and pushes it into an in-memory ring of the newest 2,000 (`CAPACITY`), which the tests and the store's fallback read.

- The daemon's listener places the event (`geo_ip::Locator`: its IP, else the host's last DNS answer, looked up in the DB-IP country database compiled into the daemon; loopback, private and link-local are `local`; lookups are not placed), emits it on its event bus as `net-activity` with that `country`, and pushes it onto `net_log`'s bounded channel. It never touches SQLite: one `net-log` writer thread drains the channel in batches into `app.db`'s `net_events` (schema v8) on a connection of its own, and a full channel drops the event from the store rather than stall the connection's task.
- `net_log` keeps events for the user's period (`meta.net_activity_retention`: day, week (default), twoWeeks, month; at most 250,000 rows), pruned at daemon start, hourly, and at once on `net.set_retention`. Reads go through a second dedicated connection on `spawn_blocking`: `net.activity { sinceMs, untilMs, account, country }` answers the newest 2,000 matching, ordered by rowid (arrival), never by `atMs` (a connection's start); `net.geo` and `net.summary` are GROUP BY aggregates over the whole window for the map and the totals. The app subscribes before it asks for the snapshot, de-duplicates the overlap, and re-asks whenever the range, account or country changes.
- The account on an event: IMAP and SMTP connections name the account they sign in as. `server::handle_request` runs any RPC whose params carry `accountEmail` inside `with_account`, so everything it records is that account's: the Graph routes (the app names the account, `accountId` and `accountEmail`, and the daemon sends its token), a token refresh (named by the account it refreshes), `unsubscribe`, `bimi_logo` and its DNS lookups, and `fetch_remote_asset` (the app passes the address of the message's account). Task-locals do not cross `spawn`, so a run that knows its account names it on the client instead (`Tracked::for_account` / `GraphClient::for_account`: the Graph backup, migration, whose source and destination clients share one future, and `aliases.discover`'s Gmail send-as lookup, purpose "alias lookup"); an explicit account wins over the scope. Account-less on purpose, shown as "Not tied to an account": the shell's own reports (`record_reported`), the connectivity probe, update check, GitHub sign-in, release notes, AI model downloads, Google Fonts downloads (purpose "fonts"), the OAuth callback and code exchange while adding an account, and account setup's DNS and autoconfig (the account does not exist yet).
- The shell's own requests (the GitHub calls, the update check on Windows and Linux) are measured in the shell and sent up the channel as a `net.report` notification, recorded as `process: "app"`. Anything the shell cannot measure is not listed: web content the standard renderer loads inside emails (the Rust renderer's remote images are fetched by the daemon and are listed, purpose "email images"; the Google Fonts a mail uses are downloaded by the daemon for either renderer and listed, purpose "fonts"), the webview's own requests, app update downloads, and the macOS update check (Sparkle). DNS resolved inside an HTTP client or SMTP connect is part of that connection, not an event of its own.
- The privacy boundary is the event shape: host, resolved IP, port, purpose, the account's address, byte counts, duration and result (addresses in it masked). Never a URL path or query (tokens live there). Nothing leaves the machine: the store is local and the country lookup is offline. SMTP events carry no IP (lettre does not expose its socket's peer) and are placed only if the host's name was looked up through a recorded DNS event.
- The app renders only: it filters by protocol and purpose, draws the map from `net.geo` (pre-projected Natural Earth paths in `src/assets/worldCountries.json`) and formats; nothing is computed or stored app-side beyond the rows on screen.

## Data Flow

The common flow is:

1. React initiates an action through a store or service adapter.
2. The adapter calls a Tauri command, which forwards to a daemon RPC.
3. The daemon performs transport or filesystem work on a worker thread.
4. Results and progress events flow back through the shell and are normalized into frontend state.
5. Components render derived state rather than owning duplicated business logic.

This means:

- Components should stay thin.
- Stores should own cross-screen state transitions.
- Services should encapsulate integration details.
- The daemon should own protocol and persistence details; the shell only forwards.

Daemon-owned commands (listed as `DAEMON_OWNED` in `src/services/transport.js`) go straight to `daemon_rpc` under their own names instead of the request/response flow above. They never fall back to `invoke`; an unreachable daemon rejects with `errors.daemonUnavailable`. Every vault file read or write, header and mailbox cache access, journal and pending-operation update, Outlook uid allocation, and custody read or write is one of these: the daemon performs the disk work, its writes under the per-root gate described above (the two exceptions named under Daemon aside), and the shell never opens the underlying file.

Three vault operations are the deliberate exception: `vault_apply_flags`, `vault_rename_mailbox` and `vault_adopt_mailbox_dirs` stay ordinary Tauri commands (not `DAEMON_OWNED`) because only the shell can resolve the backup mirror's security-scoped bookmark. Each resolves the bookmark, forwards the call to the daemon with the resolved path added as a parameter, and releases the bookmark once the daemon replies or the reply budget expires, on every path including a daemon error. Because they bypass the `DAEMON_OWNED` mapping, a daemon-side failure reaches these three callers as a raw error code rather than a translated message.

As of Phase 3 (Tasks 3.4-3.7), the daemon owns archive, bulk delete, verify and Mail Insights end to end: their own RPC routes, their own cancel-token registry, no bridge call to the app for any of it. Insights moved whole, including its snapshot map, 300s expiry and 30s sweeper; its custody reads are in-process now, and the `custody_entries_for_account` bridge route it used to call is deleted with it.

Backup's own two RPC bridges are gone with it (Phase 3 remainder). It used to call `local_index_append` over RPC after each save and `vault_apply_flags` over RPC for the mirror-bookmark rename — the daemon calling itself, because the runner lived in the app. In the daemon both are in-process: custody appends through the same shared function `local_index_append` routes to, and the flag catch-up straight into `handlers::vault_flags::apply_flags` under the same `WRITER` the frontend's own forwarder takes. `local_index_append` stays a route because the frontend still calls it (`api.js`, `DAEMON_OWNED`), not as a bridge.

As of Phase 5 (Tasks 5.1-5.9), the daemon owns the network layer end to end: interactive IMAP (20 commands, 6 of which duplicate a call `sync_engine.rs` already made — rerouted to a thin daemon RPC over the same `mailvault_core::imap` function rather than deleted, since real one-shot callers outside the sync loop still need them), SMTP (4, after the client itself relocated into `src-core` in Task 5.3), Microsoft Graph (12; the 13th, `graph_get_mime`, had 0 callers and was deleted outright), OAuth2 (3, plus the loopback listener itself), and DNS mail-health (2). None of these have an app-side Tauri-command twin left; `src-tauri/src/smtp.rs` and `src-tauri/src/dns.rs` (both once kept as thin re-export shims for an in-process app caller that no longer exists) are deleted outright. `sync.now`/`sync.watch`'s payload no longer carries credentials at all (see Known Gaps); every other migrated command still accepts credentials as an RPC param exactly as before, unchanged shape. `get_credentials` remains a quiet app-local keychain read fallback; native account and per-record credential workflows own mutations.

A second, long-lived channel (`src-tauri/src/daemon_channel.rs` ↔ `src-daemon/src/channel.rs`) carries two things outside the request/response flow: daemon bus events (e.g. `search-index-progress`), re-emitted by the shell as Tauri events for the frontend to render; and app → daemon fire-and-forget notifications (`search_index.nudge {accountId, mailbox}` from every vault writer, `search_index.sweep_soon`), dropped while disconnected and recovered by a `sweep_soon` sent on every (re)connect. The daemon starts unconfigured on each spawn, so the frontend re-pushes its effective index config on `daemon-reconnected`.

Interactive mail search is a daemon-owned job too. `mail_search_start` receives a unique `searchId`, the filter snapshot, explicit normalized account/mailbox targets, location, and effective mailbox concurrency; it registers the run before acknowledging. `mail_search_cancel` marks only that run cancelled and shares a publication lock with `mail-search-progress`, so after cancellation is acknowledged it cannot publish another result frame. Progress frames carry a monotonic sequence, local/server lane, rows, completed/total counts, local mode, fallback reason, index coverage, folder failures, and terminal state. The frontend `searchStore` only merges increasing-sequence frames for its active ID; a `current`-scope account/mailbox change or entitlement change cancels and restarts the search. Tauri remains a forwarder, and the UI does not fan out work across mailboxes. `searchResults` is a projection of the per-lane row pools; `src/stores/searchRows.js` owns every write to them (frames, read marks, verdicts, removals), so a change to a row can never be undone by the next frame.

A message's identity is owned in one place too: `rowIdentity` and `sameMessage` in `src/stores/slices/unifiedHelpers.js` place a row at its own `{accountId, mailbox, uid}` (an unstamped row is the view's) and match it against a target, and a row whose location cannot be resolved matches nothing; no matcher or row key may compare a bare uid or treat a missing `_mailbox`/`_accountId` as a wildcard.

What the vault holds is keyed the same way: the store's `archivedEmailIds` and `savedEmailIds` are sets of `accountId:mailbox:uid` (`vaultKey`, read through `vaultHas`/`vaultHasSelection`), because both span every account and folder in view; the per-folder daemon reads (`getVaultUidSets`, `getArchivedEmails`) and the per-group cache `_archivedIdsByGroup` keep bare uids of their own folder and are keyed on the way into the store (`vaultKeys`).

Which rows the list holds back (server-`\Deleted`, auto-tag hidden, deleted-not-reconciled, locally snoozed) is one predicate, `rowVisibility` in `src/utils/rowVisibility.js`: `deriveDisplayRows` filters by it and so does the Bulk Operations pool over the cache, so no second copy of those rules can drift.

A list loader never commits a bare snapshot over flags the user wrote since it began: `rebaseFlags(base, live, incoming)` in the same module three-way merges them per flag against the live store, in the commit's own tick, and `loadEmails` (IMAP and Graph), `activateAccount`'s `commitToStore` and `loadUnifiedInbox` all commit through it (a load that replaces the uid space, UIDVALIDITY changed, does not).

Every place a message row lives (`emails`, `sentEmails`, `localEmails`, the derived `sortedEmails`, the open reader and its thread, the body cache, a search's rows, a Notes card) is a container registered in `src/stores/messageRows.js`, each by the store that holds it: a writer changes a row's flags, star, tags or verdicts only through `patchEverywhere(keys, mapRow)` (one pass per container, one `setState` per store), and a resolver reads the candidate rows only through `resolvePool(state)`, so a change reaches every container and a key resolves the same everywhere; a store field that holds rows and is not registered fails the guard spec. A cache of rows outside the stores (the restore descriptors in `cacheManager.js`, the unified folder cache, the header memo) registers an `invalidate` in the same registry, which `patchEverywhere` calls once per write by key (patching or marking the entries the write names, never scanning a list or reading disk), and each module-level cache is registered or exempted with a reason in the same guard spec. A loader that reads flags from a source that is right about them (the header cache after the daemon synced another device's change, the list `loadUnifiedInbox` just committed) lays them over every container through `paintFlags(rows)` in the same module, never over `emails` alone (`paintMovedFlags` for a reread of a whole list: only the rows that differ, plus those a container holds outside the list via its `held` rows). Opening a message marks it read through the same flag core as a hand mark (`applyFlagToTargets`, not undoable): rows first, then the vault copy, the journal and the server, the last three detached from the open (`detachTail`) so the body publishes once the rows have painted; a failure there is logged and left to the journal, never the error banner. The sidebar's per-account unread counts (`unreadPerAccount`) are written by the existing settings store only after an ordered native reducer answer. The reducer counts INBOX rows from a complete cache or an observed loaded list, otherwise applies raw action shifts or a proved arrival fallback. It applies the same count visibility decisions as the former `rowVisibility` invocation, including `\Deleted`, hidden tags, a local snooze and delete tombstones; shifts ignore their own tombstone. Row-list derivation still uses `rowVisibility` independently.

The daemon runs the local and server lanes concurrently. Local search queries the existing SQLite FTS index and assembles result metadata from stored `row_json` plus current filename-derived flags, without MIME-parsing each matching `.eml`. It reports index coverage and publishes indexed rows first; when the index is off, building, unavailable, or incomplete for the requested folders, it scans only the uncovered local folders and reports why. Server search schedules mailbox work with bounded concurrency, retains successful-folder results when another folder fails, and retries a transient IMAP connection failure once. The daemon clamps concurrency to 1–5 independently of UI state; the frontend sends the saved Premium value (default 3) for Premium accounts and 1 otherwise. Losing Premium does not erase the saved preference, and an entitlement transition restarts an active search so the new limit applies immediately. Microsoft Graph remote search remains unsupported, so a Graph-only server search terminates without a remote lane rather than leaving the spinner active.

The persistent search index remains one daemon-owned SQLite connection in exclusive WAL mode. Startup and runtime SQL failures go through the existing index worker: valid newer or structurally damaged search-index databases are rebuilt from Maildir, while lock, permission, disk, and vault-access failures keep the index files and retry with a capped delay. The worker reports `starting`, `recovering`, `indexing`, `idle`, `error`, or `off`; a real recovery failure carries `searchIndex.recoveryFailed` and its detail. Rebuild, disable, Delete, and vault switches fence in-flight open and attachment-extraction work by operation generation, and attachment files/extractors run without the database mutex. Every native extractor call (Vision, PDFKit) runs on a thread of its own with a deadline (`BoundedExtractor`): a call that never returns fails that one part and holds off further native calls until it does, but never stops the worker from indexing new mail. Search-index recovery only removes the four derived index files; it does not touch Maildir, custody, or account data. The index also keeps each message's list preview (`messages.snippet`, the start of the body text; NULL until read, and read once more by the next sweep for a row indexed before the column existed). The header-cache list reads (`load_email_cache_partial`, `load_email_cache_by_uids`) stamp it onto their rows as `previewText` in one query, trying the index lock for at most ~50 ms so a sweep never holds up the list; `save_email_cache` strips it again, so the header cache never stores it. Search results carry it too: an index hit reads `messages.snippet` with the hit (`assemble_rows`, which saved views share), and a server-lane hit is stamped by the same `attach_snippets` as a list read.

Local indexed queries use the same mailbox concurrency as fallback/server work. The daemon deduplicates selected vault directories, queries them in bounded SQL scopes, and merges each scope's top 500 hits by descending indexed date and row id so the account's displayed 500 are the same as one unbatched query. Indexed progress frames carry a cumulative per-account snapshot; the store replaces that account's prior indexed rows while preserving other accounts and later fallback/server results.

The search bar holds its query as tags (`src/utils/searchTags.js`), but the store, recent searches and `mail_search_start` still carry one string: the tags joined by spaces, operator values quoted the way `parseSearchQuery` takes them, free text never quoted (the server lane would search for the quote characters). Its typeahead is `search.suggest {prefix, accounts, limit}` (`mailvault_core::search_index::query::suggest_search`: senders, offered as `from:` tags, then subject and attachment-name words, at most 10). It reads the index connection on the blocking pool, tries its lock for ~100 ms and answers `[]` when a sweep batch holds it or the index is off or closed, so a keystroke never waits on indexing; it counts as a foreground RPC, so the worker yields while someone types. The app debounces it (~120 ms) and drops a reply a later keystroke has overtaken.

Search deliberately adds neither a last-100 query cache nor a remote-only full index. The cache would duplicate the persistent FTS index while adding invalidation for scope, account, move, and delete changes, and it would not accelerate new queries. Downloading and indexing all remote-only messages would add storage, body-download, synchronization, provider-throttling, and IMAP/Graph parity decisions; this phase indexes mail already stored locally instead.

The experimental Blitz body path (setting `emailRenderer: 'blitz'`) replaces the iframe end to end. The steps below are the reader's; the thread, bubble, full view, original, pop-out and preview surfaces run the same steps 2 to 8 on their own body (the same pre-processed body, or the exact `srcdoc` as `documentHtml`) through `useSurfaceDoc` and the per-webview doc registry (*Doc lifecycle* in the Blitz section), and image export and the social card use `rasterize` and `compositeBodies` (*Export*):

1. `EmailViewer` builds the same pre-processed body it gives the iframe (cid images inlined, links scanned, trackers stripped) and hands it to `BlitzBody` through `useAltBodyRenderer`.
2. `runPrepass` strips scripts and inline handlers, marks quote and signature folds, applies privacy masking, marks unselectable text and the open search's hits, or the body stays undrawn (privacy hold, or a failed pre-pass). The mail's installed Google Fonts are sent to the worker first (`render.fonts`, held to 300 ms). The HTML it hands on is the one built for the current privacy state, and only that.
3. `BlitzTiles` sends the serialized HTML, the pane width, the pixel ratio and the theme (light, or dark with the palette's colours) in `render.open`, clamped to the 1 to 4000 CSS px and 0.5 to 4 range the daemon accepts. The daemon validates them, forwards the open to the render worker and answers `{docId, rev, meta}`: size, tile count, the links, the plain text and the folds.
4. The webview loads each tile near the viewport from the `mvrender` scheme (`mvrender://localhost/<docId>%2F<rev>%2F<index>`, or `http://mvrender.localhost/…` on Windows); the shell forwards it to `render.tile` and returns the PNG.
5. The only requests the worker makes to the network are for images (`<img>` and CSS background images), and the daemon fetches them; remote stylesheets, fonts and frames are never requested. Each completed burst arrives as a `render-updated` event with a new `rev` and `meta`; the tiles reload.
6. Pointer movement and clicks go through `render.hit` (`{link, fold}`); a click on a link is `activateEmailLink`, the iframe's rule, and a click on a fold toggle is `render.fold`, whose new layout arrives as one more `render-updated`.
7. The text layer asks `render.textRuns` for the shown tiles, and a selection is serialized by `render.serialize` when it ends, so the `copy` event can write rich and plain text synchronously from the cache. Reply reads the selection through the body's handle (`altBodyQuote`).
8. A failure at any step (a rejected `render.open`, such as `render_unavailable`, too large, too complex or a bad request, or a tile that will not load) switches `BlitzBody` to masked plain text, a notice and the one-time bubble. Switching a message away or the setting off sends `render.close`.

## Known Gaps

Deliberately deferred or unresolved boundary issues, not a bug tracker; keep this list short and re-read it before touching the areas it names.

- **OAuth2 token injection is not tied to the provider's hosts (follow-up to step 0c).** `oauth_tokens::inject` puts the daemon's token into whatever `imapHost`/`smtpHost` the request's account object names, as the app's token went before. Injecting only when the host is the provider's own for Google and Microsoft accounts would stop a malformed or hostile account object from carrying the token elsewhere. The renderer token-take route has since been retired; refresh pairs remain in native memory until the guarded native writer confirms storage.

- **The backup mirror's bookmark scope is still unverified — it just no longer blocks anything.** `resolve_external_location`'s `start_access` (`external_location.rs`) rebuilds a plain `fileURLWithPath:` from the resolved bookmark's path string rather than starting scope on the security-scoped URL itself — the same defect `open_in_finder_inner` was fixed for, but that fix (`c393c14c`) never touched the call site backup uses. Whether it silently no-ops in production needs a signed-build test Rokas has to run himself. Backup's migration no longer waits on the answer: the shell resolves and releases exactly as it always did and hands the daemon the resolved path, so a scope that was never load-bearing and one that is both behave as before. What the answer would change is whether the hold-across-a-run bookkeeping (`HeldBackupPaths`) is doing real work or is ceremony.
- **One `ImapPool` per process, gap closed.** Before Phase 5 the daemon's archive/bulk routes used the daemon's pool while the app's separately-managed pool served interactive IMAP, up to 10 concurrent connections per account combined. Task 5.4b deleted the app-managed pool; the Phase 3 remainder deleted the process-global `OnceLock` pool that `backup.rs`/`archive.rs` shared, when those runners moved. The app process now constructs no pool at all, and `tests/unit/networkInDaemon.test.js` asserts no `ImapPool::new()` remains in `src-tauri`.
- **Daemon RPC handling is serial per connection.** `archive_emails` / `bulk_delete_emails` await their run inline inside the server's per-connection request loop; `cancel_archive` only reaches a different in-flight run because `rpc_attempt_inner` opens a fresh socket per call. If RPCs are ever multiplexed over one connection, a cancel could deadlock behind the run it is meant to cancel.
- **Insights snapshot state does not survive a daemon restart.** Snapshots used to live in the app process; now they die with the daemon, so a `snapshotExpired` error mid-load has no automatic retry. Recoverable today by reopening the panel; rare.
- **Insights daemon replies are not byte-identical to the pre-migration shape.** Structured failures round-trip as `Ok({ok:false, error:{...}})` because `daemon_rpc` cannot carry a structured `Err` (Task 3.7 decision); `ok:true` also now leaks into success payloads that never had that key before, and whether that is permanent has not been decided. The JS-side unwrap of a failure reply is covered by the daemon's wire-shape tests, not by a dedicated JS unit test.
- **The archived-ids map has more bypass writers than Task 3.8 closed.** `messageListSlice.js`'s `_archivedIdsByGroup` is fed by 5 named writers, plus 3 more (`activateAccount.js`, `AccountPipeline.js`, `messageMutations.js`) fixed in a follow-up round after review found they could stale-narrow the map. Still open: `messageMutations.js:158-160` and `:425-431`, `loadEmails.js:170-187` (main path) and `:809-817` (Graph path), and a related optimistic-update desync in `localDrafts.js` all still write `archivedEmailIds` directly on a successful read without feeding the map - the same latent-stale-map shape, not yet fixed. Two comments are stale in the meantime: `messageListSlice.js:88-94` and `archivedIdsPerGroup.test.js:216-220` still say `activateAccount.js` writes "outside the map", which the follow-up round already fixed.
- **A live-bridge-object mismatch recurs at the transport boundary.** `withGlobalTauri: true` injects two separate `invoke` objects (`window.__TAURI__.core.invoke` vs. the ESM import from `@tauri-apps/api/core`); code that resolves the ESM one at module load time can silently miss a test fixture (or a future feature) that only patches the global. Fixed once in `src/services/transport.js` (`c85770c1`) and once in `src/services/daemonClient.js` (`61c75c11`) by preferring the live global. Any new module that calls `invoke` directly should check which one it is reading.
- **`backup_migrate_legacy_path` stays a Tauri command, not a daemon gap.** Phase 4 (Task 4.9) excluded it deliberately, not by oversight: unlike every other Phase 4 command, its `legacy_path` argument is read from a persisted settings value (`useSettingsStore.getState().backupCustomPath`), not a fresh picker result, and the function it calls (`external_location::migrate_legacy_path`) mints and validates a security-scoped bookmark slot (`SLOT_EXTERNAL_BACKUP`) - squarely the shell's permanent, sandbox-mandated bookmark responsibility, the same bucket `backup_resolve_external_location` already sits in. Recorded here so a future phase does not rediscover it as a gap.
- **A daemon restart mid-OAuth2-flow loses the pending exchange (Phase 5, Task 5.7).** `OAuth2Manager` moved from the app's `.manage(...)` into `DaemonState` (one instance for the daemon's whole lifetime, same shape as `imap_pool`), so its in-memory `pending`/`senders` maps — populated by `oauth2_auth_url`, redeemed later by `oauth2_exchange` once the user finishes in the system browser — now live in the daemon, not the long-lived app process. Before this move the app never restarted mid-flow; now, a daemon crash, forced respawn, or vault-move-triggered restart between "Sign in" and the provider's redirect drops the pending state, and the browser's eventual callback either hits an empty map (if the port rebinds) or a "No pending OAuth flow for this state" error. Same category as the migration-restart gap below: not fixed (would need persisting pending flows to disk keyed by state token, or the JS side detecting the failure and cleanly restarting `oauth2_auth_url`), a direct and foreseeable consequence of this relocation rather than a pre-existing issue.
- **OAuth2 loopback binding under a sandboxed daemon is unverified.** `com.apple.security.network.server` was added to `src-daemon/entitlements.plist` (Task 5.1) so the daemon can bind `127.0.0.1:19876` for the OAuth2 callback (Task 5.7 moved `OAuth2Manager` construction there). Whether a separately-signed, `app-sandbox`-entitled child process can actually bind a *listening* socket under a real signed, notarized build is unknown — the earlier P0.1 sandbox-inheritance probe covered file access and SCM_RIGHTS fd-passing, never a listening bind. It stays unverified: the in-app diagnostic that would have checked it was removed. If a signed build shows the callback never accepting a connection, the documented fallback is reverting Task 5.7's RPC-routing changes and keeping `OAuth2Manager` in the app (every other Phase 5 task is unaffected either way).
- **Migration does not survive a daemon restart mid-run.** `start_migration`/`resume_migration` register their cancel/pause/notify tokens in `DaemonState.run_tokens`, an in-memory map, and the run itself is a bare `tokio::spawn`ed task; a daemon restart drops the process and everything the run held, with only the last-saved `migration_state.json` checkpoint (written once per completed folder, plus once on pause) surviving. Nothing in the daemon's startup sequence scans for or relaunches an interrupted migration - the app must notice and issue a fresh `resume_migration` RPC itself. Recovery is folder-granularity, not message-granularity: a folder that was mid-flight when the daemon died restarts from its own beginning (safe, since Message-ID dedup against the destination skips messages that already landed, but not free - already-copied messages are re-fetched from the source and only then recognized as duplicates). Unchanged from the app's own pre-Phase-4 behavior; Task 4.7 neither improved nor worsened it, this is simply the first time it is stated explicitly in project docs.
- **Resuming a migration after a daemon restart starts a fresh run, and undercounts.** While the daemon lives, `resume_migration` wakes the parked run (`common::resume_kind` clears the pause flag and notifies; no second run is spawned), and a pause anywhere, including mid-folder, persists a `"paused"` checkpoint. After a restart there is no parked run, so `resume_migration` rebuilds one from `migration_state.json` via `filter(|f| f.status != "completed")`: it gets a new migration id and its own counters start at zero, so its progress undercounts what earlier runs copied (nothing is re-copied, because destination-side Message-ID dedup skips it).
- **`ImportResult.newAccounts` is a permanent, not transitional, deviation from the byte-identical-payload rule.** Every other Phase 4 command's JSON payload matches its pre-migration Tauri shape exactly. `import_backup`'s `newAccounts` field changed from `string[]` (bare emails) to an array of `{id, email, imapServer, smtpServer, createdAt}` objects, because the daemon route reads `accounts.json` but deliberately never writes it (that file already has an independent writer, `src/services/db/accounts.js`, and a second, uncoordinated daemon writer would turn a same-process race into a cross-process one). The app merges these descriptors into `accounts.json` itself, through `ensureAccountsInFile`. This is a permanent shape, not a migration artifact meant to be reconciled back to a bare string array later.
- **`sync.now`/`sync.watch`'s payload no longer carries credentials — permanent, not transitional (Phase 5, Task 5.2).** `toSyncAccount` (`src/services/syncService.js`) used to put `password` and `oauth2AccessToken` on `imapConfig`; it now sends eleven fields instead of thirteen, dropping both. The daemon resolves them itself, per request, via `credentials::resolve_account_credentials(account_id)` (`src-daemon/src/credentials.rs`, added Task 5.1) — the one call site in the daemon that reads the shared `com.mailvault.app`/`credentials` keychain entry the app writes (or the `MAILVAULT_TEST_CREDENTIALS` debug-only file bypass), parses that account's stored JSON, and fills `imap_config.password`/`access_token` before the request reaches `sync_engine`/`idle_watch`. The IDLE task never resolves credentials itself: it reads the account `sync.watch` last handed it at every connect and every sync (`idle_watch.rs` `run`), so `handle_sync_watch` must populate the real password/token before calling `state.idle.watch()`, the same way `handle_sync_now` does before `sync_engine.run_ticket`. New credentials for an unchanged server (an hourly OAuth refresh) are handed to the running watcher instead of replacing it; only a changed server config, or new credentials for a watcher whose login is failing, replaces it. Every (re)connect and IDLE timeout runs a catch-up INBOX sync, the watcher's sync publishes arrivals before its flag step and reconcile (`sync_account_announcing`), and their bodies are stored as vault cache copies the way an opened message is (`handlers::imap::cache_arrivals`). `get_credentials` remains a quiet shell read fallback; account add/edit and credential mutations now use native workflows.
- **MBOX import edges (vault-only folders and the server upload).**
  - A message deleted from a local folder stays in the backup mirror, which never removes anything for that folder.
  - Nothing recreates a local folder from a backup or a ZIP: the mail is copied back but the marker is not, so it lands in an unmarked dir that no view lists. (A local `deleted.recover` into a deleted local folder writes the marker again, when the account's folder list is known and has no folder of that name.)
  - A mode `local` import copy of a message with no Message-ID, followed by a `server` upload of the same file, lists twice: the rehome pass that sets such copies aside keys them by Message-ID.
  - Upload dedupe for a message with no Message-ID (Takeout chats and drafts) can only match Subject and Date against the folder's cached header rows, since there is nothing to search the server for. It can go up twice when the cache does not list an earlier upload, when a second run starts before the folder is synced, or when a kill lands between the server's OK and the journal's tail write. A message with a Message-ID but no Date is never matched and goes up on every run.
  - A label Gmail refuses is counted, not retried, and that message keeps only its home folder. The label step has been exercised against the mock IMAP server only, not a live Gmail account.
  - `import_mbox` in `local` and `folder` mode and `delete_local_folder` do their work inside their RPC, against the rule that long jobs answer at once: the import reports `mbox-import-progress`, while the folder delete has no progress event and no cancel route, and a large one holds the call for minutes.
- **JMAP edges.**
  - No OAuth for JMAP: an account signs in with a password or an API token (`JmapAuth`), so a provider that offers JMAP only behind OAuth cannot be added yet.
  - In a JMAP-format vault, three writers leave a JMAP account's record without server ids (`server: null`): the archive's JMAP arm, Archive & delete's JMAP fetch (`abd::jmap_ops`) and a local recover from the bin (`from_trash_jmap` in `handlers/deleted.rs`). No reader uses the ids yet. In a Maildir-format vault, JMAP mail is Maildir `.eml` files named by ledger uid like every other account's, and no server id is stored.
  - JMAP arrival bodies are cached for INBOX only (IDLE parity). Arrivals in other mailboxes are cached later by the hoarder.
  - `delete_mailbox` destroys a whole tree in one `Mailbox/set`, deepest first, with `onDestroyRemoveEmails` off. A server that does not honour the order may refuse a parent with `mailboxHasChild`, and a folder that still holds mail is refused with `mailboxHasEmail`; neither is retried level by level.
  - The bridge's status probes (`uidNext`, `highestModseq`) run the account-wide delta first, so a probe that arrives while a delta is running waits behind it.
  - `JmapSessions::forget` drops the account's connected client unconditionally, even when a newer client replaced the one that failed; the next call connects again.
  - The polling loop of a session without `eventSourceUrl` (`Ended::NoEventSource`) never leaves polling: new credentials, or an EventSource the server starts offering later, are picked up only when the watcher is unwatched and watched again.
  - The hoarder's count memo (`totalEmails` per folder, from the pass's own mailbox listing) cannot see count-neutral churn (one email in and one out leaves the count unchanged), so such a folder is only relisted at the 24 h `RELIST_EVERY`.
- **JMAP storage format edges.**
  - Only the generation repair sets the leftover hint (`storageLeftover`). Other messages left in the format the vault is not in (a writer that could not read the marker wrote a Maildir file into a JMAP vault) are converted by the next start, but Settings offers none for them.
  - The generation repair (`maildir::repair_generation`, after a UIDVALIDITY change) first turns a JMAP mailbox's records back into Maildir files (`message_store::demote_records`), for the whole folder in one hold of the mailbox lock, against the one-unit rule. A record that will not parse stops that demotion, so the folder's repair is tried again each time and never finishes (the record stays, nothing is lost), and the files it made are not offered for conversion.
  - The conversion addresses a folder by its on-disk directory, so an NFD name read back from an HFS+ or SMB volume keys the folder's mailbox lock differently from a writer that spells it in NFC: in a window of milliseconds, one flag change can be lost or one delete undone. Such a folder also misses its header cache rows, so it skips the rehome wait and the INTERNALDATE `receivedAt`.
  - `storage_format_pause`, `_resume` and `_cancel` go through the vault gate, so none of them reaches a job while the vault is closed.
  - An adopt does not carry the vault's conversion journal (only a move does, `follow_move`): a conversion in progress or stopped at the adopt stays with the old folder, and the adopted vault shows none.
  - An older build sharing a JMAP vault on a NAS has no `message_blobs` in its `VAULT_DIRS` and reads `cur/` only: it shows none of the records, and a vault move made by that build leaves the blobs behind, separating the records from their blobs.
- **Blitz interactions are experimental and not at parity.** The dark app theme keeps the context menu and the selection highlight light-coloured: the paper follows the theme through plan B's Dark Reader port, but `theme/darkSwatch.js` is not yet fed by a `render.inspect` probe, so both stay on their light colours. The layer's highlight follows DOM order, so a selection spanning a nested inline box (an inline-block, a button) can be highlighted differently than it copies, which follows reading order; a float or an absolute box copies after its paragraph. A drag that leaves the body box can select into the app chrome (see the drag clamp below). Rich copy writes HTML only, with no RTF or WebArchive flavour. A glyph that exists only in a family's latin-ext file falls back to the next family (see the Mail fonts bullet of the Blitz section), which must be closed before Blitz becomes the default.
- **Blitz on every surface: known limitations.** The surfaces work and are tested on the mini (`connected-blitz-surfaces` 17 of 17, `connected-blitz-preview` 1 of 1); these remain and none is a blocker for the experimental setting.
  - Drag clamp: a drag that leaves the body box can still select into the app chrome; nothing clamps it.
  - `inBody` scope: the context menu treats a press anywhere in the body's outer box as inside the body, not only in the inner click area (visible with `fill` and `collapsedMax` boxes).
  - Selection restore after rewrap: a width change remounts the body's layer and a live selection is lost.
  - B's per-doc budget: the engine's caps do not compose into one per-document memory budget (a hostile document can peak at roughly 600 to 700 MiB), and the watchdog killing a worker loses every doc on it.
  - Fold state is kept per message, so two bodies that share one doc (identical html, such as twin chat bubbles) share a fold: one click toggles both.
  - An image-heavy export whose html (with inlined `data:` images) is over 4 MiB fails in Blitz (`render_too_large`, named in `failures`), where the web path succeeds.
  - Tall exports: a relayout between the settle and the tiles (a late font or `@import`) can truncate a grown document or fail a shrunk one, and the paint time of a very tall export is unbounded apart from the 20 s image budget.
  - Engine residue the parity matrix still measures and D did not fix: the collapsed-border painter (*Vendored engine*), and the geometry classes left from plan B (code font x offset, postmark tables, cell edges about 3px, width-dependent hybrid and responsive layouts).
  - `tests/e2e/connected-blitz-reader.test.js` is red on main, before this work (tile 0 never shows the fixture colours); it is not a D regression.
  - Image double-click (opening a picture in the viewer, `attachImageDoubleClick`) is not available on any Blitz surface. A double-click inside a chat bubble's Blitz body is ignored, so it does not open the full view.
  - Thread and chat first paint missed its perf gate on a debug build (see *Thread and chat perf gate*); the numbers went to Rokas.
  - A window destroyed without a close request (the detached compose window, and the compose original that `ComposeModal` destroys directly) leaves its docs open in the worker until the app quits or the worker restarts. The 32-doc cap per worker bounds them, and the worker does not idle out meanwhile.

## State Management Guidelines

Use Zustand stores for durable app state shared across screens and workflows.

- Put long-lived state, cache coordination, and async orchestration in stores.
- Put component-local concerns in React component state.
- Put reusable side-effect orchestration in hooks.
- Put integration wrappers in `src/services/`.

Avoid:

- Duplicating the same source of truth across multiple stores.
- Hiding critical state transitions in deeply nested components.
- Mixing transport calls directly into presentational components.

Settings window lifetime is owned by `useSettingsWindow`: closed, open, or minimized. Generic open actions resume the same session; an explicit page/account/section link creates a new navigation request. Minimized Settings keeps its component tree and scroll containers mounted inside an inert dialog, while releasing focus trapping and pausing page-level keyboard listeners. Closing ends that session. This is transient UI state, not persisted account or preference data.

### Mailbox Explorer

`EmailList` switches between the existing list and `ExplorerView`. `utils/explorer` derives date, sender and conversation groups from the current loaded headers; groups never create mailboxes or move stored messages. Sender grouping uses normalized addresses and date grouping uses the local calendar. Group selection retains each message's account, mailbox and UID through the existing selection workflow.

Explorer owns its navigation, local header search, row virtualization and next/previous navigation. Settings persist its mode, date detail and bounded navigation paths per account, mailbox, storage view and grouping. Partial mailbox windows are identified in the UI and use the existing explicit load-more action. Email rows, state indicators, actions and the reader are shared with List.

Conversation groups use RFC relationships with subject fallback disabled and thread IDs qualified by account. Counts and selections stay inside the browsed date/mailbox scope; the full conversation action can include loaded messages outside that scope, including Sent. Explorer supplies its own thread map to refresh an open conversation even in Date/Sender mode. The legacy List thread refresh is inactive while Explorer owns the pane.

## Performance and Caching

### Mail Insights

Insights is a separate sidebar workspace. `insightsStore` owns shared filters, scan and query generations and drill-down; it renders what the daemon answers and computes no counts. `insightsSession` asks the daemon for one model per visit: `insights.build` (with a `buildId` the app picks) answers at once, and `handlers::insights_aggregate` pages the snapshot below in-process on a background-QoS thread, one 1,000-row page per unit, retrying a snapshot a sync made stale after 250, 500 and 1000 ms. It reports `insights-build-progress` frames (`{buildId, loaded, total, coverage}`, then one `finished` frame with `ok` and the coverage or a `{code, coverage}` error); `insights.status` answers the same state when the event stream lagged or the shell's event channel reconnected (after a daemon restart, frames sent before the channel came back reach nobody); a build the restarted daemon lost is started again once under the same `buildId`. `insights.aggregate` (totals, senders, days, timeline lanes) and `insights.messages` (a drill-down, optionally one `messageKey`) query the built `mailvault_core::insights_model::Model` as often as the controls change; a superseded or cancelled build is never adopted. `insights.release` drops a model or cancels its build when the workspace closes or refreshes; a model idle for 30 minutes, or past the three newest, is dropped by the daemon, and the session rebuilds once on `modelExpired`. `insights_model` owns logical-message identity, direction events, IANA time-zone day and week bucketing (`jiff`, tz database bundled), sender ranking and exact matching-message keys; `src-core/tests/fixtures/insights-model-cases.json` pins its answers to those of the deleted JS model. Only validated display preferences persist.

`src-daemon/src/insights.rs` (moved from `src-tauri/src/insights.rs` at Task 3.6) inventories the available header cache and Maildir metadata through the configured vault root. It exposes bounded pages with file/generation validation and explicit coverage; it never treats the current visible mailbox window as the full inventory. Provider receive dates and original sent dates retain provenance, and legacy fallback or missing dates remain disclosed. The enumerated file set is frozen for that scan; later arrivals appear on refresh. Changes to captured files, source metadata, UID generations, directory identity or vault/account context invalidate the whole snapshot rather than mixing generations. Directory timestamp changes from independent mail arrivals do not invalidate captured headers.

`openInsightsMessage` verifies a physical account/mailbox/UID locator and known identity evidence before using the existing reader. The ordinary reader is unmounted during an Insights visit; its previous selection is restored from current headers only when still valid. Choosing an ordinary account or folder discards that restoration. Insights chart browsing reads headers only; opening a matching message uses normal reader loading and mark-as-read behavior. Source, export, and reply actions keep the selected message's account and mailbox context.

### Reads come from the database

The daemon's databases are what every read consults: list headers, which messages the vault holds and with which flags, and the parsed light row of each stored message. The disk is not re-read to answer those questions.

For the vault that database is the vault registry (see Where state lives). Its blind spot is by design: a change made to the vault from outside the daemon mid-session (another Mac writing a shared SMB vault, a file copied in by hand) is not seen until the mailbox is listed again. A file removed or renamed from outside fails its next open, which relists the mailbox once; a file added from outside fails no open, because a verified miss is authoritative, so it stays invisible until the mailbox is invalidated (a structural vault change, `vault_reopen`) or the next daemon session. Jobs that walk a whole mailbox on their own schedule (the no-index search scan, backup and archive runs, generation repair) still list it from disk.

- **Read the disk once, or on recovery.** A mailbox's vault directory is listed and verified at most once per daemon session, and again only after a failed read (a stored filename that no longer opens invalidates the mailbox, triggers one rescan, then one retry). Never list or stat a whole directory to answer a question about one message.
- **Parse once.** A message is MIME-parsed the first time its light row is asked for and the result is stored; later readers take the stored row. A write or a verify records the file and never parses, and a rewritten file drops its stored row so the next read parses it again; a flag rename keeps it. A light row that gains a field is no schema change: a search index rebuild drops every stored row (`vault_reparse_rows` does it alone when the index is off), and the settings migration that adds the field raises the app's rebuild offer. Only opening a message's body or an attachment reads its `.eml`, and one open resolves the file and parses it once, however many parts it needs.
- **Writers update the database before replying.** A vault write that returns has already updated or invalidated the rows it touched, so the next read sees it. A coalesced background nudge (the search index's) is not a substitute.
- **Unknown is not empty.** A mailbox not yet verified, or a read that failed, returns `null` ("unknown, keep what you know"), never an empty set; callers persist only real answers.
- **Batch, do not loop.** One RPC per user action, not one per message, image or folder; chunk large id sets instead of issuing one query per id or one unbounded `IN (...)`.

### General caching rules

Caching exists to reduce latency, not to create alternate truth sources.

- Prefer fast restore plus background sync over blocking the UI.
- Keep cache invalidation rules explicit.
- Make background work cancelable or ignorable when user context changes.
- Optimize hot paths with measurement and clear ownership, not incidental memoization.

When adding caching, document:

- What is cached.
- What invalidates it.
- Whether stale data is acceptable temporarily.
- How recovery works if cache and server diverge.

## Reliability Rules

Mail flows are networked and failure-prone. Design for partial failure.

- Retry transient transport and keychain failures when appropriate.
- Preserve local data on failure; never trade correctness for convenience.
- Prefer degraded operation over hard failure where the user can still make progress.
- Avoid destructive writes that can silently drop existing local state.
- Treat account switching, offline mode, and provider-specific limitations as first-class scenarios.

## Provider Strategy

Provider-specific behavior should be isolated behind transport or configuration boundaries.

- General UI should work across providers.
- Special-case Microsoft Graph, OAuth provider quirks, and server capability differences in transport and service layers.
- JMAP rides the existing `imap_*` RPC surface through one interception point (`handlers::jmap_bridge::intercept`), so the frontend, the sync engine's callers and the cache keep one shape across IMAP and JMAP. Provider branching is `uses_jmap()` / `isJmapAccount` at the boundary (the bridge, the send path, the engine's id-based arms, discovery), never inside general UI. A new IMAP-session-opening path must branch on `uses_jmap()` first; `ImapPool` refuses a JMAP account with `E_JMAP_NOT_IMAP` as the net under a missed branch.
- Do not leak provider-specific branching into many unrelated components.

If a provider needs custom behavior, add it in the narrowest layer that can fully own it.

## Threading and View Consistency

Threading, sender metadata, and message indicators affect many views. When changing them:

- Keep list, thread, chat, and detail views semantically aligned.
- Prefer shared parsing and derivation utilities over view-specific reimplementation.
- Document intentional differences explicitly rather than letting them drift.

## Change Guidelines

When making architectural changes:

- Prefer one clear owner for each business rule.
- Keep data contracts explicit between frontend and Rust.
- Avoid "temporary" parallel code paths unless there is a defined removal plan.
- Update docs when the architecture or core boundaries change, not for every small implementation tweak.

Good reasons to update this file:

- New subsystem or transport layer.
- State ownership changes across stores/services.
- Storage format or cache model changes.
- New cross-cutting reliability or provider rules.

Bad reasons to update this file:

- Renaming helpers.
- Tuning constants.
- Minor UI layout details.
- Adding one more command to an existing subsystem.

## Verification Expectations

Non-trivial changes should be verified at the layer they affect.

- Frontend state and pure logic: unit tests.
- Rust transport or storage behavior: Rust tests where practical, in `src-core/` (CI does not run `cargo test` on the `src-tauri` crate).
- IMAP client behavior, including server misbehavior: the mock server in `src-mock-imap`. Server quirks that caused a shipped bug (spliced keepalives, unparseable ESEARCH, truncated UID lists, stalled APPEND) belong here as a fault scenario, not as a live test — they cannot be reproduced on demand against a real provider.
- Cross-layer user flows: integration or end-to-end coverage when the risk justifies it.
- Live provider tests (`tests/integration/`) are a conformance canary against a real mailbox. They run on a schedule, not per push, and must not be the only coverage for any client behavior.

Architectural work is complete only when the new boundary is understandable and testable.
